- **Binary:** `target/release/cratonvm-h2database-suite` (uniquely named —

## Runner-setup issues found (fixed in the runner/checkout, not upstream H2)

1. **`mvn test-compile` failed with `Source option 5 is no longer supported`**
   under the host's default toolchain. H2's `pom.xml` sets
   `<maven.compiler.release>11</maven.compiler.release>` but never pins a
   `maven-compiler-plugin` version, so Maven fell back to the ancient
   super-POM default (`3.1`, from ~2013), which predates the `release`
   property entirely and defaults to Java 5. Fixed by pinning
   `maven-compiler-plugin` `3.13.0` explicitly in the (locally-managed, not
   git-tracked) `apps/h2database/h2/pom.xml`.
2. **Even after that fix, compilation failed with `release version 11 not
   supported`.** The host's `java-21-openjdk-amd64` package turned out to be
   JRE-only (`/usr/lib/jvm/java-21-openjdk-amd64/bin/` has no `javac`), so
   Maven's in-process compiler mojo silently degraded. `update-alternatives
   --list javac` resolves to a real JDK 17 install
   (`/usr/lib/jvm/java-17-openjdk-amd64`). Added a `MVN_JAVA_HOME` override to
   `run-h2-suite.sh setup` so this doesn't need touching `JAVA_HOME` globally
   or the JDK25 used to actually run the tests.
3. **`cratonvm`'s classpath flag is `-c`/`--classpath`, not `-cp`** (that's
   plain `java`'s spelling). Fixed in `run_mode()`'s per-mode `jargs`.
4. **`jit-syn`/`nojit-syn` modes need an explicit `--synthetic-jdk` flag** —
   omitting `--java-home` does *not* select synthetic mode by itself;
   CratonVM auto-detects and boots a real JDK whenever one is on `PATH`, so
   the synthetic modes were silently running against the real JDK until this
   was added.

## Major finding: CratonVM real-JDK execution hangs on nearly every H2 `db`-package test

Of the 42 classes run under `jit-real` before the run was stopped:

```
HANG 39
FAIL  3
PASS  0
```

The same 42 classes' HotSpot counterparts overwhelmingly pass (HotSpot's
full-suite result, for reference, is `PASS 200 / FAIL 13 / HANG 5` across all
218 — the 13 HotSpot fails are environment noise: no local Postgres for
`TestJoin`, no trusted TLS cert for `TestTools`, a JDK25-vs-expected-JDK
`ClassCastException` in `TestClassLoaderLeak`, etc.; the 5 HotSpot hangs are
`org.h2.test.synth.*` classes that are open-ended stress/chaos tests by
design).

**This is not a boot-time or classpath problem.** Each `TestBase.println()`
call in H2's own progress-percentage output shows the hang happening
*mid-test*, often quite late:

```
19:34:19 00:01.104 org.h2.test.db.TestMultiDimension 35%
19:34:20 00:02.105 org.h2.test.db.TestMultiDimension 70%
<nothing else for the rest of the 60s window>
```

A manual `--nojit` (pure interpreter) rerun of the same class got even
further before stalling:

```
19:34:50 00:01.198 org.h2.test.db.TestMultiDimension 20%
19:34:51 00:02.198 org.h2.test.db.TestMultiDimension 46%
19:34:52 00:03.200 org.h2.test.db.TestMultiDimension 75%
19:34:53 00:04.204 org.h2.test.db.TestMultiDimension 97%
<hang>
```

So the hang is **not JIT-specific** (reproduces identically with `--nojit`)
and the test consistently makes it deep into (or to the very end of) its
`test()` method before stalling — consistent with something in a
teardown/connection-close path shared by most `TestDb`-based tests (many
close a `Connection`/delete db files as their last step), rather than a bug
in any one test's SQL logic. `--synthetic-jdk` mode was **not** a usable
comparison point here — it fails immediately on an unrelated gap
(`NoSuchMethodError: java.time.format.DateTimeFormatter.ofPattern`, a
missing synthetic stub hit from `TestBase.<clinit>`), so real-JDK mode is
required to exercise H2 at all currently.

Given a ~93% hang rate at `--class-to 60`, running the remaining 176 classes
serially would cost multiple additional hours for the same repeated signal,
so the run was stopped after 42 classes rather than burning the session on a
single already-well-evidenced finding. **This needs dedicated root-cause
investigation** (a live gdb attach on a hung process while it's stuck would
be the natural next step) — flagged as a follow-up task rather than chased
further here.
