## Runner-setup issue found (fixed in the fixture, not the runner)

`/data/data/tomcat-dohead-fixture-20260717/output/build/conf/` was
**completely empty** — no `logging.properties`, `web.xml`, `server.xml`,
`context.xml`, `tomcat-users.xml`. The fixture had only ever had
`ant test-compile` run against it (to get compiled test classes + a
classpath), never `ant deploy` (which populates `output/build/conf` from the
checkout's top-level `conf/` via a `<copy>` task). Every `TomcatBaseTest`
subclass hit `FileNotFoundException` from JULI's `ClassLoaderLogManager`
trying to read `conf/logging.properties`, which cascaded into `A child
container failed during start` for the embedded Tomcat instance. Fixed with a
plain `cp conf/*.{xml,xsd,properties} output/build/conf/` (verified none of
the source files carry unsubstituted Ant `${filterset}` tokens, so no need to
run the real `ant deploy` target). This only flipped 1/196 non-PASS classes
to PASS — most of the failure set was unrelated (see below).

## Why a HotSpot control pass mattered

Before attributing any of the 195 remaining non-PASS classes to CratonVM, ran
the identical 196-class list under real JDK 25 in the same fixture. **171/196
failed under HotSpot too** — this fixture has no `httpd` binary
(`org.apache.tomcat.integration.httpd.*`), no OCSP-responder test
infrastructure (`org.apache.tomcat.security.TestSecurity2017Ocsp`,
`...ocsp.*`), and doesn't apply the larger `-Xmx` Ant's `<test>` selector
normally gives `*LargeHeap` classes (they OOM at the flat 2g default on both
VMs). Diffing HotSpot-PASS against CratonVM-not-PASS isolated exactly **23
genuine CratonVM-only regressions** — see the internal record named above
for the full list and triage notes.
