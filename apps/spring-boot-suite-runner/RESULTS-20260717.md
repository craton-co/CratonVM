## Three runner bugs found + fixed this round

Found while HotSpot-baselining before trusting any comparison (all three
made `-Setup`/HotSpot runs exit 0 while silently producing wrong results —
worth checking for on any future rerun):

1. **`Invoke-Gradlew`'s `-Args` parameter name collided with PowerShell's
   automatic `$args` variable**, silently corrupting `& $Gradlew @Args`
   splatting — gradlew received zero arguments, defaulted to the `help`
   task, ran it against the wrong project directory, and every `-Setup`
   invocation exited 0 while producing **zero** real
   `cratonvm-test-cp.txt` classpath files and an empty class list. Compounded
   by a second bug in the same function: the `-p` project-dir argument
   passed the bare subtree name (`"core"`) instead of the already-computed
   absolute path, which Gradle resolves relative to the *caller's* cwd, not
   the checkout root. Renamed the parameter to `-GradleArgs` and fixed the
   `-p` argument. Verified: `-Setup` now correctly discovers 1975 classes
   across 146 real classpath files (matches the original 2026-07-11
   baseline class count exactly).
2. **HotSpot runs never applied `--add-opens=java.base/java.net=ALL-UNNAMED`.**
   Six modules (jetty, security, servlet, tomcat, webflux, websocket) set
   this flag on their own Gradle `test` task JVM args for reflective field
   resets in web-server test fixtures; this runner launches `SbRunner`
   directly instead of through Gradle's `test` task, so it never applied —
   those 7 classes failed on real HotSpot with `IllegalStateException:
   Unable to reset field`, which would have been misattributed as a genuine
   CratonVM difference. Applied the flag universally to HotSpot invocations
   (opens are additive/harmless for modules that don't need it). Verified:
   7/8 affected classes now PASS on HotSpot; the 8th fails on an unrelated
   genuine `AssertionFailedError`.
3. Two classes (`ConfigTreePropertySourceTests`, `FileWatcherTests`) fail on
   both VMs identically with a Windows `FileSystemException` creating a
   symlink in temp — this host lacks `SeCreateSymbolicLinkPrivilege`/
   Developer Mode. A genuine host-level limitation, not a JDK or CratonVM
   difference; not fixed (affects both VMs equally, so it self-filters out
   of the CratonVM-specific bucket below regardless).

## Diff methodology + actionable bucket

For each of the 510 classes, compared CratonVM status against HotSpot
status on the identical class:

- CratonVM `PASS` → fixed, dropped from any outstanding list (35 classes).
- CratonVM non-`PASS` **and** HotSpot has the **same** status on that class
  → pre-existing Spring Boot test issue unrelated to CratonVM, filtered out
  (**46 classes**: all 43 `EMPTY` — these are structurally empty test
  classes/fixtures on both VMs, not a CratonVM gap — plus 3 `FAIL` that
  fail identically on both).

  CratonVM-specific gap, kept.

## One notable CRASH finding (not fixed, flagged for follow-up)

3 of the 5 CRASHes (`BraveBaggagePropagationIntegrationTests`,
`OpenTelemetryBaggagePropagationIntegrationTests`,
`ModifiedClassPathExtensionForkParameterizedTests`/`...OverridesParameterizedTests`)
share an identical `NoClassDefFoundError: org/junit/platform/commons/util/ExceptionUtils`
at `SbRunner.main`. This matches a signature flagged as a suspected
"pathing-jar manifest truncation" runner artifact back in the 2026-07-11
run notes — **investigated and ruled out this round**: the classpath
genuinely contains `junit-platform-commons-6.0.3.jar`, and the brave
example ran for **186 seconds** (not an instant startup failure) before
hitting the missing class late, during JUnit's own failure-reporting path,
after a long sequence of `cratonvm::gc::guard` "out-of-bounds field read
dropped" warnings on `InterceptingExecutableInvoker`. This looks like a
genuine, reproducible CratonVM classloading bug (a class failing to
resolve very late in a run, possibly downstream of the same class-layout
condition the GC guard is absorbing), not a runner/classpath artifact —
worth a dedicated investigation, not attempted here.

Background context: the `cratonvm::gc::guard` "out-of-bounds field read
dropped" warning appears in 466/510 (91%) of this round's logs, including
many that otherwise `PASS` — it's a self-describing benign/absorbed guard
condition ("class layout is correct; the bug is in the caller's slot
computation"), not itself predictive of failure. Noted here only because
it precedes the one CRASH cluster investigated above; not established as
causal.

## Reproduce / rerun

```powershell
$env:JAVA_HOME = "C:\Program Files\Eclipse Adoptium\jdk-25.0.3.9-hotspot"
$exe = "<worktree>\target\release\cratonvm-spring-boot-rerun0717.exe"

# HotSpot baseline
powershell.exe -NoProfile -ExecutionPolicy Bypass -File apps\spring-boot-suite-runner\run-spring-boot-suite.ps1 `
  -Vm hotspot -JdkHome $env:JAVA_HOME -ClassList <class-list.tsv> -RunName <name> -Parallel 6 -TimeoutSec 300

# CratonVM rerun
powershell.exe -NoProfile -ExecutionPolicy Bypass -File apps\spring-boot-suite-runner\run-spring-boot-suite.ps1 `
  -Vm craton -Exe $exe -JdkHome $env:JAVA_HOME -ClassList <class-list.tsv> -RunName <name> -Parallel 2 -TimeoutSec 300
```

`<class-list.tsv>` needs a `module<TAB>class` header row (`Import-Csv`
treats the first line as a header — a bare data-first file silently
misparses, dropping one real row and using its values as column names).
