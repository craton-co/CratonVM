## Two data-quality issues found and resolved mid-round

1. **Host-load confound (07-29 preliminary pass, superseded by this
   round).** An earlier same-day attempt at this exact rerun returned 10/22
   HANG while 15 other `cratonvm`/`cargo`/`rustc` processes from concurrent
   sessions were running (50% host CPU). A serialized (`-Parallel 1`)
   reverify of those 10 showed only 6 were genuinely stuck; 2 resolved
   cleanly (`ManagementWebSecurityAutoConfigurationTests` → PASS in 308s,
   `MongoAutoConfigurationTests` → FAIL in 68s — both just slow under
   contention, not stuck) and 2 came back `ClassNotFoundException`
   (see below). This confirms [[feedback_shared_host_multitenant_confound]]
   applies here too — don't trust a HANG-heavy result from this suite
   without checking host load first.
2. **Stale absolute classpaths pointing at a deleted worktree (this
   round).** 18 of 146 `cratonvm-test-cp.txt` files in this worktree's
   `apps/spring-boot` checkout still contained absolute paths to
   `C:\craton\CratonVM-spring-boot-rerun-20260717\...` — the *original*
   worktree this checkout was `robocopy`'d from on 2026-07-28 (see
   [[feedback_shared_host_disk_cleanup]]'s 07-29 entry for that recovery).
   Those paths worked as long as the old, git-orphaned directory
   physically survived on disk; it has since been fully deleted (another
   disk-cleanup sweep), so 5 classes whose classpath still pointed there
   failed to load (`ClassNotFoundException`, all under 5s) despite the
   actual compiled `.class` files being present and correct in *this*
   worktree the whole time. Fixed with a global path rewrite across all 18
   affected files (`sed` replace old-worktree-name → current-worktree-name)
   rather than a full `-Setup` re-run — verified via a
   `grep -c` sweep showing 0 remaining stale references, and via a targeted
   rerun of the 5 affected classes confirming they now load and execute.
