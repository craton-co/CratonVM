## Two general VM bugs found + fixed this run

1. **Native-call arg-pinning panic on >4 args** (`vm/src/vm/vm_exec.rs`) —
   `Option::unwrap_or(X)` eagerly evaluates `X` in Rust (unlike
   `unwrap_or_else`), so `&inline_root_indices[..args.len()]` was sliced
   *even when* the `Some(overflow_root_indices)` branch was going to be used,
   panicking (`range end index N out of range for slice of length 4`) on
   **any** native call with more than 4 arguments. 100% deterministic, VM-wide
   (not Spring-Boot-specific) — crashed the very first `SbRunner.main` native
   call before any test could run. Fixed by switching to `unwrap_or_else`.
2. Not a VM bug, but the sibling classpath-generation bug is worth recording:
   `cratonvm-test-cp.init.gradle`'s `cratonvmTestCp` task read
   `sourceSets.test.runtimeClasspath` in `doLast` without declaring it as a
   task **input**, so Gradle never inferred that cross-project dependencies'
   `jar` tasks needed to run first. Classpaths silently pointed at
   `build/libs/*.jar` files that didn't exist (only `testClasses` had run),
   producing mass `NoClassDefFoundError` unrelated to CratonVM. Fixed by
   adding `inputs.files(cpFiles)` to the task registration.

## Notable per-class findings (not fixed, flagged for follow-up)

- **CGLIB dynamic-class generation**: `class not found:
  .../AbstractApplicationContextRunnerTests$ExampleProperties$$SpringCGLIB$$0`
  — `ApplicationContextRunnerTests`, `WebApplicationContextRunnerTests`,
  `ReactiveWebApplicationContextRunnerTests`, `SpringBootContextLoaderKotlinTests`
  all CRASH the same way (`core/spring-boot-test`). Likely related to the
  known SB-03 `@Configuration` CGLIB enhancement gap.
- **HANG cluster (150 classes, 300s timeout each)**: dominates wall time
  (~half of total). Includes YAML loading (`OriginTrackedYamlLoaderTests`),
  annotation processing (`AutoConfigureAnnotationProcessorTests`), devtools
  property binding, and `ModifiedClassPathExtensionForkTests` (spawns a
  forked JVM — likely inherently unsupported, matches the TestKit-class
  exclusion pattern from other suite runners). **See the "HANG rerun" section
  below — 60% of these are genuinely stuck even at 5x the timeout, not just
  slow.**
- See `results.tsv` `note` column per class for a quick FAIL/CRASH signature
  index before opening individual logs.
- **FAIL triage**: the 508 `FAIL`s were clustered by log signature into 5
  characterized bug docs under `docs/known-issues/springboot/` (~146 classes
  covered directly) — see that directory's `README.md` for the summary
  table. Largest: `OnClassCondition.addAll` receiving a stray
  `NullPointerException` object where a `String[]` annotation attribute
  belongs (75 classes, 348 occurrences), breaking `@ConditionalOnClass`
  broadly.

## HANG rerun (150 classes, 1500s timeout, 5 shards)

Reran exactly the 150 classes that hit the original run's 300s timeout, at
5x the timeout (1500s), to separate "genuinely stuck" from "just slower than
300s" — sharded 5 ways (`RunName=hang-rerun-20260711`, modes `hshard1..5`,
`-Parallel 2`, `-ClassList` pointed at the extracted HANG set).

| Reclassified as | Count | % of the 150 |

| HANG (still stuck at 1500s) | 90 | 60% |
| FAIL | 51 | 34% |
| PASS | 7 | 5% |
| CRASH | 2 | 1% |

**60% of the original HANG classes are genuinely stuck**, not just slow —
confirms the 300s timeout wasn't the primary cause of most of that bucket.
The 90 confirmed hangs spread across the suite (no single dominant module:
`core/spring-boot` 15, `spring-boot-jdbc` 6, `spring-boot-security` 4,
`spring-boot-devtools` 4, then a long tail of 1-3 each across ~25 other
modules) — a genuine long-tail hang class, not yet clustered by root cause.
