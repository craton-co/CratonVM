## Prerequisites that should land FIRST (small fixes, possibly already committed by the session that wrote this)
1. **`StackWalker.getCallerClass()` off-by-one** — blocks every single-test entrypoint (`TestX.main` → `TestBase.createCaller()` → `getCallerClass`). `native-builtins/src/stack_walker.rs:203` (and dup `native-builtins/src/phases_late.rs:15066`) return the `@CallerSensitive` caller's class (`TestBase`) instead of *its* caller (`TestDate`). **Caveat:** JIT vs `--nojit` produce different `thread.frames` shapes (`--nojit` already returns correct), so verify both modes — a blind "skip one more" may over-skip under `--nojit`.
2. **`Collection.toArray(T[])` multi-dim** — repro `List<String[]>.toArray(new String[0][])` → CCE `Object -> [[String` (probe `C:/tmp/audit/ToArrayProbe.java`). **CORRECTED PATH (verified 2026-06-03):** the failing allocation is NOT `native_al_to_array_typed` (`native-collections/src/lib.rs:1293`) — that native is never even reached for this case (no `CRATONVM_DBG_SBLOAD` trace). The real culprit is the **`Arrays.copyOf(Object[], int, Class)` native at `native-builtins/src/phases_early.rs:442`**, which `ArrayList.toArray(T[])` calls with `a.getClass()` and which **ignores the Class arg**, always doing `ctx.new_array(Reference, len)` = bare `Object[]`. **Attempted fix (reverted):** decode the Class arg via `crate::lang_class::mirror_class_id` -> `class_name_of_id` -> strip one `[` -> `class_id_by_name(component)` -> `new_ref_array`. It did NOT work — `class_id_by_name` apparently does **not resolve array-descriptor names** like `[Ljava/lang/String;` (only plain `pkg/Class`), so it returns `None` and falls back to `Object[]`. **RESOLVED the API gap (commit `babe433`):** added `NativeContext::array_component_class_id(class_id)` (reads `ArrayInfo.component_class_id`) and used it in the 3-arg `Arrays.copyOf` native — **verified working** for direct calls: `Arrays.copyOf(src, n, String[][].class)` and `...tmpl.getClass())` both now return `[[Ljava.lang.String;` on CratonVM (probes `C:/tmp/audit/CopyOf2.java`, `GetClassProbe.java`).

**BUT `ArrayList.toArray(T[])` is STILL broken** — and the responsible code is an UNIDENTIFIED third path:
- `ToArr3.java`: `ls.toArray(new String[0])` → CratonVM `[Ljava.lang.Object;` len=2 (1-D "passes" only via lenient checkcast); `l2.toArray(new String[0][])` → `[Ljava.lang.Object;` len=2, element[0] is correctly a `String[]` — i.e. **elements are copied correctly but the array is allocated as `Object[]`**, and `(String[][])` CCEs.
- It is **NOT** the 3-arg `Arrays.copyOf` native (that works in isolation), and **NOT** `native_al_to_array_typed`/`native_ll_to_array_typed` (`CRATONVM_DBG_SBLOAD=1` prints nothing, and re-adding the typed `alloc_array_like` fix there had ZERO effect — the function never fires for ArrayList).

The ONLY traces during the call are the *result* `Object[]`'s `getClass` (from the test's `println`) and a `get_or_create_class_mirror cid=…(="[Ljava/lang/Object;")`.

KEY NARROWING — the real mechanism:
- `(new String[0][]).getClass()` in **app-frame** code → correct `[[Ljava/lang/String;` (reaches `native_object_get_class`, header `cid=384=[Ljava/lang/String;`).
- The **template's** `a.getClass()` *inside* `ArrayList.toArray` is **never traced** — it does NOT reach `native_object_get_class`, NOR `get_or_create_class_mirror`, NOR the proxy getClass path, NOR the intrinsic callback (which would reach the native). Yet `Arrays.copyOf` then takes its `(newType == Object[].class) ? new Object[]` fast-path, so `newType` (== the template's inline getClass) is resolving to **`Object[].class` (ClassId 385 / `[Ljava/lang/Object;`)** instead of `[[Ljava/lang/String;`.
- ⇒ The bug is an **inline `Object.getClass()` fast-path / intrinsic-IC that returns a wrong (cached `Object[]`) Class mirror for an array receiver inside `ArrayList.toArray`**, NOT any toArray/copyOf native. `Arrays.copyOf` real bytecode IS running (it does `ldc Object[].class` → `get_or_create_class_mirror(385)`); it just compares against a poisoned `newType`.
- **Next step:** instrument the *virtual* `getClass` intrinsic IC populate + execute in `vm/src/runtime/interpreter.rs` (the `CachedInvokeTarget::Intrinsic` arms at ~12115 / ~15273 and the populate at ~15506) — print the receiver `class_id`, the IC `guard_class_id`, and the returned mirror's class_id for `getClass` on array receivers. Suspect: the IC caches/folds the *return mirror* from a first `Object[]` receiver and reuses it across receiver types (the `actual_class_id != guard_class_id` guard at 15302 keys on the array *component* id, which collides — every reference array shares its component's `class_id` in the heap header). Fix the guard to also distinguish `ObjectKind::Array` (or to re-resolve getClass on arrays through `native_object_get_class` unconditionally). H2 hits this in `org.h2.result.SortOrder.sort` (`Value[][]`).
- `native_al_to_array_typed`'s too-small-template branch HAS been corrected to `new_ref_array(class_id_of_object(template), size)` (correct for synthetic ArrayLists), but that native never fires for a real `java/util/ArrayList`, so it does not fix the H2 case on its own.
- **Constant-folding of `a.getClass()` to the static `Object[]` type is REFUTED** (`/tmp/tatest/FOLD.java`): `static Class<?> f(Object[] a){return a.getClass();}` called with a `String[][]` returns the correct **runtime** `[[Ljava/lang/String;` in app code on CratonVM. So `getClass()` itself is correct; the breakage is **specific to the bytecode of `java/util/ArrayList.toArray(T[])`** (a bootstrap class). **Root cause is the `getClass` inline-cache at the `a.getClass()` call site INSIDE `ArrayList.toArray`** (per-`(caller_class_id, cp_index)` invoke-IC): it returns `Object[].class` (ClassId 385 / `[Ljava/lang/Object;`) for a runtime `String[][]` receiver, without ever reaching `native_object_get_class`. A param-slot-read bug is **REFUTED**: with a big-enough template (`a.length >= size`, e.g. `list.size()==2` + `new String[2][]`) ArrayList.toArray takes the `System.arraycopy; return a;` branch and DOES return the correct `[[Ljava/lang/String;` — so local slot 1 (`a`) holds the right template; only the copyOf-branch `a.getClass()` is poisoned. **FURTHER NARROWING (later in same pass):** added an `eprintln` to the `LdcValue::ClassRef` arm (interpreter.rs ~8359, `ldc X.class`) — running `AV.java` (`ArrayList<String[]>.toArray(new String[0][])`) prints **NO `ldc class` at all** during the call. Real `java/util/Arrays.copyOf(Object[],int,Class)` bytecode does `ldc Object[].class` for its comparison, so **`Arrays.copyOf` real bytecode is NOT executing** — `ArrayList.toArray(T[])` is being served by a **native that allocates `Object[]` directly** (no getClass, no copyOf, no ldc), yet NONE of the toArray/copyOf/Array.newInstance natives' entry traces fire. **DECISIVE NEXT STEP (instrumentation already committed to the tree):** a trace was added to `NativeContext::new_ref_array` impl (`vm/src/vm/vm_exec.rs` ~1403) that, when `class_id==0` (i.e. allocating a bare `Object[]`) and `CRATONVM_DBG_TOARRAY=1`, prints `from frame=<class>.<method>`. **Build + run `AV.java` and read that one line — it names the exact Rust/Java frame allocating the `Object[]`.** That is the unidentified handler; route ITS too-small-template branch through `class_id_of_object(template)` / `array_component_class_id`. (Older lead, now lower-priority: instrument the *virtual `getClass`* IC populate at interpreter.rs ~15506 / execute ~15273 — print receiver `class_id`, `guard_class_id`, returned-mirror `class_id` for array receivers.) Likely fix: the receiver guard at ~15302 keys on `heap.class_id_of(receiver)`, which for arrays is the **component** id — so the array-kind getClass either folds to a constant at populate time or the IC entry built for a first `Object[]` receiver is reused; force getClass on `ObjectKind::Array` receivers to always re-dispatch through `native_object_get_class` (never cache as a constant/Intrinsic), or include array-ness in the IC guard.
