diag(h2): debugger-equivalent field write/retarget tracing for TestUpgrade, both clean

rr isn't installed and its hardware-perf-counter needs are unreliable on
this cloud VM class; gdb watchpoints need a byte-offset I'd have to
reverse-engineer and can't survive a moving GC relocating the object
mid-run anyway. Implemented the equivalent in Rust at the two places that
matter: does a final field ever get written twice, and is the
cross-loader field-index retargeting logic ever wrong.

Direct putfield tracing (unconditional, at the actual bytecode write, not
a construction-site guess) captured 30,761 writes to any Page/
RootReference field in a full run. field_index=0 (Page.map and
RootReference.root, each class's first field) was written more than once
for exactly zero objects - a definitive, exhaustive refutation of "a
final field gets overwritten" for the whole run, not just at known
construction sites.

Also traced retarget_instance_field_to_receiver, a pre-existing function
that recomputes a field's index when the cached resolution's declaring
class doesn't match the actual receiver - exactly the cross-loader
mismatch shape this investigation has chased, for field access. 53
retargeting events fired (confirming cross-loader RootReference.root
access genuinely happens), every single one recomputed the identical
index the cache already had. Zero index changes, zero misses.

Also added a types-crate field_watch module (address-based watch list)
as a first attempt before discovering putfield doesn't route through
gen_heap.rs::set_field for the hot bytecode path - kept for reference,
superseded by the direct putfield trace above.

Net result: every mechanism capable of making a final reference field
hold the wrong value has now been checked and found sound. This raises
real doubt about whether the compareAndSetRoot event caught in the prior
commit was ever a bug, rather than a legitimate transient artifact of
Upgrade.upgrade()'s own dual-store migration logic. See the doc's
"Same-session addendum #5" for the full writeup and a genuinely different
recommended next step: compare against real HotSpot instrumented the
same way, to determine whether this is a CratonVM bug at all.
