CratonVM: NOT RUN. No binary was built in the session that wrote this probe,
          so there is no CratonVM arm here and none should be inferred. The
          HotSpot arm below is the CONTROL — it says the instrument works, and
          it is the oracle every CratonVM row is diffed against.

What the control establishes, beyond reproducing every vector W4-3 and W7-29
recorded by hand:

  * Section C's `match=` column is `true` on all 24 digest rows AND
    `C.md.fallbackEqualsSha256 = n/a`. That `n/a` is the anti-vacuity row.
    `NO-SUCH-DIGEST` is refused here, so nothing was produced, so the
    comparison against real SHA-256 must decline to answer. If it ever reads
    `true`, the digest engine discarded the algorithm name and served SHA-256
    under it; if it ever reads `false` with two real hex strings, something
    served NO-SUCH-DIGEST with bytes of its own. Both are defects; `n/a` is
    the only correct answer for a VM that refuses the name.
    `C.mac.224equals256 = false` is the same guard on the Mac engine, and it
    reads `false` rather than `n/a` precisely because both sides produced real
    bytes — which is what makes `false` meaningful there.

  * `C.md[MD2]`, `C.md[SHAKE128-256]`, `C.md[SHAKE256-512]` all match, so the
    three algorithms this record set out to close have an independent oracle
    and are not being taken on a prior record's word.

  * `C.md[SHAKE128]` and `C.md[SHAKE256]` return bytes IDENTICAL to the
    hyphenated primaries while `A.MessageDigest.n = 15` does not list them.
    That is the alias half: `getInstance` resolving a name the advertised set
    omits is CORRECT here, and a VM that refuses SHAKE128 after implementing
    SHAKE128-256 has a different defect.

  * Section B is 22 rows and every one is `THREW`. That calibrates the
    reverse direction: on a correct VM, no unadvertised name is served.

  * HotSpot has advertise-but-refuse rows OF ITS OWN, and they are worth
    knowing before reading a CratonVM diff as a defect: the 14 `HMACPBESHA*`
    and `PBEWITHHMACSHA*` `Mac` names are advertised by SunJCE and
    `Mac.getInstance` answers them with `java.security.ProviderException:
    Could not construct MacSpi instance`. So "advertised and not serviceable"
    is not by itself proof of a CratonVM bug — the oracle has to be consulted
    per name, which is the whole reason this file exists.

  * `A.KeyGenerator[AES] keylen=32` — JDK 25's SunJCE AES default is 256-bit,
    not the 128 an older reading assumed. `keylen` is printed on every
    KeyGenerator row because an engine that stores the algorithm string and
    never reads it again answers every name with one hard-coded size, and the
    length is the only observation that can see it.
