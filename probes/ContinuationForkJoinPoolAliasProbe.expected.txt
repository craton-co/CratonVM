What CratonVM must print, and the one line that legitimately differs
--------------------------------------------------------------------

W7-75-continuation-forkjoinpool-alias.md is the record. Lines that must
MATCH HotSpot exactly:

  CONT scope-via-toString-holds-name=true       <- the swapped scope/target pair
  CONT scope-via-toString-holds-lambda=false
  CONT body-ran-count=1
  CONT second-run=THREW:java.lang.IllegalStateException   <- THE GUARD
  CONT body-ran-count-after-second=1
  FJP explicit-pool ... agree=true

Before the fix, on a real receiver, the four CONT lines read

  CONT scope-via-toString-holds-name=false
  CONT scope-via-toString-holds-lambda=true
  CONT second-run=NO-THROW(ran=2)
  CONT body-ran-count-after-second=2

because `<init>` wrote `scope` into slot 0 (`target` on the real class) and
`target` into slot 1 (`scope`), and `run()` read slot 2 as an int `state` when
slot 2 is `parent`, a Continuation reference — so the completed-continuation
guard could not fire. "The body ran" is not a test of that guard; "the second
run was refused, and the body did NOT run again" is.

`FJP explicit-pool` before the fix reads

  FJP explicit-pool getParallelism=1 toString-parallelism=4 agree=false

— the native read slot 0 (`termination`, a null CountDownLatch), missed the
`Value::Int` arm and answered its fallback 1, while the pool's own JDK
`toString()` correctly reported 4.

The line that does NOT match, deliberately and not a defect of this lane:

  FJP common-pool getParallelism=1 toString-parallelism=1 agree=true
  FJP common-pool getCommonPoolParallelism=1

CratonVM's common-pool proxy is clamped to parallelism 1 for determinism
(`NEW15_COMMON_POOL_PARALLELISM`, T16.7 — `forkjoin_pool_basic` asserts that
minimum, and the real carrier pool lives in
`SharedVm.threads.virtual_scheduler`, not this proxy). HotSpot's 31 is
`availableProcessors() - 1` on this host and varies per machine, so the
comparable assertion for that row is `agree=true` — accessor and the JDK's own
`toString()` reporting the SAME number — not the absolute value. Before the fix
that row read `agree=false` too: the 1 went into `termination` and the real
`parallelism` field stayed 0.

`toString-parallelism=THREW:...` on the common-pool row is a possible third
answer on CratonVM and is not this lane's defect: the proxy is an allocated
`ForkJoinPool` whose `queues`/`ctl`/`runState` no constructor ever populated, so
real `toString()` bytecode may not survive it. The probe prints that instead of
dying so the explicit-pool row — the one that is the finding — still lands.
