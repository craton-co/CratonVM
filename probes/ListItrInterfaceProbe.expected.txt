What the control establishes, beyond the 16 PASSes:

  * `selfTestNoCheckcast` — the calibration for lie #1. Every other cast row
    launders its reference through `opaque(Object)` so javac MUST emit a
    checkcast; this row does the same cast on a reference javac already knows
    the type of, where no checkcast is emitted. It is the row that says the
    difference between the two is deliberate.

  * `selfTestRed`, `selfTestRedIterator`, `selfTestRedInstanceof` — the
    calibration for the failure direction, and the reason this probe is
    evidence rather than decoration. Every `ll.*` / `al.*` row reports PASS
    when a cast SUCCEEDS, so a helper that swallowed the ClassCastException
    would turn the whole file green while measuring nothing. These three are
    the only rows whose expected answer is the exception (and `false`), taken
    against a bare `java.lang.Object`. If they ever pass vacuously, no other
    row in the file means anything however green.

  * `al.*` is the CONTROL FAMILY, not filler. CratonVM already carries a
    `jdk_interfaces` arm for `java/util/ArrayList$ListItr`, so an `al.*` row
    going red on a CratonVM arm is a broken instrument and the `ll.*` rows say
    nothing that run.

Two INFO rows on this host are worth reading before comparing arms:

  * `ll.getClass` is `java.util.LinkedList$ListItr` here and is expected to be
    `cratonvm.internal.LinkedListSnapshotListItr` on CratonVM in BOTH modes.
    That divergence is deliberate and is NOT scored: the carrier was
    deliberately not named `java.util.LinkedList$ListItr`, because that name
    resolves to the real 5-field class whose layout mangles the carrier's Int
    cursor into the real `next:Node` slot — `next()` then never advances and
    `AbstractList.equals` compares element 0 forever.

  * `ll.iterator.getClass` is ALSO `java.util.LinkedList$ListItr` here, because
    JDK 25's `LinkedList.iterator()` delegates to `listIterator(0)`. CratonVM
    serves the two from different carriers (`java/util/LinkedList$Itr` for
    `iterator()`), which is why the probe prints both: a fix applied to one
    carrier and not the other is a shape this file can see.

=== how to run both arms ===

    JDK=/path/to/jdk-25
    javac -d /tmp/probeout probes/ListItrInterfaceProbe.java
    for M in --real-jdk --jdk-only; do
      target/release/cratonvm $M --java-home "$JDK" -cp /tmp/probeout ListItrInterfaceProbe
    done

Pass `--java-home`. A hand-run that omits it measures the host's default JDK
instead of the JDK 25 image, which has already inverted a per-mode verdict once
in this campaign.
