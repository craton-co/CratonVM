What the control establishes, beyond the PASSes:

  * `selfTestNoPark parked=false` — the anti-vacuity guard FIRES. Every other
    row's verdict rests on `parked=true`, and a `parked` check nobody has seen
    say `false` is an uncalibrated instrument. This is the row that calibrates
    it. If it ever reports `parked=true`, no other row in the file means
    anything however green.

  * The failure path is not hypothetical either. Measured on the same host:

        java -Dprobe.skipClose=socketRead -cp <out> \
             AsyncCloseProbe selfTestNoPark socketRead channelRead

        PROBE selfTestNoPark parked=false ms=0 outcome=returned:42 want=must-not-park PASS
        PROBE socketRead     parked=true ms=4000 outcome=TIMEOUT want=SocketException FAIL
        PROBE channelRead    parked=true ms=1 outcome=AsynchronousCloseException want=AsynchronousCloseException PASS
        SUMMARY pass=2 fail=1 inconclusive=0

    Wall clock 5.1 s, exit 1. A missing wakeup REDs after exactly `probe.wakeMs`
    and the process leaves; it does not hang. That is the property that makes
    this usable in a suite, and it has been executed rather than asserted.

  * `tlsSelfTestNoPark parked=false` — the TLS-specific calibration. The plain
    `selfTestNoPark` proves the park guard can say `false` on a plain socket;
    it says nothing about TLS, where a read can fail to park for a reason that
    exists only in the record layer (a whole record already decrypted and
    sitting in the engine's buffer). Without this row, `parked=true` on
    `tlsRead` would rest on a check nobody has seen refuse a TLS read.

  * `tlsReadIntegrity returned:204800` — the anti-vacuity row for the RECORD
    LAYER, and the one that makes this file able to catch the failure W7-53
    named: asserting a TLS read returned SOMETHING is not a test that it
    returned a complete record. This row reads a 200 KiB multi-record payload
    back byte-for-byte and reports `CORRUPT@<offset>` at the first wrong byte.
    A close-aware loop bolted on at the wrong level — one that wakes a reader
    mid-record and hands back a partial buffer — corrupts here while `tlsRead`
    stays green.

  * The TLS failure path was executed too, on the same host:

        java -Dprobe.skipClose=tlsRead -cp <out>              AsyncCloseProbe tlsSelfTestNoPark tlsReadIntegrity tlsRead

        PROBE tlsSelfTestNoPark parked=false ms=0 outcome=returned:42 want=must-not-park PASS
        PROBE tlsReadIntegrity  parked=false ms=0 outcome=returned:204800 want=returned:204800 PASS
        PROBE tlsRead           parked=true ms=4000 outcome=TIMEOUT want=SocketException|SSLException|IOException FAIL
        SUMMARY pass=2 fail=1 inconclusive=0

    Exit 1, process leaves. The TLS rows RED rather than hang, same as the
    others.

  * `tlsWrite CLOSE_BLOCKED` is a MEASUREMENT OF THE ORACLE, not a workaround.
    `SSLSocket.close()` issued from another thread while a writer is parked
    inside `getOutputStream().write()` does not return on HotSpot 25.0.3: JSSE
    serialises `duplexCloseOutput()` behind the write it would have to
    interrupt. So there is no reference behaviour in which a close wakes a
    parked TLS write, and that is the measured reason W7-61 leaves
    `servlet.rs::s2_tls_write` and `t27_tls.rs::rustls_stream_write` alone.
    The row still fails on exactly one reading — `TIMEOUT`, meaning the close
    DID return and the writer is still parked, which is the genuine defect a
    half-repair would produce.

    This is also what forced the harness change in the same commit: `close()`
    and the row cleanup now each run on a bounded daemon thread. Run inline,
    they made this probe the hang it measures. The 13 pre-existing rows are
    unaffected — their closers return immediately — and their timings below are
    unchanged.

One `want` was corrected against the measurement rather than the other way
round: `channelWrite` answers `ClosedChannelException` on HotSpot 25.0.3,
because the parked write returns its partial count and the NEXT iteration of
the row's write loop finds the channel already closed. All three of
AsynchronousCloseException / ClosedChannelException / a partial count are
wakeups; only TIMEOUT is the defect this family is about.
