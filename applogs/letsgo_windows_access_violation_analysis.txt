Letsgo-main under rustjvm java.exe — Windows exit code -1073741819 (0xC0000005 STATUS_ACCESS_VIOLATION)
================================================================================

Reproduction (release build, 2026-05-13)
----------------------------------------
  $env:RUST_BACKTRACE='1'
  $env:RUSTJVM_DISABLE_JIT='1'   # optional; see below
  & C:\craton\CratonVM\target\release\java.exe --jar `
    C:\Users\Victor\YandexDisk\PRO\JAVA\letsgo\letsgo-main\target\letsgo-main-0.0.1-SNAPSHOT.jar

Evidence (interpreter path, JIT off)
-----------------------------------
With RUSTJVM_DISABLE_JIT=1 the VM reached Spring Boot 2.7 banner, AutoConfiguration.imports,
and ConfigurationClassEnhancer bypass, then logged:

  2026-05-13T21:35:20.831937Z  WARN rustjvm_vm::vm::vm_exec: Missing native method in real-JDK mode method=org/apache/tomcat/jni/Library.size(I)I

Immediately followed by process exit -1073741819 (no Java stack trace).

Root cause (first fault)
------------------------
Tomcat 9.0.x `org.apache.tomcat.jni.Library.initialize(String)` (embedded core) calls private
native methods beyond `version(int)`:

  - private static native boolean has(int);
  - private static native int size(int);

(see Tomcat 9.0.x Library.java — APR_SIZEOF_VOIDP = size(1); … APR_MMAP_LIMIT = size(7);)

RustJVM already stubbed `version`, `versionString`, `aprVersionString`, `initialize`, `terminate`
in `native-builtins/src/lib.rs::register_tomcat_jni_natives`, but not `size` / `has` / `globalPool`.

When the builtin registry missed `size`, dispatch fell through to
`resolve_jni_native_in_libraries`, which can bind `Java_org_apache_tomcat_jni_Library_size` from a
host `tcnative-*.dll` on `java.library.path`. That JNI entry is not ABI-compatible with RustJVM’s
libffi-based `dispatch_jni_native` on this Windows build, producing STATUS_ACCESS_VIOLATION.

Fix applied in VM / builtins
----------------------------
1) `register_tomcat_jni_natives`: register `has(I)Z`, `size(I)I`, `globalPool()J` with values that
   satisfy `Library.initialize` (APR_HAS_THREADS via `has`, size constants for fields 1..7).

2) `vm_exec.rs`: skip `resolve_jni_native_in_libraries` for class names under `org/apache/tomcat/jni/`
   so uncovered Tomcat JNI methods surface `UnsatisfiedLinkError` instead of calling mismatched
   host DLL symbols.

Remaining issue (second fault, same exit code)
----------------------------------------------
After the above, `RUSTJVM_DISABLE_JIT=1` runs still terminate with -1073741819 immediately after
`[CCE-DBG] ConfigurationClassEnhancer.enhance -> bypass` with no further stderr — no new
"Missing native" line in that window. This points to a separate crash (interpreter / non-Tomcat-JNI
path) still under investigation.
