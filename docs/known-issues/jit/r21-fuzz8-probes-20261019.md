Found by: JIT round 21 wave 22, lane fuzz8. The probes were written without compiling or running anything (no
javac, no HotSpot, no CratonVM). Each probe header gives its expected HotSpot 25 output, worked out by reading the
JDK and HotSpot sources. Expect one round of javac fixes and expectation fixes after the orchestrator's first run.
Probes 2, 3 and 5 build classes with `java.lang.classfile`.

The conventions are those of `r21-fuzz5-probes-20261019.md`:

- Default package, ASCII only.
- Deterministic stdout: no timings, identity hashes, addresses, or output that depends on thread order.
- Hidden-class names are printed with their `/0x<hex>` suffix replaced by `/0xH`.
- Messages of exceptions that name a hidden class are not printed.
- Every hot loop runs at least 20k times.

**HotSpot expectation for every probe: every line identical on every arm, and equal to the lines in the probe's
header.** The one exception is a control arm, which may differ.

## What a mismatch means

1. **`R21Fz8HiddenDeoptStorm1`**
   - `match=false`, or counts that move between `h1`, `plain` and `other` after the `plain` line, mean that a
     deopted frame resumed in the ordinary class. That is w21 item 1 again, or one of the doors wave 20 did not
     convert.
   - A mismatch in `storm1` only (before any same-named class exists) points at the deopt resume, not at name
     binding.
2. **`R21Fz8HiddenNestmate1`**
   - A `solo` line that answers a value instead of `IllegalAccessError` means the nestmate check was skipped. If
     only `hot` or `hotIAE` differs, the skip is in compiled code.
   - A naming difference points at the hidden name, the simple-name bridge, or MethodType text.
   - If `counter` differs, a host private ran when it should not have, or ran twice.
3. **`R21Fz8ResolveRetry1`**
   - A `cause=null` on any line except the first means the rethrow lost its cause (item 6c).
   - A `user again` site that succeeds means the error was not sticky.
   - `asked` greater than 0 on `null-cold` means `instanceof` or `checkcast` of null resolved the class.
   - `record 2` still failing means the descriptor failure was recorded (item 6b).
4. **`R21Fz8FinPrologue1`**
   - A non-zero `finalized` count for mode 1 or 4 means a finalizer was registered for an object whose
     constructor never reached `Object.<init>`.
   - A short count for mode 0, 2 or 3 means the `<init>`-return scan refused a JEP 513 prologue and withdrew the
     registration.
   - Before filing a short count, rerun: the settle loop may have timed out.
   - **Wave 25 battery result and fix (wave 26, lane finprologue; pending orchestrator build).** Every mode
     (jdk, compat, nojit) printed `finalized 8000,0,4000,4000,0 total=16000` for both phases; HotSpot prints
     `4000,0,4000,4000,0 total=12000`. The extra 4000 in slot 0 are the mode-1 objects: `Fin`'s prologue throws
     before `m = mode` runs, so `finalize()` counts them under `m == 0`. Mode 4 (Base's prologue throws) was already
     right. Cause: the unwinder's "throw precedes initialization" proof (`exception_dispatch.rs` `ctor_prefix_scan`)
     refused any constructor with an exception handler that starts before the first initializing `invokespecial`.
     `Fin(String, int)` has the prologue `try { Integer.parseInt(s) } catch (NumberFormatException e) { .. }`, so the
     proof refused the whole body. The registration made at `new` was never withdrawn, and the same refusal let the
     compile bar (`finalizer_bars_compiling`) compile that constructor. Fix, `CRATONVM_FINALIZER_CTOR_PROLOGUE_HANDLERS`
     (default ON, `=0` restores the old rule): a handler before the first initializing call is accepted when its row
     covers only pcs before that call (`end_pc <= first`; `ctor_handler_rows_allow`). Such a handler is reached only
     by a throw before the call, so control that reaches it never passed the call. A row that covers the call, or
     sends control from past it back below it, still refuses. The wave-21 `<init>`-return scan is unchanged. Expected
     after the build: both lines match HotSpot in all three modes. `R21Fz10FinCtorThrow1` has no handler before an
     initializing call, so none of its rows should change. Unit test:
     `the_unwinder_proof_accepts_a_jep_513_prologue_handler`.
5. **`R21Fz8Nesting1`**
   - A cold-line difference means a reflection answer is wrong.
   - A `hot ... differs` line means a memo or compiled intrinsic changed the answer after the first call.
   - On `--compatible`, compare the HLoc, HAnon and HMem rows first (the w21 item 7 bridges).
   - **Wave-25 result, and fix (wave 26, lane nesting; pending orchestrator build).** This section also covers
     `R21Fz6InnerRows1` (no fuzz6 page exists; its header is cited by `r21-review-w18-findings-20261019.md`) and
     `R21Fz8ReviewEmGone1` (`r21-review-w22-findings-20261019.md`). On the wave-25 binary, which includes the dev
     merge, all three probes differed from HotSpot 25 in all three modes (jdk, compat, nojit). The diffs were the
     same in every mode. Two HotSpot rules were missing. Neither came from the dev merge: dev's boxing of
     `EnclosingMethodInfo` (`72be304cbb`) and `hotspot_stored_inner_classes` (flags only) changed no answer. The
     EnclosingMethod-alone reading comes from this branch's waves 18-19 (`9a8da8f7dc`), and its probe headers
     predicted that reading too. The local-class check was never modelled.
     1. **EnclosingMethod without InnerClasses is not stored.** Rows `R21Fz6InnerRows1` X$4, `R21Fz8Nesting1` Y$1 and
        `R21Fz8ReviewEmGone1` $E. HotSpot printed `anon=false ... simple="X$4" canonical="r21fz6.X$4" enclosing=null`
        (and the same shape for Y$1 and $E, with no NCDFE for $E's missing class). CratonVM printed
        `anon=true simple="" canonical=null enclosing=X`, and for $E an NCDFE in every column. HotSpot keeps the
        EnclosingMethod indices as the two-slot tail of `InstanceKlass::_inner_classes`. The call site of
        `parse_classfile_inner_classes_attribute` passes `parsed_innerclasses_attribute` as the parameter named
        `parsed_enclosingmethod_attribute`. So the tail exists only when an InnerClasses attribute was parsed, even
        an empty one or one ignored as circular. With EnclosingMethod alone the array is empty, and
        `enclosing_method_class_index()` is 0. As a result `getEnclosingMethod0` is null, the class is top level for
        every JDK 25 question, and the EnclosingMethod class is never resolved. Fix,
        `CRATONVM_ENCLOSING_METHOD_NEEDS_INNER_CLASSES` (default ON, `=0` keeps the attribute): every class-file
        reader (define, synthetic upgrade, redefinition scratch class) drops `EnclosingMethod` when the file has no
        `InnerClasses` attribute (`NestingAttributes::hotspot_stored`, `classloading/src/class_manager.rs`). Because
        it happens at define time, the JDK bodies (`--jdk-only`) and the `--compatible` bridges both see the class as
        top level. In X$4's `in(X)=9` the `Lookup.in` walk follows too. javac never writes this shape: every local
        and anonymous class has its own row. Unit test: `enclosing_method_needs_an_inner_classes_attribute`.
     2. **A local or anonymous class must be listed by its EnclosingMethod class.** Rows `R21Fz8Nesting1` HLoc and
        HAnon (hidden, self row without an outer class, EM(host)) and `R21Fz8ReviewEmGone1` $C (row `($C, -, C)`,
        EM(host); the host lists nothing). HotSpot printed `declaring=ICCE`, CratonVM printed `declaring=null`.
        `JVM_GetDeclaringClass` -> `compute_enclosing_class`: when the first self row (`find_inner_classes_attr`) has
        no outer class, the EnclosingMethod class is resolved. Then `check_for_inner_class(outer, this, false)` runs
        before the null answer for a non-member. That check needs a row in the outer class whose inner entry is this
        class and whose outer entry is 0. A hidden class can never pass it, because its row is renamed to the hidden
        name. The controls show the passing side: `R21Fz9EmMissing1`'s H$C and D$X, whose hosts list them, answer
        null on HotSpot, and so does every javac class. Fix, `CRATONVM_CLASS_LOCAL_INNER_CLASSES_CHECK` (default ON,
        `=0` answers null): `lang_class::local_class_inner_classes_disagreement`, asked by `getDeclaringClass0` after
        `declaring_class_id_checked` answered no declaring class. It applies only to classes backed by real bytes
        (`ClassOrigin`; the outer class too unless the inner class is hidden). `getDeclaringClass0` is the Bridge
        that both modes reach from the JDK body of `getDeclaringClass`. Unit test:
        `r21w26_local_class_must_be_listed_by_its_enclosing_class`.

     Expected after the build, in all three modes: `R21Fz6InnerRows1` matches HotSpot (X$4 row). `R21Fz8Nesting1`
     matches (HLoc, HAnon and Y$1 rows; hot lines unchanged). `R21Fz8ReviewEmGone1` matches ($E and $C rows).
     Unresolved, by design: the local-class check compares names inside the outer class's table. A cross-loader
     identity mismatch (`klass_at(ioff) != inner`) is not modelled for the local arm.
6. **`R21Fz8OsrCasMega1`**
   - `casOk` or `x` differs: the CAS result, or the witness value, is wrong across the OSR entry or the deopt.
   - `scoreMatch=false`: the megamorphic default stub, or the splice of `Sub.score` / `S3.score` / `S5.twice`.
   - `chaMatch=false`: a CHA dependency survived the arrival of `ChaLate`.
