## Probe 2 (`R21Fz10VhCovariant1`): w25 measurement and fix (wave 26, lane vhase; pending orchestrator build)

The w25 binary differs from HotSpot 25.0.3 (`-XX:-OmitStackTraceInFastThrow` on both VMs) on 6 rows, and the
diff is the same in `--jdk-only`, `--compatible` and `--nojit`. All fixes are in the interpreter-side natives,
which compiled code also calls.

1. **`CS/covCS {setVolatile,getAndSet,CAS} Integer`** (an `Integer` through a `CharSequence[]` handle into a
   `String[]`).
   - HotSpot gives `ArrayStoreException()`; we gave `ClassCastException: Cannot cast java.lang.Integer to
     java.lang.CharSequence`.
   - JDK 25 `runtimeTypeCheck` uses `componentType.cast` only when `handle.arrayType == oarray.getClass()`.
     Otherwise it calls `reflectiveTypeCheck`, which throws `new ArrayStoreException()`.
   - Fix, `CRATONVM_VH_ARRAY_COVARIANT_SLOW_PATH` (default ON): in `native-builtins/src/lang_invoke.rs`,
     `vh_array_store_refusal_route` handles a non-`set` mode whose value the handle's component refuses. When
     the array's header component is known, non-zero and differs from the handle `componentType`'s class id
     (`vh_array_covariant_slow_path`), it throws the message-less ASE. The real component is a subtype of the
     handle's, so the value is refused there too.
   - Not covered: a component that is an array, or a primitive, keeps the fast-path CCE. One such case is an
     `Object[][]` handle on a `String[][]` with a non-array value.
2. **`HV/covH set String`** (plain `set` through `arrayElementVarHandle(H[].class)`, `H` hidden).
   - HotSpot gives `ClassCastException: Cannot cast java.lang.String to H`; we gave `ArrayStoreException:
     java.lang.String`.
   - The handle's `componentType` IS the array's, so this is not a covariance problem. The value's cast
     (`vh_array_component_cast_refusal`) asks `reference_arg_admitted` by NAME. A hidden class does not
     resolve by name, so it answered `None` (admit), and the `aastore` check refused instead.
   - Fix, `CRATONVM_VH_ARRAY_HIDDEN_COMPONENT_CAST` (default ON): for a hidden component, the verdict comes from
     the mirror's class id (`vh_hidden_component_admits`: the same class, or `is_subclass`).
   - The CCE text goes through `reference_cast_failure`'s `class_text`, which keeps the `/0x<hex>` tail.
   - The same verdict also serves the CAS expected-value cast.
3. **`arraycopy String[] -> hidden[]` and `Object[] -> hidden[]`.**
   - HotSpot gives `type mismatch: can not copy java.lang.String[] into H[]` and the element sentence ending
     `destination array, H`, both with the `/0x` tail.
   - We gave the element sentence for `String[]`: the name-based subtype rule cannot resolve `H` and answers
     "unknown", which picks the element sentence. We also dotted `$Hc.#H` in both rows.
   - Fix, `CRATONVM_ARRAYCOPY_HIDDEN_COMPONENT_TEXT` (default ON): in `native-builtins/src/lang_system.rs`,
     `element_type_mismatch_message` handles a hidden source or destination component (by the class's hidden
     flag). It decides the sentence on class ids and `class_assignable_to_name`, and renders each component
     with `dotted_binary_name_of_class`. The sentences come from the new
     `arraycopy_message::{element,reference}_type_mismatch_rendered` in `types/src/error.rs`.
   - `System.arraycopy`, `Arrays.copyOf(U[],int,Class)` and the `lib.rs` copy share this function.
   - Not changed: `ArrayList.toArray` (`native-api` `array_store.rs`, `StoreRoute::Arraycopy`) still dots a
     hidden destination.

Unit tests:
- `the_covariant_slow_path_needs_a_known_different_component` (`lang_invoke.rs`);
- `arraycopy_rendered_sentences_keep_a_hidden_tail` (`types`).

## What a mismatch means

1. **`R21Fz10NameChurn1`**
   - `bad` > 0 prints the first wrong answer. If the wrong answer is another generation's name (`fz10n.G<g-1>`),
     or a hidden name with another suffix, a memo answered for a dead mirror or a reused id.
   - A failure only on the `[]` / `[][]` or primitive rows is the id-less mirror path (the wave 24
     `class_names_idless` holds).
   - `distinct=false` means two live hidden classes got the same name.
2. **`R21Fz10VhCovariant1`**
   - A store row that prints `stored` where HotSpot throws: the store check used the handle's static component
     type, not the array's real one. A throw where HotSpot stores is the reverse.
   - `ASE: <class>` where HotSpot prints `ASE()` (or the reverse): the door took the aastore path for a
     non-`set` mode, or `runtimeTypeCheck` for `set`.
   - A `dest=` difference on an arraycopy row means the elements copied before the bad one were not kept.
   - A `hot <row>` line means the compiled store disagrees with the cold one.
3. **`R21Fz10HiddenCastMsg1`**
   - `/0x` where HotSpot keeps `+`, or `.` where HotSpot keeps `/`, means the shape rule fired on an ordinary
     class, or the wrong `+` was converted (`$Q+0x7`).
   - A `#X` label on the wrong class's text, or an unmasked `0x` suffix, means the text named another hidden
     class or a stale one.
   - A difference only in the `(... is in unnamed module of loader ...)` tail is the module/loader renderer.

   **Probe 3 rows after wave 26 (lane hexname; pending orchestrator build).** The w25 diffs are in
   `C:\craton\CVM-r21b\w25diffs\R21Fz10HiddenCastMsg1.{jdk,compat,nojit}.diff`. Two defects explain every
   differing line:

   - **(a) A hidden class's self-checkcast named the pool's `Hd`, not the resolved `Hd/0x..`.** This affects rows
     `A|B|C self String`, `self main` and `self other` in all modes, and `cross Plus self A` (compiled). The text
     came out short (`X cannot be cast to Y`) because the message funnel's target-by-id check refused a display
     that was not the class's own name. Now the interpreter's `checkcast` (`opcodes.rs`) and the JIT's
     `jit_checkcast_body` (`helpers.rs`) both name the target by the class the site resolved
     (`exceptions.rs` `cast_target_display` / `resolved_hidden_cast_target_name`). This applies only when that
     class's bottom class is hidden, its name is not the pool's, and both have the same array depth. The funnel
     then finds both operands by id.
   - **(b) An array of a hidden class lost the module/loader clause.** This affects rows `A|B|C cc String[]`
     (all modes) and `cross hiddenArr toSeg`. `klass_origin_by_id` refused every `[`-display, and the name
     path cannot find a hidden class by name, so the whole rebuild fell back. The interpreter printed the bare
     form; the JIT printed its own `class X cannot be cast to class Y`, with no clause. Now
     `klass_origin_by_id` walks the noted id down `array_info` to the bottom class. That class must spell the
     display's bottom name. The clause is then read from that class, as HotSpot reads `bottom_klass`.

   The `hot A|B|C|cross rows=... same=124 / 250 firstDiff=...` lines follow from the cold rows above and are
   expected to read `same=20000`. Expected after the build: every line of the probe equals HotSpot in
   `--jdk-only`, `--compatible` and `--nojit`. One assumption: the compiled path needs the site's resolved
   target (`typecheck_target_for_site`). If a compiled self cast still prints `$Hd` with no tail, that table had
   no entry for the hidden class's self site; the interpreted rows will match regardless.
   `CRATONVM_CAST_TEXT_BY_RESOLVED_CLASS=0` restores the w25 texts.
4. **`R21Fz10FinCtorThrow1`**
   - A non-zero count on slots 2, 3 or 8, or more than 10000 on slot 5, means a finalizer was registered at
     allocation, or was left registered after a throw before `Object.<init>`. That is never noise.
   - A short count on 0, 1, 7, 9, 10 or 12 means the registration was lost when the constructor threw after
     `Object.<init>`. Rerun first, because the settle loop may be the cause.
   - A `vsum` difference on 1 or 10 (HotSpot: 0) means finalize saw a field the base never stored.
5. **`R21Fz10FreshVolPub1`**
   - Any non-zero `bad` means a volatile store into a fresh object was reordered or elided past its publication.
   - A non-zero `self` means store-to-load forwarding is broken in the writer itself.
   - A non-zero `stuck` means a store never became visible. Rerun before filing, because it can be a starved
     reader on a loaded host.
6. **`R21Fz10NcdfeSites1`**
   - A different `gMulti` text means the array-name entry is rendered differently. The header's `GM` guess is
     the most likely header fix.
   - `bArr` / `bLit` / `bCast` / `bInst` failing after `Boom` is erroneous means the initialization error leaked
     into sites that never initialize.
   - `User2 cold bCall` as EIIE means `<clinit>` ran twice.
   - `newThrowable=false` means a recorded error was rethrown as the same object.
   - An `asked` count above the header's means the failure was not recorded per class entry.
   - A `hot` or `spin` count below 20000 means the compiled throw path differs from the interpreter.

   **Probe 6 after wave 26 (lane reserr; pending orchestrator build).** The w25 run differed from HotSpot
   25.0.3 in every mode (`--jdk-only`, `--compatible`, `--nojit`) on one line only: `User1 fresh boom newThrowable=true sameCause=false`
   (HotSpot `sameCause=true`). HotSpot keeps ONE `ExceptionInInitializerError` per erroneous class in its
   initialization-error table (JDK-8048190) and every "Could not initialize class" error carries that object;
   `raise_could_not_initialize_class_for` (`vm/src/runtime/exceptions.rs`) built a fresh one per throw. It now
   keeps the first one under a strong global handle (`RecordedClassInitError::saved_cause`) and hands it out
   afterwards (`CRATONVM_INIT_ERROR_SAVED_CAUSE`, default ON, `=0` restores the fresh cause). That function is
   the only raiser: the interpreter and compiled code both reach it through `ensure_class_initialized_shared`
   (`vm/src/vm/vm_util.rs`). Expected after the build: every line equals HotSpot in all three modes.
