## Probe 1 (`R21Fz9VhArrRef1`): set-mode check order (wave 26, lane vhase; pending orchestrator build)

- **Measured (w25 binary vs HotSpot 25.0.3 with `-XX:-OmitStackTraceInFastThrow`).** 15 rows differed, the same
  in `--jdk-only`, `--compatible` and `--nojit`: `cold V{S,N,C,OO,SS} {setVolatile,setRelease,setOpaque}
  <own array> wrong@-1`. HotSpot throws `ArrayIndexOutOfBoundsException msg=Index -1 out of bounds for length 4`;
  CratonVM threw the value's `ClassCastException` (`Cannot cast java.lang.Integer to java.lang.String`, ...).
- **JDK 25 order (`VarHandleReferences.Array`, local `src.zip`).** Plain `set` is
  `array[index] = handle.componentType.cast(value)`: Java evaluates the RHS before the `aastore` checks
  the bounds, so the cast comes first (CCE; HotSpot agrees). Every other mode is
  `UNSAFE.xxx(array, (long) Preconditions.checkIndex(..) << ashift + abase, [componentType.cast(expected),]
  runtimeTypeCheck(handle, array, value))`, so the order is index, then expected, then value. Before every
  mode, `arrayType.cast(oarray)` runs (the coordinate). The call sites are erased `(Object, int, Object..)`, so
  no `asType` cast runs ahead of the body.
- **Cause.** `CRATONVM_VH_ARRAY_CAST_BEFORE_INDEX` (round 15 wave 5, lane vh7) encodes "plain `set` casts the
  value before the index check". Its doc says CAS / CAE / getAndSet stay index-first. But it was applied in
  `varhandle_set_mode`, which serves all four set modes, so `setVolatile` / `setRelease` / `setOpaque` inherited
  cast-first as well. `R15Vh7ArrayCastOrder` never probed those three modes.
- **Fix (default ON, both modes): `CRATONVM_VH_ARRAY_CAST_BEFORE_INDEX_SET_ONLY`.** In
  `native-builtins/src/lang_invoke.rs`, `vh_array_mode_casts_before_index(mode)` limits the cast-first arm to
  `mode == "set"`. In the other set modes, `vh_array_refusal_after_index` runs the whole refusal (cast, then the
  array's own component) after the index check. `=0` restores cast-first on all four set modes. The CAS / CAE /
  getAndSet arms were already index-first, and their rows match. Compiled code reaches the same native, because
  the vh-const prefixes decline every refusal to the call. Unit test:
  `only_plain_set_casts_its_value_before_the_index_check`.
- **Expected.** All 15 rows print the AIOOBE, and the probe equals the reference on every arm. `R21VhConstRefRows`
  is unchanged: its `Object[]` handle's cast never refuses, and `sarr-setvolatile-both-bad` was already AIOOBE.
- **Known gap, not probed.** A non-`set` store whose value fails the handle's component, into a subclass
  array (for example a `String` through a `Number[]` handle into an `Integer[]`). The JDK's slow path
  (`arrayType != array.getClass()`) runs only `reflectiveTypeCheck`, so HotSpot gives `ArrayStoreException
  msg=null` for every non-`set` mode, while CratonVM's check 1 still gives the `Number` CCE. This needs the
  handle's `arrayType` to be compared with the array's class. It is unmeasured.

## Probe 6 (`R21Fz9HiddenUnload1`): compiled self cast in a hidden class (wave 26, lane hiddenunload; pending orchestrator build)

- **Measured (w25 binary).** `--nojit` matches HotSpot through `normal run=12` (and on). `--jdk-only` and
  `--compatible` print `keeper name=R21Fz9HU/0xH hidden=true` and then die in generation 0:
  `ClassCastException: class R21Fz9HU/0x0000000000000004 cannot be cast to class R21Fz9HU` at
  `runSum(R21Fz9HiddenUnload1.java:101)` (`/0x..02` in `--compatible`; the counter differs by mode). The
  `walkH` / `walk` / `dive` lines are missing only because they are printed after `ephemerals()`, which threw.
  They are not a separate unwinder defect.
- **Which class fails.** The failing class is the FIRST ephemeral class. The keepers are minted first
  (`/0x..00`, `/0x..01` in `--compatible`), and nothing has been unloaded yet: the first `System.gc()` runs at the
  end of generation 0. Class ids are never reused (`ClassStore`). So this is not unload, id reuse, or a stale
  cross-generation constant, and `CRATONVM_JIT_UNLOAD_WITHDRAWS_COPIED` is not involved. The frame is
  `runSum` because the hidden `run` frame is hidden from the trace, as HotSpot hides it.
- **Cause.** `run`'s `checkcast R21Fz9HU` runs compiled. `class_resolved_without_loading` defers a hidden self
  reference, so the site is interned holder-keyed (`intern_typecheck_unresolved_in`). On its first execution,
  `jit_typecheck_holder_site_target` resolves it through the holder. `resolve_class_loader_aware_unrecorded`
  applies the self rule and answers the hidden class itself, which is correct. Every compiled type check then
  validates a site id with `cm.get_class(id).name == class_name` (three copies: the holder-site record, the
  array branch, and the recorded-site branch of `jit_typecheck_resolve`). A hidden class is stored as
  `R21Fz9HU/0x..` while its pool spells `R21Fz9HU`, so the check failed. The id was neither recorded nor
  trusted, and the call fell through to the by-name tail. There `find_unique_class_by_name("R21Fz9HU")` found
  nothing and `load_class_concurrent` LOADED the class path's ordinary `R21Fz9HU`, three generations before the
  probe touches it. The hidden receiver was then refused against that class. The interpreter's `checkcast`
  compares ids after the self rule and passes. The message's bare target `R21Fz9HU` is the site's spelling
  (`jit_checkcast_body` renders `class_name`), not a resolved class.
- **Fix** (`vm/src/jit/helpers.rs`). There is now one predicate, `typecheck_site_names_class`: the stored name
  matches, or the id is a HIDDEN class and the site's name is its own class-file name
  (`ClassManager::is_hidden_self_name`, the wave-21 self-name rule). All three validations use it. The holder
  site is then recorded with the hidden class's id, and later executions (and recompiles, which intern the same
  `(holder, cp index)` pointer) answer by identity. A hidden class is in no loader's namespace, so only the self
  rule can hand a site such an id.
- **Switch.** `CRATONVM_JIT_TYPECHECK_HIDDEN_SELF_SITE` (correctness, default ON; `=0` restores the
  stored-name-only check). It is read only after a stored-name miss on a hidden class whose class-file name is
  the site's name, so in practice once per (site, receiver class, class-definition epoch) before the answer
  memos take over. It is not cached, because the vm crate's static ratchet allows no new static.
- **Tests.** `vm/src/jit/helpers.rs` module `r21w26_hiddenunload_typecheck_site_tests`. It covers the decision
  with the switch on and off, checks that the hidden rule and the switch are never asked on a stored-name match,
  and pins the source so that no stored-name-only validation is left in the holder-site and resolve bodies.
- **Expected after the build.** `--jdk-only` and `--compatible` match HotSpot line for line: the `walkH`, `walk`
  and `dive` lines, `gen 0`..`gen 5` all `true`/`same`/`2000/2000`, `normal run=12` before `gen 3`, and
  `final k0=true k1=true`. Run `CRATONVM_JIT_TYPECHECK_HIDDEN_SELF_SITE=0` as a control: it is expected to show
  the CCE again. If a `walkH`/`walk`/`dive` row still differs once the cast passes, that is a separate unwinder
  finding: those rows were never reached on the w25 binary.
- **Not changed.** The CCE text for a hidden target is lane hexname's (`cast_target_display`, wave 26).
  `class_resolved_without_loading` still defers the hidden self reference at compile time (wave 14), so the
  first compiled execution of each such site takes the holder path once.

## What a mismatch means

1. **`R21Fz9VhArrRef1`**
   - A `cold` row that stores where HotSpot throws, or the reverse, means the door's store check is wrong for that
     component type.
   - A different exception for a `both-bad` row means the check order is wrong (coordinate, then index, then
     expected, then value).
   - A `warm differs` or `hot differs` line on an arm that matches cold means the compiled store disagrees with the
     interpreter.
   - The `set` row's ArrayStoreException message (null, or the value's class name) is HotSpot's to decide. If the
     header guessed wrong, fix the header.
2. **`R21Fz9VhCaeCast1`**
   - If `field=` differs on a CCE row, the exchange was skipped (cast before the exchange) or done twice.
   - If `objInt short/char` differs, the asType widening is wrong.
   - A CCE on a `pattern` row means a cast was inserted where there is none.
3. **`R21Fz9FreshVolatile1`**
   - Any non-zero `bad` means a volatile store into a fresh object was reordered or elided past its publication.
   - A non-zero `stuck` means the store never became visible.
   - A non-zero `self` means store-to-load forwarding is broken in the writer itself.
   - Rerun before filing: a `stuck` can be a starved reader on a loaded host.
4. **`R21Fz9EmMissing1`**
   - A name answer instead of NCDFE means the compatible bridge skipped the EnclosingMethod resolution (w22
     item 1).
   - `cause` differs only after the first ask: the sticky error lost its cause.
   - Flaky asked fewer than 4 times, or still throwing after ask 3, means a non-LinkageError was recorded.
   - Ask counts above 1 for Gone, Nc or Wrong per asking class mean the error was not recorded.
   - **Wave-25 result, and fix (wave 26, lane nesting; pending orchestrator build).** This section also covers
     `R21Fz9ReviewEmUser1` (`r21-review-w23-findings-20261019.md`). Both probes differed from HotSpot 25 in all
     three modes, with the same diff in each mode.
     - `R21Fz9EmMissing1`, rows `cold C$E`, `array C$E[]`, `again C$E` and `asks` (`Gone=2` on HotSpot, 3 on
       CratonVM). C$E has EnclosingMethod(r21fz9e.Gone) and no InnerClasses attribute. HotSpot answers it as a top
       level class, never resolves Gone and so never asks the loader for it. CratonVM threw NCDFE from every query.
       The cause is the HotSpot parser rule in `r21-fuzz8-probes-20261019.md` item 5, point 1: EnclosingMethod is
       stored only beside an InnerClasses attribute. Fix, `CRATONVM_ENCLOSING_METHOD_NEEDS_INNER_CLASSES`. This
       also corrects the probe header's own expectation ("every column NCDFE", "Gone=3").
     - `R21Fz9ReviewEmUser1` `$H simple`. The hidden $H has EM(Missing) and no InnerClasses. HotSpot answered
       `"R21Fz9ReviewEmUser1$H/0x*"`, CratonVM threw NCDFE. Same rule, same fix.
     - `R21Fz9ReviewEmUser1` `$L after simple` / `canonical`. Once the loader can find Fz9EmGone, HotSpot still
       throws the recorded NCDFE (JVMS 5.4.3; the entry's resolution error is sticky). CratonVM answered `"L"` /
       null. `lang_reflect::loader_scoped_enclosing_lookup_checked` (the `getEnclosingMethod0` and
       `getEnclosingClass` lookup) first asks the user loader's exact namespace (`class_id_defined_by_loader_exact`).
       That probe found the class defined later and returned before the recorded failure was read. Since the FFM
       merge, both modes run the JDK body of `getSimpleName`, which reaches this native, so the diff was the same in
       every mode. Fix, `CRATONVM_ENCLOSING_LOOKUP_STICKY_FIRST` (default ON, `=0` restores the old order): the
       recorded failure is asked before the exact probe, but only where the error is propagated
       (`outer_resolution_errors_apply`, via `lang_class::recorded_outer_resolution_failure_of`).
     - `R21Fz9ReviewEmUser1` `$B simple` / `canonical` / `again`. Fz9EmBad's superclass is missing. HotSpot throws
       `NoClassDefFoundError: Fz9EmGoneSuper` caused by the loader's `ClassNotFoundException: Fz9EmGoneSuper`
       (`resolve_super_or_fail` -> `handle_resolution_exception`, `THROW_MSG_CAUSE`). CratonVM's NCDFE had no cause.
       The `defineClass1` / `defineClass2` supertype pre-pass (`preload_supertypes_via_loader`,
       `native-builtins/src/lang_system.rs`) swallows the loader's throw and leaves the error to
       `define_class_full`, which names the supertype but has no cause. Fix, `CRATONVM_DEFINE_SUPERTYPE_MISS_CAUSE`
       (default ON, `=0` throws the cause-less error): the pre-pass records the first supertype whose `loadClass`
       threw a `ClassNotFoundException` (class and message). When the define then fails with NCDFE naming that
       supertype, the error is rebuilt with a new throwable of the recorded class and message as its cause
       (`supertype_miss_with_cause`). The EnclosingMethod record keeps that cause, so the "again" line rethrows it
       too. Unit test: `only_the_missed_supertypes_error_gets_a_cause`.

     Expected after the build, in all three modes: both probes match HotSpot, including `asks ... Gone=2` and
     `asks gone=2 goneSuper=1`. Unresolved: `defineClass0` (Lookup / hidden defines) does not take the cause; no probe
     reaches it. A loader that throws something other than `ClassNotFoundException` for a supertype is still
     swallowed, where HotSpot propagates that throwable unchanged. Both are out of this lane's rows.
5. **`R21Fz9FinLater1`**
   - A short `finalized` count for a finalizable shape means the registration was missed. Check 9 and 14 first,

   - A `reg` line that says `registered` for 0, 2, 3, 6, 8, 12, 13 or 15 means the empty-finalizer rule was
     ignored, or has_finalizer leaked by name.
   - `reg 11` that says `not registered` means the abstract finalize was treated as empty.
   - Rerun on a short count, because the settle loop may be the cause.
6. **`R21Fz9HiddenUnload1`**

   - A different `walkH`, `walk` or `dive` line means the unwinder named or showed hidden frames differently from
