## Still open, carried

- **C1** (MEDIUM-HIGH perf): each concurrent sweep slice re-sorts the free list. Proposal `gcj-j2og2-proposal-concurrent-sweep-keeps-the-sorted-free-view-20261019.md`. O5 does not close it: the sweep frees through `OldGen::free`, not through a coalesce.
- **C4** (MEDIUM pause): the initial mark builds the eligibility set and the slice cache's set from one walk by two `OldGenObjectStarts::build_from` calls. The cheap cut (build once, copy the words) needs a `duplicate()` on `young_mark::ObjectStartBits`, which is lane yg's file: cross-lane hunk X2 of the j3/og3 report.
- **C5** (MEDIUM perf, and not as cheap as it looks): the stripe mutex per 16-byte legacy slot in the stop-the-world remark drain "protects nothing" only if nothing writes a legacy slot while the remark runs. Threads in native are counted as stopped at a safepoint; whether a JNI field store (`Set<Type>Field` through the field helpers) can run in that state during the remark was NOT established by this lane's reading. Close by proving it cannot (lanes rt3 / jn: the in-native band and the helpers' transition), then pass an `in_pause` flag to the remark's scan (`scan_object_into_with`) and skip the lock there.
- **C6** (LOW): cleanups, as listed (the `finish_sweep_as` clear stays on purpose).
- **C7, the second half**: retained dead finalizables are re-traced every concurrent cycle until a stop-the-world collection drains them. That re-trace is what keeps them (and their subgraph) alive until reported, so it cannot simply be dropped; the cost is bounded by the remark retaining at most the published candidates.
- **O4** (LOW): `close_live_set_from_seeds` scans a seed twice when an earlier seed promoted it (opt-in path only).
- **O6, the third item**: the pinned compactor's Phase 0b still builds its own start set (`close_live_set_over_old_gen`); it could take the collection's shared one as the slide does. With `CRATONVM_GC_OLD_PINNED_COMPACT_REUSE_CLOSE` it is skipped on true-root majors anyway.
- **O7** (LOW, release hazard), as refined by og2: needs a filler-header writer for the trimmed remainder; not done.
- **O9, the flag half**: `CLOSE_BITMAP_FLAG` / `FORWARD_INDEX_FLAG` are read per closure / per compaction. Reading them once per generation would break the unit tests that set them with `with_thread_overrides` after the generation exists; leave until the tests build the generation inside the override.

## New this wave

**P1. INFO (measurement): the j1c block F VOID verdict had two causes, both artifacts** -- the probe's `System.gc()` ran under a compiled frame (a requested major with a conservative root reclaims in place), and the pinned compactor never printed the forward-index line. Page `gcj-j3og3-old-gen-compaction-reachability-on-default-generational-20261019.md`; probe `Gcj3Og3CompactingMajorProbe`. `tools/probes/Gcj1OgFullGcCompactProbe.java`'s doc ("Every `System.gc()` ... is a full mark-compact") is false on a JIT-warm Generational run; left unedited (its class md5 keys the HotSpot cache of block F's rows).

**P2. MEDIUM (parity): on a default run the full-GC slide is reached only under a pending fragmentation request** (P-C takes every frame-free moving major, the JIT guard vetoes the rest), and the pinned compaction only on an interpreted `System.gc()` or a refused humongous allocation. Same page; proposal `gcj-j3og3-proposal-fragmented-in-place-majors-compact-through-the-pinned-compactor-20261019.md`.

**P3. LOW (FIXED IN CODE, opt-in arm only): the young pause's deferral to an open concurrent cycle returned before `OldGen::major_trigger`** (`major_trigger_decision_policy`, the `note_stw_deferred` arm), so that cycle made no counted decision. Harmless for the 75 % trigger (it has no per-cycle state); for the Serial-shaped trigger it would have folded two cycles' promotions into one sample. The arm now takes the sample (`OldGen::sample_young_cycle_promotion`).

**P4. MEDIUM (the residual risk of `CRATONVM_GC_OLD_COMPACT_TRUST_MARK`): the BFS only scans what it pushes, and it pushes only what it newly marks.** An object that carries `GC_FLAG_MARKED` at the START of a major (a mark another collector left) is never scanned, and Phase 0 is what used to close over it. Every collector is meant to clear the bits it set (the in-place free loop, the compactors' slides, their escape arms); this lane did not re-verify every exit, the switch's `slide_trusted` assumes it, and nothing checks it. The verify mode (`CRATONVM_GC_OLD_COMPACT_TRUST_MARK_VERIFY=1`) is the check: run the whole battery with it before any flip; one `compact-trust-mark-disagreement` line refutes the switch.

**P5. LOW (design note): the Serial-shaped trigger cannot count the reservation headroom HotSpot counts.** HotSpot's `promotion_attempt_is_safe` includes the tenured generation's uncommitted virtual space, because a promotion can expand it. Here a growth happens only at a collection's end after a refused allocation (`grow_after_refusal`), so counting the headroom would let a promotion fail first; `serial_trigger_verdict` counts committed-capacity free space only and so collects earlier than HotSpot on a heap with headroom. Its other clause (`available >= young used`) is not taken either: `OldGen` does not see the young used size. Both make the switch collect more, never less; the rows decide whether it matters.

**P6. LOW-MEDIUM (observability; j3a row `og3_b3_nums`): `CRATONVM_GEN_TENURED_POOL_MAX_FIXED` can reach HotSpot's fixed tenured max only partly.** The pools' maxima must sum to `maxMemory()` (`max_usable_heap_bytes` = young semi max at the CAPACITY plus the capacity), and the young max may not fall below the semi-space the young arena already has (`max(from, to)`). The first version broke the sum (rc 1, 245 vs 192 MiB at `-Xmx256m`); the fixed one reports `min(growth limit, maxMemory - max(from, to))`, never below the capacity, so while the young arena is at its maximum the tenured max is the capacity again (128 vs HotSpot's 170 MiB). Closing it needs a fixed `maxMemory` (lane ob, `max_usable_heap_bytes`), i.e. HotSpot's accounting of the copy reserve. The original note stands too: past the soft cap a refused request still moves it.

**P7. LOW: `OldGen::ungrow_after_collection` follows the committed end, not `MaxHeapFreeRatio` directly** (`ungrow_target`): the capacity falls only as far as the committed resize (`resize_after_collection`, with its damping and the opt-in shrink factor) already released. That is the proposal's design (the capacity follows the committed size with the same damping); a run whose committed size never falls keeps its grown capacity.

**P8. INFO: the cross-lane counters of this wave and the last are printed only under `CRATONVM_DBG_GCPHASE`** (`[gcphase] old-gen compact-phase0-skipped` etc.). The `[GC] oldgen_j1og:` summary line (lane ob's function in `vm_heap.rs`) needs hunk X1 of the j3/og3 report to show `oldsz_phase0_skips`, `oldsz_trust_mark_disagreements`, the Serial trigger and capacity-shrink counters.
