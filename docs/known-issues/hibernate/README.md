# Hibernate ORM test suite — known issues index (2026-07-16 full-suite rerun)

Source: full 4548-class Hibernate ORM 8.0 test suite run on this local Windows
host, `dev` merged to `2f02e939d`, real-JDK, JIT on, 4 shards, `TIMEOUT=1200`.
Result: `PASS=4437 (97.6%) FAIL=10 HANG=1 CRASH=1 ABORTED=8 NOTESTS=91`. This is
a large improvement over the 2026-07-11 audit baseline (`PASS=4095, 90.0%`),
reflecting the large number of concurrent fix branches merged into `dev`
since (statistics-counter cluster, sql.exec cluster, enhancement/setter
cluster, ANTLR entity-graph NPE cluster, immutable-collection and
cascade-multipath hang clusters, connections/proxy serialization cluster,
boot-models XML/Jandex cluster, and the assertion-longtail catalog — see
`docs/internal/fixed-suite-bugs/` for the individual write-ups). Every
cluster from the 2026-07-11 audit is now archived there as FIXED/RESOLVED.

**Data-loss note:** the exact 2026-07-11 453-class and later 224-class
non-passed baselines (`apps/hib-suite-runner/nonpassed*.txt`) were lost to
local-disk-exhaustion file corruption discovered 2026-07-16 (511/683 files in
`apps/hib-suite-runner`, including `rerun.sh`, `common.args`,
`CratonRunner.java/.class`, and `testlist.txt`, were silently truncated to
zero bytes). The harness driver files were recovered from an intact
`hib-suite-runner.tar` backup (2026-06-28/29 vintage); the non-passed class
*lists* themselves were not in that backup and could not be recovered. This
full-suite rerun was run specifically to regenerate an accurate current
baseline rather than trust a stale/partial list.

The new 20-class non-passed list is saved as the canonical baseline at
`apps/hib-suite-runner/nonpassed.txt` (also `nonpassed20.txt`) for future
regression tracking — not committed (`apps/` is gitignored).

## Residual clusters (2026-07-21 "passed"-category rerun, HANG triage)

- [`hql.ASTParserLoadingTest` JAXB reflection throughput wall — FIXED](../../internal/fixed-suite-bugs/hibernate/astparserloadingtest-jaxb-reflection-storm-throughput-wall-20260721-FIXED.md) — the safe-native root snapshot is now published only at collector-visible boundaries, and the Hibernate runner defaults to 2 GiB. The exact 106-test class passes within the 300-second cap under both JIT and `--nojit`.
- [ejb3xmlelementcollectiontest-jaxb-reflection-storm-20260721.md](ejb3xmlelementcollectiontest-jaxb-reflection-storm-20260721.md) — `annotations.xml.ejb3.Ejb3XmlElementCollectionTest` HANG (rc=124), a second unrelated shard in this same run. Another confirmed trigger of the same `update_root_snapshot` JAXB reflection-storm wall (371 live stack samples, oscillating 139-150 frames deep inside GlassFish JAXB's `RuntimeModelBuilder`/`ClassInfoImpl` model construction, never stuck). Supersedes the older `hibernate-jaxb-classloading-bytebuddy-bootstrap-slow.md`'s "RESOLVED/does-not-reproduce" verdict for this specific class — no `retainAll`-stuck frame observed in this session's repro; the class still hangs on current `dev`, just via the newer, still-OPEN root cause rather than the older (already-fixed) class-load-storm layer.
- [insertorderingrcatest-eager-circular-fetch-recursion-20260721.md](insertorderingrcatest-eager-circular-fetch-recursion-20260721.md) — `insertordering.InsertOrderingRCATest` HANG (rc=124), unrelated to the above. Solo repro (2396 live stack samples, oscillating 146-164 frames deep) shows genuine, continuous forward progress inside Hibernate's `ToOneAttributeMapping`/`LoaderSelectBuilder` EAGER circular-fetch SQL-AST builder — a different phase (schema-DDL-adjacent, pre-batch-insert) and a different Hibernate subsystem than the previously-documented ~59-70s "generic architectural gap" (JDBC batch-insert method-diversity) for this same class. Most likely another trigger of the same `update_root_snapshot` mechanism, via Hibernate's densely-cross-referenced, all-`FetchType.EAGER` `Condition`/`Expression` entity hierarchy rather than JAXB or ANTLR.
- `query.hql.FunctionTests` and `function.json.JsonArrayUnnestTest` also HANG (rc=124) in this same run, but both are **already-known, already-documented throughput characteristics, not new bugs**: `FunctionTests` shares one `SessionFactory`/GAMBIT domain model across 123 `@Test` methods and was already shown to complete cleanly (`found=123 ok=117`) given enough time (see [`hib-query-hql-functiontests-translation-cluster-NOT-A-BUG.md`](../../internal/hib-query-hql-functiontests-translation-cluster-NOT-A-BUG.md), [`fixed-suite-bugs/functests-astparser-defaultcatalog-post-fix-slow-FIXED.md`](../../internal/fixed-suite-bugs/functests-astparser-defaultcatalog-post-fix-slow-FIXED.md)) — solo repro this session **completed** at `ms=663793` (11.1 minutes — over 2x the harness's 300s default): `found=123 started=117 ok=89 failed=28 aborted=0 skipped=6`. Definitively not a hang — it terminates, just slowly. (The exact failure count varies run-to-run — 28 here vs. 20/18/0 in the three prior docs above — consistent with the already-documented test-order/shared-fixture-dependent flakiness of this class, not a new regression.) `JsonArrayUnnestTest` is Cluster H4 territory ([`hibernate-hang-clusters-summary.md`](../../internal/fixed-suite-bugs/hibernate/hibernate-hang-clusters-summary.md), [`jit-deep-recursion-fault-recovery.md`](../../internal/jit-deep-recursion-fault-recovery.md)) and its own historical "FIXED" validation runs already recorded 201-412s for this 5-test class, i.e. already at or past this harness's flat 300s default even when working correctly — **refined this session**: a `--stack-dump-on-timeout 150` solo repro (reproduced identically twice, same exact stall point both times) shows the actual mechanism for `testUnnest` is not H4's ANTLR-parse-time cold prediction (the HQL had already fully translated to SQL, logged, before the stall) but **execution-time**: H2's nested-loop evaluation of the `lateral unnest` → `join system_range(1,1000)` translation's join condition, which calls `array_length`/JSON `getDecomposition` (a fresh JSON parse) on every one of up to ~3,000,000 row candidates (3 books × 1000 × 1000), each iteration threading ~100 interpreter frames deep (`Comparison.getValue → ExpressionColumn.getValue → Value.convertTo → ValueJson.getDecomposition → JSONArray.length → Value.isFalse`, repeating identically — 3258 live samples confirm real, cyclic, terminating iteration, not a stuck frame). Severe but finite; likely the same interpreter-dispatch/native-call-overhead family as the `update_root_snapshot` findings above, just keyed by iteration count rather than call depth. Both `FunctionTests` and `JsonArrayUnnestTest` are the same class of finding as this run's `DefaultCatalogAndSchemaTest` (see [`qualfiedtablenaming-hang-cluster-20260721.md`](qualfiedtablenaming-hang-cluster-20260721.md)): the harness's one-size-fits-all 300s timeout is simply too short for these already-known-slow classes. No new doc filed for either (refinement folded into this entry instead).

## Residual clusters (2026-07-21 "passed" rerun)

- [atnstate-transitions-npe-intermittent-hql-parse-20260721.md](atnstate-transitions-npe-intermittent-hql-parse-20260721.md) — `query.hhh12225.HQLTypeTest` and `query.hql.JsonFunctionTests` both intermittently throw `java.lang.NullPointerException: ATNState.transitions` inside real (unshaded) `org.antlr.v4.runtime.atn.ParserATNSimulator.computeTargetState`/`execATN`/`adaptivePredict`, reached from Hibernate's generated `HqlParser` while parsing a SELECT expression list. Confirmed genuine and non-deterministic (isolated repro: 3/6 clean-JVM attempts for `JsonFunctionTests`, 0/6 for `HQLTypeTest`). Distinct from both previously-fixed ANTLR bugs in this codebase (the deterministic chained-operator closure bug and the entity-graph `RuleNode.getChildCount()` cluster) and from the JIT-ban already in place for the real ANTLR runtime. Leading (unconfirmed) hypothesis: a GC-timing-sensitive stale-object-reference issue in the native Rust reimplementation of `ParserATNSimulator`'s closure/reach-set methods (`native-builtins/src/lib.rs`), the same code area as the earlier fixed bug. OPEN, root cause not pinned.

## Residual clusters (2026-07-21 "others" rerun)

- [joinedsubclassbatch `CycleBreaker` flush hang — FIXED](../../internal/fixed-suite-bugs/hibernate/joinedsubclassbatch-cyclebreaker-flush-hang-20260721-FIXED.md) — real-JDK CratonVM now defaults Hibernate's supported `hibernate.flush.queue.type` to `legacy` unless explicitly configured, avoiding the GRAPH `ActionQueue` `CycleBreaker` throughput wall while preserving an explicit `graph` override. Final fresh-binary validation passed both six-test classes in JIT (12/12, 73.3 s) and `--nojit` (12/12, 65.0 s).
- [qualfiedtablenaming-hang-cluster-20260721.md](qualfiedtablenaming-hang-cluster-20260721.md) — `DefaultCatalogAndSchemaTest` + `NamespaceTest` (`org.hibernate.orm.test.boot.database.qualfiedTableNaming`) both reported `HANG` (rc=124) in the 2026-07-21 "passed" rerun. `DefaultCatalogAndSchemaTest`: **NOT a regression** — the BigInteger AIOOBE quarantine (`41cdfdf94`) is verified intact on this run's `dev` tip; this class's own well-documented "clean" runtime floor (620s-1083s+, per `hib-misc-residuals-20260716-FIXED.md`) simply exceeds the harness's flat 300s per-class timeout, and solo CPU-sampling confirms genuine sustained computation, not a stall. `NamespaceTest`: does not reproduce solo (9.6s clean run); most likely shared-host contention noise given confirmed concurrent CratonVM processes on the host and temporal clustering with the sibling shard's hang. No code change.
- [storedproc-h2-inprocess-javac-classpath-scan-slowness-20260721.md](storedproc-h2-inprocess-javac-classpath-scan-slowness-20260721.md) — `sql.storedproc.{ResultMappingTest,StoredProcedureTest}` HANG (rc=124) and `sql.storedproc.StoredProcedureResultSetMappingTest`/`jpa.procedure.StoredProcedureResultSetMappingTest` FAIL with JUnit per-test/setup `TimeoutException` (120s). All four use H2's `CREATE ALIAS ... AS $$ ... $$` to compile a small Java stored-procedure body in-process via the real JDK's `javax.tools.JavaCompiler`. Root-caused (via a `--stack-dump-on-timeout` repro) to genuine, continuous CPU-bound forward progress deep inside real `javac`'s classpath scanner (`ClassFinder.scanUserPaths`/`JavacFileManager$ArchiveContainer.list`) walking the harness's ~241-jar test classpath to resolve one `import` — not a deadlock. Distinct from the already-fixed HIB-CV-27 `File.separator` compile-error bug (confirmed still fixed here). Reconciles two prior docs that flagged this same class pair as unexplained host-load-correlated flakiness — the underlying compile is inherently slow enough on CratonVM to sit at the edge of the 120s/300s timeouts, so host contention (present in abundance on this shared box) tips individual runs over one threshold or another. OPEN, not fixed; exact CratonVM-side hot loop responsible for the per-call overhead not yet isolated.

- ~~packagedentitymanagertest-regression-20260721.md~~ — **FIXED 2026-07-22**; moved to [`docs/internal/fixed-suite-bugs/hibernate/packagedentitymanagertest-regression-20260721-FIXED.md`](../../internal/fixed-suite-bugs/hibernate/packagedentitymanagertest-regression-20260721-FIXED.md). `ClassPath::new()` had accepted only `.jar` entries while a child URLClassLoader contained valid `.par` ZIPs; treating existing archive files uniformly restores XML mappings, XML-only entities/listeners, and ServiceLoader resources.
