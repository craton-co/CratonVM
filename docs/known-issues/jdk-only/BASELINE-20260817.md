## First diagnosed failure: `RArrayStoreInterfaces`

MEASURED by diffing both VMs' raw output. **One row of 108** diverges:

```
s12  Runnable[]  <- Proxy(Marker)
  HotSpot   cold=[ArrayStoreException]  hot=[ArrayStoreException]
  CratonVM  cold=[no-throw]             hot=[no-throw]
```
`illegalRefused=11/12` against the oracle's `12/12`; `legalAdmitted=15/15` on both.

It fails **identically in the interpreter (`cold`) and the JIT (`hot`)**, which
rules out both a JIT-lowering bug and an artefact of the `aastore` ABI
unification this merge performed: the *shared* refusal decision is wrong.
Row `s25` (`Marker[] <- Proxy(Marker)`, legal) passes, so proxies are not
ignored wholesale — the predicate admits a proxy into an array of an interface
it does implement, and fails to **refuse** one for an interface it does not.

`RJdkProxy` and `RJdkProxyIface` also fail, so the blast radius is plausibly
three vectors, not one. That is a hypothesis, not a measurement.

`AbstractMethodError: ... has no Code attribute` — on two unrelated types

implementation. That is the interface-door family (`C7-2`, `C13-1`), and
fixing it plausibly closes two vectors. **Plausibly** — not measured.

Do not fix it with a blanket rule — the blanket rule is what the handoff
warns produced broken paths.

### `RCrypto` is a correct fix exposing an older defect, not a regression

`RCrypto.java` never names `PathMatcher` or `newDirectoryStream`; the call
comes from inside JDK code. The chain, MEASURED:

`Files.newDirectoryStream(dir, glob)` **never read its
`DirectoryStream$Filter` argument at all** — glob filtering silently returned
every entry. That was fixed in `d378eee51`, and the io/nio lane flagged it at
the time as its single riskiest edit for exactly this reason. Now the filter
is invoked, so `PathMatcher.matches` is dispatched for the first time — and
lands on the abstract declaration.

So `RCrypto` was **never really green**: it was green because a filter it
depended on was never called. The vector was passing over a silent lie. That
is the same category the io/nio sweep exists to find, and it is the second
time in this session that removing a fabricated success turned a green vector
red for a correct reason.

### The `AbstractMethodError` family is now THREE vectors

`java.util.Map.isEmpty()`, `java.net.http.HttpRequest.version()` and
`java.nio.file.PathMatcher.matches()` — three unrelated types, one error
shape. `RCrypto` is the cheapest repro of the three: the receiver is a real
JDK implementation reached from JDK bytecode, with no synthetic carrier
anywhere in the path.

**ANSWERED 2026-08-17 (lane G13): TWO mechanisms, and the split is not the one
the type names suggest.** The discriminator is a single field -- is the
receiver's runtime class the resolved class?

* **`HttpRequest.version()` and `PathMatcher.matches()` are the SAME bug.** A
  native fabricates an instance of an abstract type and the method invoked on
  it has no native either. `HttpRequest$Builder.build()` mints a
  `java/net/http/HttpRequest` with **3 of 7** accessors registered;
  `FileSystem.getPathMatcher()` mints a `PathMatcher` with **0 of 1** -- an
  object with no usable method at all. Both fail identically WITHOUT
  `--jdk-only`. `AbstractMethodError` is the correct JVMS answer here; the
  mistake happened one call earlier. Control: `HttpClient` is built the same
  way in the same file and its accessor surface is 7 of 7 correct.

* **`Map.isEmpty()` is a FIELD-SLOT COLLISION**, proven by reflection on both
  VMs. `LinkedHashMap$LinkedValues` is the only one of the six view carriers
  declaring TWO fields (`reversed`@0, `this$0`@1), so ArrayList's absolute
  `elementData` slot 1 overwrites `this$0`. `vc_route` reads it back by name
  and hands an `Object[11]` to `collect_entries_any`, which then invokes
  `java/util/Map.isEmpty()` on an array. **In Compatible mode the substitution
  SUCCEEDS and reports a three-entry view as empty** -- the error is the
  better outcome.

## Tooling correction: `invocations` in `--dump-native-registry` is NOT useless

A lane concluded that "the registry dump is taken at registration time, so
`invocations` is useless for ownership and `owns_slot` is the proof." The
first half is wrong and the correction matters, because the whole method in
`HANDOFF-20260814` §4 rests on this tool.

MEASURED, two dumps on the `d2e127930` binary under `--jdk-only`:

| workload | rows with non-zero `invocations` | `Handler.setLevel` |
|---|---|---|
| `RJdkHello` | **120** of 10,640 | `invocations=0` |
| `RJdkIntrinsics3` | **392** of 10,640 | **`invocations=2`** |

The counter works. It read zero for `Handler.setLevel` under `RJdkHello`
because `RJdkHello` never calls `setLevel`. The dump also carries a top-level
`invocations` block (`intrinsic: 267, bridge: 2818` on the `RJdkHello` run),
which alone disproves "taken at registration time".

The rule, stated properly:

- **`owns_slot=true` proves OWNERSHIP** — this registration holds the slot.
  It is workload-independent.
- **`invocations > 0` proves the body RAN**, and only in that run. It is
  workload-DEPENDENT, so it is evidence only if the workload you dumped
  against actually exercises the triple.
- Dumping against a workload that does not call your method and concluding
  "invocations is broken" gets the tool exactly backwards.

Row keys, for reference: `class, descriptor, name, kind, kind_stated,
kind_chosen, registered_by, overwrote, owns_slot, invocations,
real_declaring_method, image_declaring_method`.

Also worth knowing on this host: the flag needs a **Windows** path. Git Bash's
`/tmp` is a POSIX mapping the VM (a native Windows binary) does not resolve,
so `--dump-native-registry /tmp/reg.json` writes somewhere `ls` can see and
native tools cannot.
