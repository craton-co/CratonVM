# Phase 1: the measurement after the fixes

**Measured 2026-08-12 on a release binary built from this branch
(`cargo build --release -p cratonvm-cli`, exit 0, 0 errors, 17m46s), against
HotSpot 25.0.3+9 as oracle, same host, same session, same class files.**

The "before" is `P1-BASELINE-20260812.md`, taken on the pre-wave binary.

## The sweep — FINAL, after the `Arena.allocateFrom` fix

| probe | HotSpot | before | after |
|---|---|---|---|
| `P1Witness` (java.sql, `getenv`, SSL construction) | 8 / 0 | 2 / 6 | **8 / 0** |
| `P1Tls` (real loopback TLS round trip) | 6 / 0 | 3 / 1 | **6 / 0** |
| `FabReach` (iteration, functional, proxies, sockets) | 17 / 0 | 15 / 2 | **17 / 0** |
| `FabReach2` (streams, FFM, NIO, HttpServer, JMX) | 16 / 0 | 15 / 1 | **16 / 0** |
| `FabReach3` (Enumeration, async channels, `Runtime.exec`) | 7 / 0 | 3 / 4 | **7 / 0** |

**54 of 54 checks match HotSpot exactly**, from 28 of 54 before. The FFM
downcall completes: `strlen("abcd") == 4`, `rc=0`, on a real libffi call
through a real `MethodHandle` carrier.

`FabReach2` needs `--enable-native-access=ALL-UNNAMED`. That is **not** a
defect: CratonVM's Panama gate is default-**closed** where HotSpot 25 only
warns, so without the flag the probe gets a clean, correct
`IllegalCallerException`. `regression-suite/run.sh`'s `class_cv_args` already
supplies the flag for `RJdkForeign`. An earlier run of this page's own sweep
script reported 15/1 purely because the script did not pass it — **the harness
was measuring its own omission**, which is the same species of error this
campaign has recorded four times, and it is recorded here a fifth.

All nine blocking families are closed and verified by measurement:
`java.sql`/`Atomic*FieldUpdater`, `System.getenv()`, the TLS stream receivers,
`Consumer.andThen`/`Predicate.and-or-negate`, `ConcurrentHashMap.keys()`,
`Hashtable.keys()`, `AsynchronousFileChannel`, and all six `Runtime.exec`
overloads.

## The census moved exactly as predicted

`compatibility-class-requested` fell **19 → 6**, and the six survivors are
precisely the recovered-from set the "a request is not a failure" analysis
named:

```

Every one is requested, refused, and **recovered from** — the corresponding
Java passes. Not one names `vm/src/vm/vm_init.rs`, confirming the boot block no
longer asks. `Enumeration$Impl`'s requester is now `classloader.rs:6074`, the

`try_alloc_synthetic` records the violation **before** refusing and the

counts requests, and a fixed family stops being fatal without stopping being
counted.**

## The ninth family: the carrier was never the problem — CORRECTED

> **This section originally read "fixed at the carrier, and it exposed a crash",
> and attributed the SIGSEGV to the newly reachable invoke path. That was
> wrong.** A lane traced it and produced a positive control that settles it.
>
> **The fault is `Arena.allocateFrom(String)`.** It is registered exactly once
> (`native-builtins/src/phases_late/foreign_ffm.rs:1826`) and calls
> `p67_arena_segment`, which **allocates no memory at all**, never copies the
> string's bytes anywhere, and writes the **size into slot 0** — the inverse of
> the `[0]=ptr, [1]=size` convention every reader uses. So
> `panama_libffi::segment_address` fell through to `get_field(seg, 0)`, read
> `Long(5)` — the byte length of `"abcd\0"` — and libffi passed **5** as the
> `char *`. `strlen` dereferenced address `0x5`.
>
> The crash dump says exactly that: `read at address 0x0000000000000005`,
> `rax=0x5`, and the faulting `pc` matches the independently measured address of
> `strlen`. **The callee was correct; only the argument was wrong.** The same
> object reports `byteSize() == 0` and `address() == 5` — inverted on both.
>
> **Positive control, on the same binary**, building the argument with
> `allocate(5)` plus explicit byte stores instead of `allocateFrom(String)`:
>
> ```
> CratonVM  arg address=0x23489c31848 byteSize=5   strlen(abcd) = 4   rc=0
> HotSpot   arg address=0x298ce9f6cf0 byteSize=5   strlen(abcd) = 4   rc=0
> ```
>
> So the carrier, the signature-polymorphic `mh.invoke` dispatch, the CIF build,
> the libffi call and the return unmarshal are **all correct and match
> HotSpot**. The P1-E fix is complete and verified. The SIGSEGV is a
> **pre-existing `allocateFrom(String)` defect that the carrier fix merely made
> reachable** — the old binary died at `downcallHandle` before any argument was
> ever built.
>
> Fixed by routing `allocateFrom(String)` through `pe_arena_allocate` (the same
> path `Arena.allocate(long,long)` uses) and copying the bytes in.
>
> **The lesson is the one this campaign keeps paying for.** I attributed a crash
> to the code that had just changed, because it had just changed. The lane
> disagreed, built the discriminating control, and was right. *"It broke after
> your change"* locates a **reachability** boundary, not a cause.
>
> Two further measured findings from the same lane, both now refused rather than
> dereferenced: `MemorySegment.ofBuffer(ByteBuffer.allocateDirect(32))` reports
> a **tagged** arena handle (`0x4000001000000000`, bit 62 set) which libffi would
> hand to a callee — always fatal; and `validated_fn_ptr` was equally exposed,
> since a tagged handle is non-null and 16-aligned and so passed both existing
> checks and would have been **called**.

## The ninth family: the original (incorrect) reading, kept for the record

`java/lang/foreign/DowncallHandle` is gone. The carrier is now a real
`java.lang.invoke.MethodHandle` and it matches HotSpot field for field:

```
              CratonVM                          HotSpot
handle class  java.lang.invoke.MethodHandle     BoundMethodHandle$Species_LLLL
handle type   (MemorySegment)long               (MemorySegment)long
```

But `mh.invoke(segment)` **SIGSEGVs**. Three states, cleanly attributed:

| binary | flags | result |
|---|---|---|
| pre-fix | `--enable-native-access` | `NoClassDefFoundError: DowncallHandle`, rc 1 |
| post-fix | *default* | real handle, correct type, clean `IllegalCallerException`, rc 1 |
| post-fix | `--enable-native-access` | **SIGSEGV, rc 139** |

**This is newly reachable code, not a regression in something that worked** —
the old binary never got past `downcallHandle`, so the invoke path had never
run. The default configuration is strictly better than before: a clean typed
exception from the Panama gate instead of a `NoClassDefFoundError` about a
class no JDK declares.

It is still recorded as **not fixed**. A crash is worse than an exception, and
an application that enables native access reaches it. Saying "nine of nine"
here would be counting the carrier and ignoring the call.

## What this does and does not license

**Does:** the Phase 1 mechanism — an essential-set native asking for a
fabricated receiver and killing the application at its own call site — is
closed on every route these 54 checks take. JDBC class loading, `System.getenv`,
a real TLS round trip, the core functional interfaces, the legacy `Enumeration`
getters, async file channels and `Runtime.exec` all work under `--jdk-only`.

**Does not:** 54 deterministic checks are not an application. The roadmap's own
definition of done is a Spring Boot application, a servlet container serving
HTTPS, and a JDBC workload each running to completion — none of which has been
run. The corpus runner landed this session and **no corpus has been run under
`--jdk-only` yet.** That is the next measurement, and it is the one that can
still overturn this page.

Also unchanged: the census's 229 `native-shadows-bytecode` rows are Phase 2 and
untouched, and an ambient-`Intrinsic` block is invisible to that census by
construction — which is how `Math.min(1.0, NaN)` returned `1.0` for an unknown
length of time.

## The regression suite, after everything

**76 passed / 6 failed**, from a **69 / 2** baseline, with **ten new vectors
added** — so the suite grew by ten and the green count grew by seven.

| new fixture | verdict |
|---|---|
| `RJdkSqlPackage`, `RJdkEnvMap`, `RJdkFormatLocale`, `RJdkStrictMath`, `RJdkByteOrder`, `RJdkFunctionCombinators`, `RJdkAsyncChannel` | **PASS** |
| `RJdkProxyIface` | FAIL — `ldc CONSTANT_MethodType` yields a **non-interned** `MethodType`. Predicted verbatim by the lane that implemented the decoder. |
| `RJdkForeign` | FAIL — `MemoryLayout.byteOffset` / `MemorySegment.getString` raise `AbstractMethodError`. The FFM **interface-instance wall**, predicted verbatim as "the next wall" by the lane that fixed the carrier. |
| `RJdkEnumerations` | FAIL — `Hashtable.keys()` returns `java.util.Collections$3`, not the JDK's dual `Enumeration`/`Iterator` carrier. |

The `RJdkEnumerations` failure is the most instructive of the three. Its author
wrote, before any fix existed: *"Mutating the carrier to
`Collections.enumeration(h.keySet())` — the tempting shim a fix could regress
into — → RED."* The fix that landed is exactly that shim, and the fixture caught
it. It works, and it returns the wrong carrier type. **A fixture written to
catch the tempting wrong fix caught the tempting wrong fix.**

`RExceptions` is the one deliberate long-standing red (the `aastore` covariance
hole, patch written and held pending a store-heavy A/B).

Two of the six failures are `HARNESS` rows downstream of a vector that died and
therefore emitted no output — not independent defects.
