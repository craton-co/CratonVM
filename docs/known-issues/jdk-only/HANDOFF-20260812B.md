**The shape they all share, and the orchestrator's own correction on it
(`88eaeacfb`):**

> A native registered in the **essential** set survives strict mode, runs, asks
> for a **fabricated** receiver, gets the refusal that `--jdk-only` exists to
> give, and dies as `NoClassDefFoundError` at the application's call site.
> **The refusal is correct. The survival of its caller is the defect.**

A lane read the FFM row as "strict mode correctly refusing a synthetic carrier —
a control, not a defect". Half right, and the wrong half matters: *every* one of
the nine has a correct refusal, so if that made a row a control, Phase 1 would
be empty while `java.sql` stays unloadable. **Ask what the application can do,
not whether the VM behaved as designed.** The lane's narrower point is kept and
is worth keeping: P1-E is **not a missing feature** — `Linker.downcallHandle`
works, the carrier was simply the wrong class.

### Residuals inside the applied fixes, named so they are not lost

* **P1-B's last-ditch arm returns a MUTABLE map.** If neither
  `java.util.Collections.unmodifiableMap` nor the stand-in is available, the
  native warns and returns the backing `HashMap` — its own message says
  "which is MUTABLE unlike HotSpot's". That is a deliberate, documented
  degradation, not an oversight, and it is a divergence a fixture should pin.
* **P1-A removed the base-class accessors as well as `newUpdater`**, and the
  module explains why that is load-bearing rather than tidying:
  `getAndIncrement`/`addAndGet`/… are concrete on the abstract base and are not
  overridden by `Atomic*FieldUpdaterImpl`, so a real JDK receiver reaching the
  native would read `offset`/`cclass` as the VM's own slots and fetch-add
  **slot 0** of the target — a silent wrong-slot write. Leaving them registered
  while dropping `newUpdater` would have been worse than either.
* **P1-F replaced only the carrier, deliberately.** A natively-backed
  `ConcurrentHashMap` keeps entries in a segmented layout that never populates
  `table`, so *deleting* the natives would answer an empty enumeration over a
  populated map — strictly worse than the refusal it replaced.

## 2. The instruments — the durable asset of this campaign

More was learned this wave from instruments that already existed than from any
new code. All four below work today on a shipping binary.

| instrument | invocation | what it answers |
|---|---|---|
| **JSON violation census** | `cratonvm --jdk-only --explain-jdk-only --jdk-only-report r.json -cp <cp> <Main>` | every policy violation of one run, three kinds, `schema_version: 1` |
| **registry census** | `cratonvm --jdk-only --explain-jdk-only --dump-native-registry c.json -cp <cp> <Main>` | per-row `(class, method, descriptor, kind, registrar)` + `image_declaring_method` |
| **class-origin census** | `cratonvm --jdk-only --dump-class-origins o.json …` | one row per loaded class with its **producer** — this is what caught P1-D's `$$Lambda` hole |
| **layout censuses** | `CRATONVM_DBG=layout` / `CRATONVM_DBG=layout-alias` | allocation-width and read-side slot-map disagreement |
| **corpus driver** | `bash regression-suite/corpus/run-corpus.sh run <corpus> …` | pass/fail/**diverge** against a HotSpot 25 oracle on a real application |

The JSON census's three kinds, on one ordinary program (1569 rows total):
`compatibility-class-requested` **19**, `native-shadows-bytecode` **226**,
`synthetic-native-registered` **1324**. Each row carries `class`, `requester`
(`file:line`), `initiating_loader` and `reason`.

**The flag-order trap, which costs an hour every time:** a VM flag placed
*after* the main class is a **program** argument. `--jdk-only-report` and
`--dump-native-registry` then produce **no file, no warning, exit 0** — the
failure mode that looks exactly like a broken flag. Two more ways to get the
same nothing, both from APP-READINESS-20260812.md §2: the report needs a
**Windows-shaped path** (a `/c/Users/...` path prints `os error 3` and
continues), and it is **not written when the program calls `System.exit`** —
every probe there grew a `-Dprobe.noexit=1` escape.

Two more instrument facts worth not re-deriving:

* `--explain-jdk-only` is **required** for `image_declaring_method`; without it
  the four-way split of STUB-CENSUS-20260812.md collapses.
* The registry census's stderr banner says "schema 3" while the payload is
  schema 4. **Read `natives[0]`, not the banner.** Do not confuse either with
  the violation census's `schema_version: 1` — different flag, different file.
* `CRATONVM_DBG_LAYOUT_ALIAS=1` still works and warns; the supported spelling is
  `CRATONVM_DBG=layout-alias`. Six records prescribe the deprecated form.

The corpus driver is new this wave and is the piece Phase 2 was blocked on. Its
design rules are worth carrying into anything else that adjudicates a real
application: HotSpot is the oracle and never the other CratonVM mode; an oracle
that started nothing is `ORACLE-UNUSABLE` and an oracle reporting `tests=0` is
`ORACLE-VACUOUS`, both **unadjudicated** rather than passes; failure is reported
in four disjoint shapes (`NOSTART` / `CRASH` / `TIMEOUT` / `RAN`) because they
have disjoint suspects; and the `cv_ms`/`hs_ms` columns are explicitly
**non-metric** on this shared host.

## 3. The method that worked, stated so it can be reused

**Two instruments with opposite biases. Only their intersection is the blocking
set.**

* **A reachability probe UNDER-reports.** It sees only the routes it thought to
  take. `FabReach`/`FabReach2` (33 probes, HotSpot 33/33) found five families
  and could not have found the other four, because no probe took those routes.
* **The census OVER-reports.** Every refusal appears, including the harmless
  ones. Reading it alone puts 19 classes on the Phase 1 worklist when a handful
  break anything.

The proof that a request is not a failure: `HashMap` iteration, `Comparator`
combinators and `Collections.enumeration` all **pass** under `--jdk-only` in the
same run in which the census records `HashMap$KeyItr`, `Comparator$Native` and
`Enumeration$Impl` being requested and refused. The native asks, is correctly
refused, and **the caller recovers onto real JDK bytecode.**

**Refine that rule before reusing it: recovery is a property of the CALLER, not
of the class.** `java/util/Enumeration$Impl` is on both sides — it is the
harmless-recovery example above *and* blocking family P1-G, because
`Collections.enumeration`'s caller recovers and `Hashtable.keys()`'s did not.
Reading "class X recovers" off one route is how a blocker hides.

**Both directions of surprise happened, and that is the argument for keeping
both instruments:**

* **The audit found what probing missed.** A two-term source rule — the
  receiver is on `NO_IMAGE_JDK_RECEIVERS`/`VM_MINTED_STAND_IN_RECEIVERS` *and*
  the minting native's frozen kind is `bridge` — predicted three families none
  of the 33 routes reached. Term 2 is free: the kind map at
  `scripts/baselines/jdk-only-kind-map-25-linux.tsv` is frozen and
  per-registration.
* **The audit's SCOPING was wrong where the probe was right.** `Properties`
  was predicted the widest failure — `System.getProperties().propertyNames()` is
  the JDBC/logging idiom — and it **passes**. Two `Enumeration` routes recover
  and two do not, naming two different fabricated classes. `FabReach3` is
  7 probes: HotSpot 7/7, `--jdk-only` **3/7**.

Two corollaries for whoever plans the next wave:

* **A screen that does not declare its own gaps reads as a proof of absence.**
  P1-BASELINE-20260812.md's "What these 33 probes did NOT reach" is the model to
  copy: roughly eight table entries were never exercised by any probe, and it
  says which.
* The 226 `native-shadows-bytecode` rows are **not 226 defects**. They are 226
  places to ask the question, and the corpus is what answers it.

## 4. The recurring defect shapes, with this wave's instances

These predict where the next ones are. Each carries a grep you can run.

### 4.1 Fix the positive half, leave its twin

The dominant shape of the campaign, and this wave produced the cleanest
demonstration yet: **the pinned half and its twin failing in the same probe
run.** `ProcessBuilder.start` and `Runtime.exec` share one mint
(`native-io/src/process.rs::spawn_and_wrap_with_redirects`). `start` was
re-tagged `SyntheticStub` so the fabricated class could not escape into strict
mode; the six `exec` overloads were left ambient `Bridge`:

```
OK   ProcessBuilder.start (the pinned half)
FAIL Runtime.exec(String[]) -> NoClassDefFoundError: cratonvm/synthetic/Process
```

Same wave, same shape, three more times: `Function.identity/andThen/compose`
passing while `Predicate` and `Consumer` failed **from the same file, minted the
same way**; `SSLSocketOutputStream` repaired while its `Input` twin nearly was
not; and `Enumeration$Impl` fixed at three mint sites and not at all of them.

**Rule: a re-tag that pins one caller of a shared mint must enumerate the
callers.** Grep the mint function's callers, not the fixed symbol's.

### 4.2 A registrar can be dead and nothing says so

**The orchestrator wrote a brief aiming a whole lane at `panama.rs`'s
`DowncallHandle` mint sites. Those sites are behind
`#[cfg(feature = "synthetic-jdk")]`, reachable only from
`register_synthetic_overrides` — in **neither** shipping binary. The live mint
was in `phases_late/foreign_ffm.rs`. The lane caught it and said so.**

This is category (D) of STUB-CENSUS-20260812.md, sized at ~4390 source call
sites in 282 synthetic-exclusive registrars, contributing **zero** census rows
by construction. Nothing refuses such a registrar loudly. A `Bridge` behind that
cfg is as dead in a shipping build as a `SyntheticStub` is in strict mode.

**Before briefing a lane at a registrar, establish it is reached in the mode you
care about.** The cheapest check is the registry census: a row that never
appears in either shipping binary's dump is not a row you can fix.

Beware the mirror-image trap when deleting: 428 of the 710 registrars reachable
from `register_synthetic_overrides` are **also** reachable from the shipping
path (`register_unsafe_natives`, `register_lock_support_natives`,
`register_net_natives`, and 27 others). Deleting one of those breaks the
shipping binary.

### 4.3 One rule implemented twice, then it drifts

* **The verifier accepted `ldc` operands the interpreter refused.**
  `classloading::verify_insn`'s `verify_ldc`/`verify_ldc2w` have long accepted
  `CONSTANT_MethodType`, `CONSTANT_MethodHandle` and category-2
  `CONSTANT_Dynamic`; the interpreter refused all three. A class file passed
  verification and then died at execution with `ClassFormatError: ldc:
  unsupported constant pool entry type` — which is exactly the
  `MethodHandleProxies.asInterfaceInstance` blocker (roadmap P3-B) that no stub
  census could see. The repair (`vm/src/runtime/interpreter/constants.rs`, +807)
  deliberately calls the three existing implementations of the same JVMS rules
  rather than restating them, and its header says why hardwiring a
  `MethodHandle` representation would have created a fourth twin.
* **`make_snapshot_enumeration` exists in two crates and only one grew the
  fallback** — and the one without it was the **winner**. `lib.rs` calls
  `deprecated_io_util::register_*` then `deprecated_util::register_*`, and
  `register()` is last-write-wins. The loser routed through the copy that had
  the recovery arm; the winner did not, so `Hashtable.keys()` died precisely
  because the winning copy was the one without it.

**Grep the SHAPE, not the symbol** — memory's "1 of 10 callsites" record is the
same species and cost more.

### 4.4 A name-shape check gating a policy decision

`fabricate_class`'s `--jdk-only` refusal is gated on
`origin.is_compatibility_stub()`. `fabricated_origin_for_name` used to route any
name containing `$$Lambda` to `ClassOrigin::GeneratedLambda`, a non-stub origin.
**A fabricated class could therefore exempt itself from the strict-mode policy
by choosing its own name.** Measured with `--jdk-only --dump-class-origins`:
`compatibility-stub 0` (the refusal working) and exactly one `generated-lambda`
row — `java/util/function/Predicate$$Lambda$And`, a stand-in minted by
`phases_late/streams.rs` and **created in strict mode purely because of the
infix**. Its sibling `Consumer$AndThen`, same species, no infix, was refused at
the door. The two failures looked unrelated in the field —
`NoClassDefFoundError` for one, `AbstractMethodError: … has no Code attribute`
for the other — which is why the shared cause went untraced.

The discriminator that replaced it is **structural, not lexical**: a genuine
`LambdaMetafactory`/`$ProxyN`/accessor class has bytes and is classified on the
real-bytes path; anything reaching `fabricate_class` has already failed
`get_loaded_class_id` **and** `find_class_bytes_delegated`, so it has no bytes
in any loader on any classpath entry.

And the comment that had been guarding the old arms was **false, not merely
stale**: *"Measured 2026-08-05 and again 2026-08-06: none of the three fires."*
True of those two probes, false of the VM — neither probe ever calls a
`Predicate` combinator. **A narrow probe reports its own reach, not the defect**,
and this is the instance where the wrong reading was frozen into a source
comment for a week.

### 4.5 Non-null is not the contract

Two defects survived this year behind `!= null` and count checks: three
fabricated enum constants passed `values().length == 3`, and `Thread$State`
passed non-null-and-named while `values()[0] == State.NEW` was false. This wave
re-checked the repairs rather than the dates on them (W7-93): the fixture now
asserts **identity** per declared constant, with the declared list taken from
the class's own `getDeclaredFields()` filtered by type, so nothing is named in
the test. Three of that lane's four checks confirmed the record; the fourth
found a live hole in the coverage the record claimed.

**Assert identity and equality.** A gate that measures a fraction, or a
presence, reads as good news.

## 6. What is NOT done, ranked

1. **Nothing is built.** `cargo check --workspace --all-targets`, then the
   suite in both arms with `TIMEOUT=420`. Until then no fix in §1 has any
   evidence behind it beyond a lane's reading.
2. **No corpus has been run under `--jdk-only`.** The driver exists, six
   `corpora.d` definitions exist (`h2`, `tomcat`, `spring-framework`,
   `commons-math`, `bc-java`, `hibernate`), and exactly one dry run happened
   against a stale binary. `hibernate` is **blocked** by design — 183 of 241
   classpath entries are evicted gradle-cache jars and the runner refuses
   loudly rather than composing a partial classpath. This is the single highest
   value run available, because Phase 2 cannot be adjudicated without it.
3. **The read-side alias census has never been run in anything scheduled.**
   `CRATONVM_DBG_LAYOUT_ALIAS` appears **zero** times under `regression-suite/`
   or `ci/`. Its one-off first census found **32 slot maps disagreeing with the
   real JDK layout and 23 agreeing**; nobody has re-run it. Note the
   distinction: the flag works (the first row a twelve-line probe produces is
   already an `undeclared`/`ClassId(0)` row) — the gap is scheduling.
4. **Phase 2 has one pilot lane and 226 measured shadow rows unaddressed.**
   The static picture is 4455 slots that shadow real bytecode (3956 `bridge` +
   499 `intrinsic`, of which the intrinsics are mostly legitimate
   acceleration); the *measured* figure on a real run is the 226. Retire by
   family and let the corpus adjudicate — 3956 differential tests is not a plan.
5. **`--features synthetic-jdk` mode is unexercised by any `RJdk*` vector.**
   The mode **requires** the feature build: a shipping binary refuses
   `--synthetic-jdk` at argument parsing with exit 1 and a correct explanation.
   So there is no "run it once" chore; it needs its own build of its own binary,
   from a clean `git archive HEAD` export rather than this working tree. A
   residual that lives only in that configuration **cannot** be adjudicated by
   any run of a shipping binary — and, symmetrically, cannot affect any shipped
   run, which is a legitimate reason to rank it low *if stated for that reason*.
6. **The Linux arms.** `native-io/src/process.rs`'s non-Windows arms have never
   been compiled by any lane that edited them; two ratchets and the kind map are
   keyed `25/linux` and both gate scripts exit 2 ("REFUSING") on this host.
7. **The eight new fixtures have never executed.** All eight are scheduled in
   `run.sh` (so `prune_missing` will not silently drop them — the files exist),
   but **seven of the eight are untracked**, and a source-witness gate reads the
   working tree,
   so an untracked scratch file in this worktree can trip unrelated tests.
   Commit them or move them out before running the gates.
8. **P3-A, the one deliberate red.** `RExceptions` fails in both arms because
   the JIT lowers `aastore` inline and never performs the JVMS covariance check
   (`cold=[java.lang.Integer] hot=[no-throw]`). The patch is written in full in
   W7-37-differential-throwable-and-vm.md Part 4 and is deliberately unapplied:
   it puts a Rust-boundary call on the hottest reference-store path in the VM.

## 7. Ratchets, baselines, and the predictions to check

**The standing rule, and it is not negotiable: never freeze a number you cannot

## 8. Inconsistencies between the evidence documents

Found while writing this handoff. They are recorded rather than smoothed,
because each is a number a later reader would otherwise inherit.

### 8.1 `RJdkLogging`'s expected byte count is quoted three ways

HANDOFF-20260812 §1 says HotSpot prints **179** and "the row should read 179 and
go green". Its own §2c then says the number is a hazard and **the fixture
asserts no such thing**. RETIREMENT-20260812B §1.8 **measured** HotSpot 177 and
the fixed CratonVM 177 in the same session, and says explicitly that *"a lane
that had pinned 179 would have read this run as a failure"* — because the model
is `2M + 2H + 167` and at that hour the 12-hour field `H` is one digit on both
VMs. The designed witness is `defaultZoneRawOffsetMs` (`0 → -10800000`), not the
byte count. **Do not quote 175, 177 or 179.**

### 8.2 `VM_MINTED_STAND_IN_RECEIVERS` has 8 entries, not 9 — and the source says 9

P1-BASELINE-20260812.md §P1-D writes "49 `NO_IMAGE_JDK_RECEIVERS` plus **9**
`VM_MINTED_STAND_IN_RECEIVERS`" and then totals them as **57 candidates**.
STUB-CENSUS-20260812.md §2.3 writes **8**. Counted in the tree today:
`NO_IMAGE_JDK_RECEIVERS` **49**, `VM_MINTED_STAND_IN_RECEIVERS` **8**,
`VM_SERVICE_RECEIVERS` **9**. So the census is right, the total 57 is right
(49+8), and P1-BASELINE's "9" is the `VM_SERVICE_RECEIVERS` count borrowed by
mistake. **The likely source of the error is the tree itself**: the doc comment
on `receiver_declared_by_no_supported_image` in
`native-api/src/no_image_receiver.rs` says "Linear scans over a 49- and a
9-entry" list. See NOMINATIONS.

### 8.3 The roadmap's §1 body still says three families

`docs/feature-designs/jdk-only-completion-roadmap.md` opens by pointing at
P1-BASELINE for "**nine** families, not §1's original three", and then §1 is
still headed *"One defect shape, three reachable instances"* with a three-row
table. Two more §1 claims are superseded and not marked: the cross-cutting
"under-reports the blocker set by half — 13 of 27" was corrected by
P1-BASELINE to **every boot refusal is reported and every runtime refusal is
silent**, and §4's P4-B still reads *"run `--synthetic-jdk` MODE once — it has
never been executed, ever"*, which P4B-SYNTHETIC-JDK-MODE-20260812.md corrects in
its own opening banner. (Another lane was editing that roadmap while this was
written; check before re-filing.)

### 8.4 27 vs 19 fabricated classes — not a contradiction, but it reads as one

APP-READINESS §5 reports **27 distinct compatibility classes** across six real
workloads in Compatible mode. JDK-ONLY-REPORT-CENSUS reports **19** on one
ordinary program. Different workloads, both correct. Anyone quoting either must
say which run it came from — the rule HANDOFF-20260812 §1 already states as
*quote the run, not the table*.

### 8.5 The oracle is labelled "Adoptium" at a Microsoft path

RETIREMENT-20260812B's instrument note reads "HotSpot **Adoptium** 25.0.3.9 at
`C:/Program Files/Microsoft/jdk-25.0.3.9-hotspot`". The path is the correct one;
the vendor label is the exact error HANDOFF-20260812's header was written to
kill, because copying the Adoptium *path* silently measures the host default JDK
instead of the image, and that inverted a per-mode verdict once already.
Cosmetic here, load-bearing if copied.

### 8.6 The census's own reproduce block will silently produce nothing

JDK-ONLY-REPORT-CENSUS's "Reproduce" section names the flag-order trap but not
the other two ways to get no file (Windows-shaped path; `System.exit`), both of
which are recorded in APP-READINESS §2. All three belong in one place — §2 above
is that place.

## 9. What carries forward from HANDOFF-20260812 unchanged

Do not re-derive these; that document is still the reference for them.

* **§1's host row.** Microsoft OpenJDK 25.0.3.9 at
  `C:/Program Files/Microsoft/jdk-25.0.3.9-hotspot`. `TIMEOUT=420` is not
  optional. `RBlockingQueue` is a suspected flake, not a regression.
* **§2, registration semantics.** `register()` is last-write-wins and
  `NativeKind` is **ambient**, set by `set_category`/`with_category` around a
  block. Nine lanes shipped or nearly shipped an inert fix on this. **Do not
  settle registrar order by indentation** — four lanes were burned brace-scanning
  a 24k-line file.
* **§2b.** `probes/` is **never** run by `run.sh` at any `SUITE=` value. A record
  whose only evidence is a probe cannot be discharged by a suite run, however
  green. **Put the assertion in a scheduled fixture, or the record cannot
  close.** Corollary found by the retirement pass: `close-strict.log` and
  `close-compat.log` carry `PASS`/`FAIL` and **no check counts**, so no record
  whose falsifier is `PASS X (N checks)` is discharged by them.
* **§2c**, the stale-row table, and the standing bookkeeping finding: a
  reconciliation over 62 records found **30 status lines materially wrong and
  all 30 overstated how much was open. Zero went the other way.** If you land a
  hand-off patch, edit the originating record in the same commit.
* **§5's traps**: feature ≠ mode; a slot count cannot identify a layout;
  `report_layout_alias` sees allocation width only; `cargo check --all-targets`
  runs no tests and `vm/src/vm/tests.rs` is synthetic-jdk-ONLY; any `CRATONVM_*`
  name needs four edits or `cargo test -p cratonvm-types` goes red; cite
  internal docs prefix-less and as plain text, never a markdown link.
* **§6's orchestration lessons**: check `BUILD_RC` explicitly and compare the
  binary's mtime against `git log -1`; do not mutate the tree while a
  measurement runs, and have agents pin a private copy of the binary; never
  `git add -A` in the main worktree; do not union prose conflicts mechanically.
* **§7's species** — a test that passes on the path where the fix does not
  matter. Four live instances there; §4.4 above is the fifth, and the first
  where the wrong reading had been frozen into a source comment.
