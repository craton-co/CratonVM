**Status:** MEASURED. Nothing closed, deliberately. Two rows have far stronger
evidence than recorded; one residual defect named exactly.
**Provenance:** `--jdk-only --jdk-only-report` over `RJdkStrict` (365 checks),
CratonVM `C:/craton/target-nolto`, 2026-08-19, Temurin 25.0.3+9.

## 0. The report nobody had read

`--jdk-only-report <FILE>` emits a structured census of a strict run. Three P0
rows are about exactly what it counts, and none of them cites it. This is the
same shape as `G82-1` (a row waiting on a command) and `G83-1` (a cited test
nobody ran): **the instrument exists and the rows are argued without it.**

## 1. The Synthetic-class-fallback row is in far better shape than recorded

Its required resolution: *"Under `JdkOnly`, return the specification-appropriate
`ClassNotFoundException`/`NoClassDefFoundError` and record
`CompatibilityClassRequested`. Never fabricate a non-array class."*

Measured, all three halves:

* **the errors** — `RJdkStrict.noFabricatedEnterpriseClasses()` already probes
  every enterprise prefix through BOTH `Class.forName` and
  `ClassLoader.loadClass` and requires `ClassNotFoundException` /
  `NoClassDefFoundError`. It passes strict;
* **the recording** — `compatibility-class-requested` violations carry class,
  initiating loader, requester `file:line`, and reason;
* **never fabricate** — `compatibility_classes: 0`.

And the refusal looks CATEGORICAL rather than prefix-gated, which the row asks
for and doubts: the single request in the whole run is
`cratonvm/stream/LazyOp` — a CratonVM-internal name matching no enterprise
prefix — and it was refused like anything else.

## 2. Why I did not close it anyway

Because refusing correctly and working correctly are not the same claim, and
this row is one where they come apart.

That single refusal is `ensure_synthetic_class` called from
`native-collections/src/lib.rs:21683` with *"no class file on any classpath
entry"*. The refusal is right. But the caller still did not get its receiver,
and the in-tree warning says what follows: *"the failure will surface later, at
that caller's own call site and usually naming a different class."*

So the policy is enforced and something in the stream implementation is
silently degraded by it. Closing on "the policy refuses correctly" would be
literally true and substantively misleading — the exact failure mode I have hit
twice in this session (`G83-1` §2, where a strict count of zero turned out to
be a drop rather than a resolution). **One residual, precisely named, is worth
more than a closure that has to be walked back.**

## 3. The two numbers nobody is counting

**`interpreter_shadow_unenforced: 77`** and **`native-shadows-bytecode: 104`.**
These are the *Native-first dispatch* and *Duplicate dispatch implementations*
rows, quantified, in a single ordinary run — 104 places where a native shadows
real bytecode and 77 where the shadow went unenforced. Those rows currently
argue from source reading and hand-maintained allowlists. They have a counter.

**`synthetic-native-registered: 1350`** matches the registry dump's 1330
`SyntheticStub` registrations (`G83-1`) to within the difference between a
`RJdkStrict` run and an `RJdkHello` one — two independent instruments agreeing,
which is worth knowing given `G83-1` found the ratchet's published `157`
matches neither.

## 4. NOMINATIONS

**N1 — `cratonvm/stream/LazyOp` has no class file.** One VM-internal class,
requested by `native-collections/src/lib.rs:21683`, refused under strict mode
every run. Either it should exist as real generated bytes (closure rule 4) or
that call site should not need it. It is the only compatibility-class request
in a full `RJdkStrict` run, so it is a bounded, nameable piece of work.

**N2 — cite the report in the three rows it measures.** Native-first dispatch,
Duplicate dispatch and Residual synthetic native set all argue from source
while `--jdk-only-report` counts precisely what they are about. A row whose
evidence column contains a number nobody re-derives goes stale — this session
has now found three that did (`G79-1`, `G83-1`, and `Function.identity()`
described as `Bridge` when the dump says `synthetic-stub`).

**N3 — make the report part of the arms.** It costs one flag on an existing
run. `interpreter_shadow_unenforced` moving is exactly the signal the dispatch
rows need and currently lack, and unlike the stub ratchet it does not need a
frozen baseline to be informative.
