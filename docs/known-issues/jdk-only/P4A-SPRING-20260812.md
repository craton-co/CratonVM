## 3. The corpus definition could not run a single Spring test — three defects

`regression-suite/corpus/corpora.d/spring-framework.sh` was marked
`CORPUS_CONFIDENCE=verified`. Its composed classpath failed **on HotSpot**, for
three independent reasons, all of which surface as linkage errors inside
`org.springframework.*`:

1. **No commons-logging** (§2).
2. **No test fixtures.** Spring's tests are written against per-module fixture
   classes (`org.springframework.beans.testfixture.beans.TestBean` and
   friends) which live in `build/classes/java/testFixtures` — a source set the
   file did not add — while it *also* excluded the `-test-fixtures.jar`
   variants on the theory that they drag in absent optional dependencies. That
   theory is wrong in the way that matters: the fixtures are the tests' own
   vocabulary, and a missing optional dependency inside one fixture only fails
   when that fixture is loaded, whereas their wholesale absence fails
   everything.
3. **Two JUnit majors on one classpath.** It globbed every jar under the local
   maven repo's `org/junit`, which on this host is jupiter 5.14.4 + platform
   1.12.1 **and** 1.14.4 + the vintage engine. Spring 7.1 is built against
   JUnit 6.1.0. Which of the three `junit-platform-commons` jars won the
   classpath order decided whether the launcher could see an engine at all.

**Fixed in this session** (that file is lane B2's to edit). Third-party jars
are now **pinned by exact coordinate** to what gradle resolved for this build,
resolved out of `~/.gradle/caches/modules-2/files-2.1`, and a missing pin
**REFUSES** the classpath rather than silently composing a shorter one — the
runner's own `cp_add` drops non-existent entries silently, and a silently
shorter classpath is precisely how a fixture defect gets filed as a VM bug.
Also dropped: `buildSrc/build/libs/buildSrc.jar` (gradle build logic) and
`build/libs/spring-7.1.0-SNAPSHOT.jar` (the root aggregate — it contains
exactly a manifest).

Post-fix: 111 classpath entries, 12502 characters, and Spring test classes run

## 4. THE FINDING: CratonVM never runs shutdown hooks

Every single Spring test class in the corpus run reports **DIVERGE**. All but
one of them diverge for the *same one reason* (the exception is §5c; §5d hid
behind a timeout row rather than a DIVERGE), and it is not Spring:

```
--- HotSpot ---
CORPUS-START SbRunner
SBRUNNER_RESULT tests=7 failed=0 aborted=0 skipped=0 containersFailed=0
CORPUS-END SbRunner completed=exit
--- CratonVM ---
CORPUS-START SbRunner
SBRUNNER_RESULT tests=7 failed=0 aborted=0 skipped=0 containersFailed=0
```

The test numbers match exactly. The missing line is `CORPUS-END`, which
`CorpusMain` prints **from a shutdown hook** because `SbRunner` ends in
`System.exit`. `CorpusMain`'s own header predicted this:

> *"if it came only from the hook then every corpus run would silently depend
> on shutdown-hook delivery, and a VM that never runs hooks would fail every
> workload for one shared reason."*

That is exactly what happened.

### 4a. Isolated, with the control arm

`HookProbe` registers two hooks and terminates by a selectable route.
`HOOK-RAN A` / `HOOK-RAN B` are printed by the hooks.

| route | HotSpot 25 | CratonVM `--jdk-only` | CratonVM `--real-jdk` |
|---|---|---|---|
| `main` returns normally | `BEFORE AFTER HOOK-RAN A HOOK-RAN B` rc=0 | `BEFORE AFTER` rc=0 | `BEFORE AFTER` rc=0 |
| `System.exit(0)` | `BEFORE HOOK-RAN B HOOK-RAN A` rc=0 | `BEFORE` rc=0 | `BEFORE` rc=0 |
| `System.exit(1)` | `BEFORE HOOK-RAN A HOOK-RAN B` rc=1 | `BEFORE` rc=1 | `BEFORE` rc=1 |
| `Runtime.halt(0)` | `BEFORE` rc=0 | `BEFORE` rc=0 | `BEFORE` rc=0 |
| uncaught throw | `BEFORE HOOK-RAN B HOOK-RAN A` rc=1 | `BEFORE` rc=1 | `BEFORE` rc=1 |

**Attribution: NOT a `--jdk-only` regression.** `--real-jdk` behaves
identically, so this is a pre-existing VM-wide gap that strict mode neither
introduced nor worsened. Exit codes are correct on every route; only hook
delivery is missing. `Runtime.halt` agrees with HotSpot by accident — hooks are
specified *not* to run there, and `native_shutdown_halt0`'s doc comment already
says so correctly.

### 4b. It is a known gap in code, and nowhere in `docs/known-issues/`

`native-builtins/src/lang_system.rs:50-53` says so in as many words:

> *"Known gap, unchanged by this registry: cratonvm does not yet RUN the
> registered hooks at VM shutdown."*

The registry itself is correct and careful — it roots each hook as a
JNI-global-ref handle so `WildFly`'s `BootstrapImpl$ShutdownHook` chain stays
reachable. What is missing is the *execution*. No file under
`docs/known-issues/` mentions shutdown hooks at all (`grep -rli 'shutdown hook'
docs/known-issues/` → nothing), so this record is the first.

**Why it matters beyond a marker line — measured, not argued.** §1c ran
Spring's own `AbstractApplicationContext.registerShutdownHook()` against a bean
with a `@PreDestroy` method. HotSpot prints `DESTROY-RAN` on both the
`System.exit` route and the normal-return route. CratonVM prints it on
neither. **A Spring context that registers a shutdown hook never destroys its
beans on this VM**, in either mode. Any Spring Boot application registers one
by default; logging frameworks flush from hooks; temp-file cleanup runs from
hooks.

### 5d. Second divergence: `Map.of(...) instanceof Collection` is TRUE — the `getClass()` alias vs the opcode

The `ObjectUtilsTests` re-run of §8 came back **not** as a timeout but as
`tests=140 failed=2` against HotSpot's `failed=0`. Both failures are the same
assertion:

```
ObjectUtilsTests$NullSafeConciseToStringTests.nullSafeConciseToStringForEmptyMaps
ObjectUtilsTests$NullSafeConciseToStringTests.nullSafeConciseToStringForNonEmptyMaps
  expected: "{...}"   but was: "[...]"
```

`ObjectUtils.nullSafeConciseToString` (spring-core `ObjectUtils.java:899-939`)
tests `obj instanceof Collection` *before* `obj instanceof Map` and returns
`COLLECTION = "[...]"`. So a `Map.of(...)` is answering `instanceof Collection`
**true**. It is a two-line assertion sitting on top of a VM defect.

Isolated to exactly two classes and three predicates:

| receiver | predicate | HotSpot | `--jdk-only` | `--real-jdk` |
|---|---|---|---|---|
| `Map.of(k,v)` / `Map.of(k,v,k2,v2)` | `instanceof Collection` | false | **true** | false |
| same | `instanceof Iterable` | false | **true** | false |
| same | `instanceof AbstractMap` | true | true | **false** |
| same | `(Collection) cast` | CCE | **succeeds** | CCE |
| same | `instanceof Map` / `Serializable` / `Runnable` / `Comparable` / `CharSequence` | — | correct | correct |
| `Map.entry`, `Set.of`, `List.of`, `HashMap`, `TreeMap`, `ConcurrentHashMap`, `Collections.emptyMap`, `String`, `Object` | all of the above | — | **all correct** | **all correct** |

**Both modes are wrong, in opposite directions**, on the same opcode:
`--jdk-only` over-accepts two interfaces the class does not implement;
`--real-jdk` under-accepts a superclass it does have. So this is not a
strict-mode regression — it is a shared defect with two faces, and a fix aimed
only at strict mode would leave `--real-jdk` answering `AbstractMap` = false.

**Reflection is right everywhere, and that is the diagnosis.** In all three
arms `getClass().getName()` is `ImmutableCollections$Map1`, the reported
superclass chain is `Map1 -> AbstractImmutableMap -> AbstractMap -> Object`,
`getInterfaces()` is `[Serializable]`, and `Collection.class.isInstance(o)` and
`Collection.class.isAssignableFrom(o.getClass())` both answer **false**
correctly. Only the `instanceof` / `checkcast` opcodes disagree — the
`reflective-native-and-its-opcode-are-twins-that-drift` shape.

The reason they can drift is `native-builtins/src/lib.rs:25385-25605`
(`GetClassDisplay::CollMap`): `Map.of(...)` does **not** produce a real
`java.util.ImmutableCollections$Map1`. It produces a VM-internal unmodifiable-map
receiver whose `getClass()` is **aliased**, per object and by size, to report
`Map1` or `MapN`. Reflection reads the aliased mirror and looks perfect; the
opcodes test the *actual stamped class*, whose hierarchy is whatever the VM
gave the internal type. `--real-jdk` answering `instanceof AbstractMap` = false
is the proof that the receiver is not a genuine `Map1`: no aliasing story
explains a missing link in a chain `getSuperclass()` itself reports.

The `checkcast` case is the dangerous one, because the wrong answer does not
surface where it is made:

```
(Collection) Map.of("k","v")       --jdk-only: succeeds
    then .iterator()               NoSuchMethodError:
                                   java.util.ImmutableCollections$Map1.iterator()Ljava/util/Iterator;
```

HotSpot raises `ClassCastException` at the cast. CratonVM lets the cast through
and fails later at a call site naming a different method — exactly the failure
shape the class-fabrication refusal warning describes.

### 6a. `java.version` does not follow `--java-home`

| property | HotSpot (`jdk-25.0.3.9-hotspot`) | CratonVM `--jdk-only` | CratonVM `--real-jdk` |
|---|---|---|---|
| `java.version` | `25.0.3` | `25.0.1` | `25.0.1` |

`java.vm.name` and `java.vendor` reporting CratonVM is correct and deliberate.
`java.version` / `java.runtime.version` are a different matter: they are

version-gates on `java.runtime.version` — and real ones do, for JDK patch-level
workarounds — gets an answer about a JDK that is not present. Both modes, so
not a strict-mode regression. Low severity, real fabrication.

```rust
/// Run every registered `Runtime.addShutdownHook` hook, once, before the
/// process is torn down. HotSpot starts each hook as its own thread and
/// joins them all; this runs each hook's `run()` inline on the exiting
/// thread instead. That is the smaller change and it fixes the observed
/// gap (hooks never firing at all); it is NOT equivalent for a hook that
/// blocks waiting on another hook, which is why the difference is stated
/// here rather than left to be discovered.
///
/// Idempotent: the list is drained, so a hook that itself calls
/// `System.exit` re-entrantly cannot run the set twice.
///
/// NOT called from `native_shutdown_halt0`: `Runtime.halt` is specified as
/// forcible termination and the JDK runs hooks from `Shutdown.exit`, which
/// halt bypasses.
fn run_shutdown_hooks(ctx: &mut dyn NativeContext) {
    let handles: Vec<usize> = {
        let mut hooks = SHUTDOWN_HOOKS.lock().unwrap_or_else(|e| e.into_inner());
        std::mem::take(&mut *hooks)
    };
    for handle in handles {
        let Some(hook) = ctx.resolve_global_root(handle) else {
            continue;
        };
        if let Err(e) = ctx.invoke_virtual(hook, "run", "()V", &[]) {
            tracing::warn!(
                target: "cratonvm::system_exit",
                "shutdown hook threw; continuing with the remaining hooks (HotSpot \
                 does the same: an exception out of a hook thread does not stop the \
                 others): {e:?}"
            );
        }
        ctx.remove_global_root(handle);
    }
}

type PreExitHook = fn(code: i32);
```

### N1b (equal priority) — the aliased unmodifiable-map receiver must satisfy the `instanceof` opcode too

§5d. No literal patch is offered here because the right fix is a design choice
this lane cannot make without building, and the two candidate shapes differ a
lot in cost:

* **Make the receiver real.** Stop stamping a VM-internal type for
  `Map.of(...)` and allocate the actual `java.util.ImmutableCollections$Map1` /
  `$MapN`. Removes the whole alias, and with it every future instance of this
  class of bug. Largest change.
* **Make the stamped type's hierarchy match what `getClass()` claims.** Give
  the internal unmodifiable-map class the supertype set of
  `AbstractImmutableMap` (`AbstractMap` → `Object`, interfaces `{Map,
  Serializable}`) and — the actual strict-mode bug — stop it inheriting
  `Collection`/`Iterable` from whatever collection-shaped internal base it
  currently sits under. Cheapest fix that closes both faces.
* **Route `instanceof`/`checkcast` through the same alias `getClass()` uses.**
  Superficially attractive, but it means every subtype test on every object
  pays the alias lookup, and it leaves the two answers derived from different
  code — the drift that produced this.

Whichever is chosen, the regression vector is four lines and belongs in the
suite, because *nothing currently covers it*: assert that `Map.of("k","v")`
is NOT `instanceof Collection`, is NOT `instanceof Iterable`, IS `instanceof
AbstractMap`, and that `(Collection) Map.of("k","v")` throws
`ClassCastException` — **in both modes**, since `--real-jdk` fails the third
and `--jdk-only` fails the first, second and fourth.

The same audit should be run over the other `GetClassDisplay` arms at
`native-builtins/src/lib.rs:25385-25605` — `CollList`, `CollSet`,
`CollSortedSet`, `CollNavigableSet`, `CollUnmod`. They alias by the same
mechanism. `Set.of` and `List.of` answered every predicate in the §5d probe
correctly, so those two arms are clean *for the predicates tested*; the
`Collections$Unmodifiable*` and `SortedSet`/`NavigableSet` arms were not
probed at all.

### N2 — `java.version` / `java.runtime.version` should follow `--java-home`

See §6a. They are hard-coded `25.0.1+8` while the loaded class library is
whatever `--java-home` points at (`25.0.3+9-LTS` here). `java.vm.name` and
`java.vendor` should stay `cratonvm` / `CratonVM` — those are honest. The right
source is the `release` file in the JDK home (`JAVA_VERSION=` /
`JAVA_RUNTIME_VERSION=`), which is already being read for other purposes on the
`--java-home` path. Both modes; low severity; a real fabrication that
version-gating applications will read.

### N3 — `ensure_wrapper` caches `SbRunner.class` across corpora with different classpaths

`regression-suite/corpus/run-corpus.sh:207-221` (`ensure_wrapper`, the
`$BUILD/$CORPUS_RUNNER_CLASS.class` staleness check at :216) recompiles the
runner only when
`CORPUS_RUNNER_SRC` is **newer than** the `.class`. `SbRunner` is shared by
several corpora whose composed classpaths pin **different JUnit majors**, so
the cached artefact is a class compiled against whichever corpus ran last. On
this host it was found holding a build against JUnit Platform 1.12 while the
spring corpus needs 6.1.0, and it had to be deleted by hand before the spring
batch would run. The cache key must include the corpus (or the composed
classpath), e.g. build into `$BUILD/$CORPUS/` rather than `$BUILD/`. Not
edited here — that file is not this lane's.

### N4 — `CORPUS-END` alone should not be able to fail every workload

`arm_key` (`run-corpus.sh:273`) compares `CORPUS-START`, `CORPUS-END`,
`CORPUS-THROW`, `CORPUS-NOMAIN` and `SBRUNNER_RESULT` as one opaque key, so a
single VM-wide gap (§4) turns *every* junit-kind row into DIVERGE and hides
whether the tests agreed. `CorpusMain`'s header already anticipated the failure
mode; the driver did not act on it. Suggestion: when the two arms' keys differ
**only** by a `CORPUS-END … completed=exit` line present on one side, report a
distinct verdict (`DIVERGE-TERMINATION`) rather than folding it in with a real
answer difference. This is a reporting change only — it must not make the row
green, because the hooks genuinely did not run.

## 8. Residuals — what was NOT done

* **Every measurement here was taken on a binary that predates two same-day
  fixes.** `/c/craton/jdkonly-wave2-target/release/cratonvm.exe` was built at
  20:18; commit `f0a472dcf` landed at 21:46 carrying both the ServiceLoader
  module-provider patch of §5c **and** a fix to `run-corpus.sh` for a working
  directory it computed and never used. Nothing in this document is a claim
  about dev tip. §5c in particular should be re-measured first.
* **`ObjectUtilsTests`' timeout WAS load — but the re-run found something
  else.** Run alone at a 420 s wall it completes in time and reports
  `tests=140 failed=2` against HotSpot's `failed=0`; that is §5d, and it is a
  real finding. The lesson is the one already on file: the first row was a
  wall-clock artefact of five concurrent CratonVM processes, and had it been
  reported as "CratonVM hangs on ObjectUtilsTests" the actual two-test
  divergence underneath would have been missed entirely. Its HotSpot arm in
  the solo run had not finished at the time of writing —
  `regression-suite/corpus/out/spring-framework-jdk-only-20260812-215547/` —
  but the HotSpot number is already known from the batch run (140/0) and the
  §5d probes take HotSpot directly.
* **§5d's `--real-jdk` face is not covered by any corpus row.** It was found
  by probe. `ObjectUtilsTests` under `--mode real-jdk` has not been run, and it
  is the obvious confirmation: the same two tests should fail there too, for
  the opposite reason.

  taken where they mattered — §4a (conclusive, direct) and §5b's two timeouts.

  every 25th class of the 785 that live in the five context modules. It is a

  identically to HotSpot across 23 probe stages, and 29 of 32 sampled test
