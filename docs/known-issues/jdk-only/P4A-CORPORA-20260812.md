## A. NEW DEFECT — `SimpleTimeZone(rawOffset, ID)` ignores `rawOffset`

### The contract

`java.util.SimpleTimeZone(int rawOffset, String ID)` takes the offset from
`rawOffset`. The `ID` is an **opaque label**: it is not looked up in the
timezone database, and it does not contribute an offset. So
`new SimpleTimeZone(0, "America/Buenos_Aires")` is **UTC that happens to be
named `America/Buenos_Aires`**.

### Measured, all three arms

`StzProbe`, four constructions and one parse. Host default zone is
`America/Buenos_Aires` (-03:00, no DST).

| construction | HotSpot 25 `getRawOffset()` | CratonVM `--jdk-only` | CratonVM `--real-jdk` |
|---|---|---|---|
| `new SimpleTimeZone(0, "America/Buenos_Aires")` | `0` | **`-10800000`** | **`-10800000`** |
| `new SimpleTimeZone(0, "Z")` | `0` | `0` | `0` |
| `new SimpleTimeZone(0, "GMT+05:00")` | `0` | **`18000000`** | **`18000000`** |
| `new SimpleTimeZone(18000000, "America/Buenos_Aires")` | `18000000` | **`-10800000`** | **`-10800000`** |

`getOffset(0L)` tracks `getRawOffset()` in every row, so this is not a
reporting-only defect — the zone genuinely behaves as the resolved zone.

**The fourth row is the diagnosis.** The caller passed `+5h` explicitly and
CratonVM answered `-3h`. `rawOffset` is not merely overridden on a tie, it is
**discarded entirely** whenever `ID` happens to resolve.

**The second row is why this survived so long.** `new SimpleTimeZone(0, "Z")`
is the common idiom, `"Z"` is not a resolvable zone ID, so the fallback lands
on `0` and the idiom is accidentally correct. Any test using only that spelling
reads green — including this lane's own first probe, which is why the first
`TimeZone` differential came back identical and nearly closed the
investigation.

**Both modes are affected**, so this is not a `--jdk-only` regression.

### How the corpus found it

`org.bouncycastle.asn1.test.AllTests` was the one class in this lane's whole
run whose `SBRUNNER_RESULT` counts genuinely disagreed:

```
HotSpot  : SBRUNNER_RESULT tests=20 failed=0
CratonVM : SBRUNNER_RESULT tests=20 failed=1
SBRUNNER_FAILURE_DETAIL testASN1
junit.framework.AssertionFailedError: GeneralizedTime: failed long date conversion test
```

`ASN1GeneralizedTime.getDate()` takes a local-time branch for inputs with no
zone suffix, and that branch ends:

```java
dateF.setTimeZone(new SimpleTimeZone(0, TimeZone.getDefault().getID()));
```

— i.e. "parse this at UTC", spelled with the default zone's *name*. On
CratonVM the name wins and the parse happens at -03:00.

Narrowed with `GtProbe` over the test's own 21 inputs. **The 16 inputs carrying
an explicit zone (`Z`, `-1000`, `+00`, `+1000`) agree exactly on both VMs. The
5 local-time inputs — indices 0, 4, 8, 12, 16 — are each off by exactly
`10800000` ms, the host UTC offset:**

```
GT 0  in=20020122122220        HotSpot epochMs=1011702140000   CratonVM epochMs=1011712940000
GT 4  in=20020122122220.1      HotSpot epochMs=1011702140100   CratonVM epochMs=1011712940100
GT 8  in=20020122122220.01     HotSpot epochMs=1011702140010   CratonVM epochMs=1011712940010
GT 12 in=20020122122220.001    HotSpot epochMs=1011702140001   CratonVM epochMs=1011712940001
GT 16 in=20020122122220.0001   HotSpot epochMs=1011702140000   CratonVM epochMs=1011712940000
```

BC's own `getTime()` string is byte-identical on both arms
(`20020122122220GMT-03:00`), so the ASN.1 text handling is fine; only the
`Date` is wrong.

### Why it matters beyond bc-java

The defect is silent, it is in the wrong direction by a full UTC offset, and it
is invisible on a UTC host — every one of these rows would read green in CI at
`Etc/UTC`, because the resolved offset and the passed `rawOffset` would both be
zero. It affects any caller that builds a fixed-offset zone with a descriptive
ID, which is the documented use of the two-argument constructor.

### NOMINATION 3

Not written as a patch: this lane did not locate the implementation, and
`SimpleTimeZone`'s constructor may be Java-side, natively shadowed, or both
(the `--real-jdk` arm is equally wrong, so a shared native is likely).

**Lead on the mechanism.** `RETIREMENT-20260812B.md:337` establishes that on
this host the named IANA id **does** resolve, via the
`getTimeZone(zoneID, false)` route rather than the `getSystemGMTOffsetID`
fallback. The symptom here is exactly what that route produces if the
two-argument `SimpleTimeZone` constructor is shadowed onto it: the `ID`
argument is looked up and the `rawOffset` argument is dropped on the floor.
The `"Z"` and default-zone rows are consistent with that reading — `"Z"` does
not resolve, so it falls back to `0` and looks correct. Start by asking whether
`SimpleTimeZone.<init>(ILjava/lang/String;)V` is registered as a native at all;
per the standing note on duplicate registrations, check **which** registration
wins before changing one.

The required behaviour is exact and testable:

* `new SimpleTimeZone(r, id).getRawOffset()` **must** be `r` for every `r` and
  every `id`, including ids that name real zones.
* `getOffset(...)` must derive from that `r` (plus only the DST rules supplied
  through the longer constructors), never from a lookup of `id`.
* `getID()` must return `id` verbatim — this half is already correct.

Suggested regression vector, in the style of `regression-suite/src/R*.java`:
assert all four rows of the table above, and **include the
`SimpleTimeZone(18000000, <a real zone id>)` row** — a vector built only from
`SimpleTimeZone(0, "Z")` and `SimpleTimeZone(0, "UTC")` passes today.

## B. SECOND DIVERGENCE — German locale time pattern and zone display name

`org.bouncycastle.i18n.test.AllTests`, `testGetEntry`. HotSpot `tests=5
failed=0`; CratonVM `tests=5 failed=1`:

```
junit.framework.ComparisonFailure:
  expected:<Es ist 13:12[ Uhr GMT] am 17.08.2006.>
  but was: <Es ist 13:12[:00 Greenwich Mean Time] am 17.08.2006.>
```

The date half (`am 17.08.2006`) and the hours/minutes are right. Two things are
wrong in the time half, and they are independent:

1. **The locale's time pattern.** German expects `HH:mm 'Uhr' z`; CratonVM
   produced `HH:mm:ss zzzz`. Both the seconds field and the literal `Uhr` are
   wrong, so this is the wrong *pattern* for the locale/style, not a formatting
   slip.
2. **The zone display name.** Expected the short form `GMT`; got the long form
   `Greenwich Mean Time`, **and in English inside an otherwise German string**.
   So the name is wrong in length and not localized.

This is adjacent to `W7-91-format-date-symbols-hardcoded-english.md` but is
**not** the same mechanism: W7-91 is about `Formatter`'s `%t`/`%T` name tables,
and this is `DateFormat`'s per-locale pattern and `TimeZone`'s display-name
lookup. It is recorded here as an application-level witness rather than a
diagnosis — **this lane did not isolate it to a specific JDK call**, and it
should get its own probe before anyone patches anything.

Note it is *not* the §A defect: `SimpleTimeZone` is not involved, and the two
failures are in different suites.

## 3. NOMINATION 2 — the shutdown-hook artefact is manufacturing divergence

Every `DIVERGE` in both corpora, after the §1 fix, has this shape:

```
--- HotSpot ---                                     --- CratonVM ---
CORPUS-START SbRunner                               CORPUS-START SbRunner
SBRUNNER_RESULT tests=5 failed=0 aborted=0 ...      SBRUNNER_RESULT tests=5 failed=0 aborted=0 ...
CORPUS-END SbRunner completed=exit                  (nothing)
```

Identical test counts. The whole difference is a missing `CORPUS-END`.

`CorpusMain.java:90-95` emits `CORPUS-END … completed=exit` from a
`Runtime.getRuntime().addShutdownHook(...)`. `SbRunner` calls `System.exit`, so
on HotSpot the hook fires and on CratonVM it does not.

Isolated to 15 lines of Java, no JUnit, no corpus (`HookProbe`: register a hook
printing `HOOK-RAN`, print `BEFORE-EXIT`, optionally `System.exit(7)`):

| arm | `System.exit(7)` | normal return |
|---|---|---|
| HotSpot 25 | `BEFORE-EXIT` **`HOOK-RAN`** rc=7 | `BEFORE-EXIT` `NORMAL-RETURN` **`HOOK-RAN`** rc=0 |
| CratonVM `--jdk-only` | `BEFORE-EXIT` — rc=7 | `BEFORE-EXIT` `NORMAL-RETURN` — rc=0 |
| CratonVM `--real-jdk` | `BEFORE-EXIT` — rc=7 | — |

The hook **never runs, on either exit path, in either mode**. Registration
raises nothing. Exit codes are correct. This is the fabricated-success shape:
`addShutdownHook` accepts the registration and silently drops it.

**This is not new and is not a `--jdk-only` regression** — the `--real-jdk`
control arm is identical, and `W7-27-thread-exit-java-cleanup.md` already
records it verbatim: *"Adjacent and NOT to be bundled: `Runtime.addShutdownHook`
hooks are registered and never run."*

**What is new is the consequence.** `CorpusMain` chose a shutdown hook to
express its terminal marker, so *every* `junit`-kind corpus class whose runner
calls `System.exit` diverges for this one reason, on every corpus in the suite,
regardless of what the workload did. It converts a clean sweep into
`DIVERGE=9`, and it will hide a real divergence inside the noise the first time
one appears.

### NOMINATION 2 (`regression-suite/corpus/run-corpus.sh`) — APPLIED 2026-08-12, IN A CORRECTED FORM

> **THE PATCH BELOW IS INSUFFICIENT AND MUST NOT BE APPLIED AS WRITTEN. It is
> kept only so this record shows what was proposed and why it was wrong.**
>
> Run against the real logs it still diverges: stripping the ` completed=`
> qualifier leaves a bare `CORPUS-END SbRunner` line present on HotSpot and
> absent on CratonVM, so the row is still `DIVERGE`. It also erases the `true`
> vs `exit` distinction, which is the only signal separating a bytecode-sourced
> marker from a hook-sourced one — i.e. it destroys the evidence while failing
> to fix the symptom. A form of it did land briefly
> (`sed 's/ completed=[A-Za-z]*//'`) and was measurably ineffective.
>
> What is in `run-corpus.sh` today deletes ONLY the hook-sourced line
> (`sed '/^CORPUS-END .* completed=exit$/d'`), keeps `completed=true` in the
> key, compares exit statuses when the keys match, and reports the hook
> asymmetry as a note on the row. Measured effect: **62 of the 75 stored
> `DIVERGE` rows are the artefact** (C8), independently reproduced row-by-row by
> lane C17 in §R below. See `C8-CORPUS-HARNESS-DEFECTS-20260812.md` §2.1.

The comparison key must not rest on whether a shutdown hook fired. In
`arm_key`, drop the `completed=` qualifier so `completed=exit` and a hook that
never ran do not read as different answers. Replace literally:

```sh
  grep -aE '^(CORPUS-START|CORPUS-END|CORPUS-THROW|CORPUS-NOMAIN|SBRUNNER_RESULT) ' "$1" 2>/dev/null \
    | sed 's/\x1b\[[0-9;]*m//g'
```

with:

```sh
  # `CORPUS-END`'s completed= qualifier is NOT part of the key. It is emitted
  # by a shutdown hook, and CratonVM registers hooks without ever running them
  # (W7-27) -- so keying on it made every junit-kind class DIVERGE on that one
  # unrelated defect while its SBRUNNER_RESULT counts matched HotSpot exactly
  # (measured 2026-08-12: bc-java 9/9, commons-math 4/4). The test counts are
  # the answer; whether the hook fired is not.
  grep -aE '^(CORPUS-START|CORPUS-END|CORPUS-THROW|CORPUS-NOMAIN|SBRUNNER_RESULT) ' "$1" 2>/dev/null \
    | sed 's/\x1b\[[0-9;]*m//g' \
    | sed 's/^\(CORPUS-END .*\) completed=.*$/\1/'
```

The second half alone is sufficient and is the one to land if only one is
taken. **Do not** simply drop `CORPUS-END` from the key: its presence still
distinguishes "reached a terminal marker" from "died silently".

```sh

```

with:

```sh

  # class whose dependencies are missing. Nothing was discovered, so there is
  # no ground truth. classify_arm calls this RAN, which is correct for a
  # workload that throws and wrong for the harness runner that throws.
  #
  # Measured 2026-08-12 (B7), both directions of the resulting error:

  #     zero tests ran on either VM.
  #   * AccurateMathTest / DfpTest, NoClassDefFoundError on the evicted
  #     commons-rng: HotSpot discovered nothing while CratonVM ran 70 and 78
  #     tests -- scored DIVERGE against an oracle that had failed.
  if [ "$CORPUS_KIND" = junit ] \
     && grep -qa '^CORPUS-THROW ' "$logf" 2>/dev/null \
     && ! grep -qa '^SBRUNNER_RESULT ' "$logf" 2>/dev/null; then
    echo "the JUnit launcher threw during discovery and no SBRUNNER_RESULT was produced -- nothing was discovered, so there is no ground truth"
    return 0
  fi
  line="$(grep -a '^SBRUNNER_RESULT ' "$logf" 2>/dev/null | tail -1)"
```

wrong, and would have scored a full sweep of `AGREE` having adjudicated
nothing — the exact trap `README.md` was written to refuse. The pass/fail text
exists only on stdout, which `arm_key` excludes on purpose.
