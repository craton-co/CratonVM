# P4A — a servlet container serving HTTPS, and four defects found getting there

**2026-08-12, lane B3. Embedded Tomcat 12 serves HTTPS under `--jdk-only`.**
That is the roadmap's second acceptance criterion and it had never been
attempted: until today `SSLSocket.get{Input,Output}Stream()` returned
`javax/net/ssl/SSLSocket{Input,Output}Stream`, classes no real JDK declares, so
the handshake succeeded and the first stream access threw (see
`W7-61-sslengine-layout-and-tls-blocking.md`, which fixed it).

Everything below was **run**, on this host, this session, against
`/c/craton/jdkonly-wave2-target/release/cratonvm.exe`, with HotSpot 25
(`C:/Program Files/Microsoft/jdk-25.0.3.9-hotspot`) as the oracle on the
identical program. Where a defect is claimed, the `--real-jdk` control was
taken as well; two of the three VM defects reproduce in **both** modes and are
therefore **not** strict-mode regressions.

## 2. THE HEADLINE — it serves HTTPS

Same embedded server with `SSLEnabled=true`, `scheme=https`, one
`SSLHostConfig` + `SSLHostConfigCertificate` pointing at an **RSA** PKCS12
keystore (`CN=localhost`, SAN `localhost`/`127.0.0.1`, 2048-bit, SHA384withRSA).
RSA deliberately: JDK-generated **EC** identities are a separate open defect
(PKCS#8 without the `publicKey [1]` field) and mixing them would confound this.

Tomcat's default `SSLImplementation` is JSSE (`SSLImplementation.java:57`), so
the server side runs the JDK **`SSLEngine`** through `SecureNioChannel` — a
much larger surface than the `SSLSocket` path W7-61 repaired.

**CratonVM `--jdk-only`, reproduced twice, identical both times:**

```
MARKER sslhostconfig = attached
MARKER started.port  = 62096
MARKER client.ctx    = TLS
MARKER get.status    = 200
MARKER get.body      = HELLO-GET:/hello:secure=true:scheme=https
MARKER post.status   = 200
MARKER post.body     = HELLO-POST:PING-TLS
MARKER stopped = ok    MARKER destroyed = ok    MARKER RESULT = PASS
```

`secure=true` and `scheme=https` are the servlet's own view of the request, so
the container — not just the socket — knows it is on TLS. HotSpot is PASS on
the identical program and additionally reports
`get.cipher = TLS_AES_256_GCM_SHA384`.

**The handshake is genuinely verified, not permissive.** Arm C of the trust
matrix below points the same client at the same self-signed server with
*default* trust, and CratonVM rejects it
(`SSLHandshakeException: invalid peer certificate: UnknownIssuer`), as HotSpot
does. So the 200s above were obtained across a real, certificate-verified TLS
session.

The one divergence in this transcript — `get.cipher` — is defect 3.

## 3. DEFECT: the `https:` URL carrier is the ABSTRACT `HttpsURLConnection`

`new URL("https://…").openConnection()` returns an instance of
**`javax.net.ssl.HttpsURLConnection` itself**, which is `abstract`. HotSpot
returns `sun.net.www.protocol.https.HttpsURLConnectionImpl`.

```
                        CratonVM (both modes)                 HotSpot 25
conn.class              javax.net.ssl.HttpsURLConnection      sun.net.www.protocol.https.HttpsURLConnectionImpl
getCipherSuite()        AbstractMethodError                   TLS_AES_256_GCM_SHA384
getServerCertificates() AbstractMethodError                   1
getSSLSession()         Optional.empty()  (silent)            (present)
```

```
java.lang.AbstractMethodError: method javax/net/ssl/HttpsURLConnection.getCipherSuite()Ljava/lang/String; has no Code attribute
java.lang.AbstractMethodError: method javax/net/ssl/HttpsURLConnection.getServerCertificates()[Ljava/security/cert/Certificate; has no Code attribute
```

`javap javax.net.ssl.HttpsURLConnection` on this host confirms
`getCipherSuite()`, `getLocalCertificates()` and `getServerCertificates()` are
**declared abstract**. So this is the *abstract-declaration* shape, **not** a
fabricated receiver — `javax/net/ssl/HttpsURLConnection` is a real JDK class.
The request itself works; only session introspection is unreachable.

**`getSSLSession()` is the more dangerous half.** It is a *concrete* method on
the abstract base whose body returns `Optional.empty()`. It therefore does not
throw — it silently answers "this connection has no TLS session" on a
connection that has one. A caller that branches on it takes the wrong branch
with no diagnostic.

**Control:** identical under `--real-jdk`. **Pre-existing, not strict mode.**

**Site — `native-builtins/src/net_phase_e.rs:8683-8692`:**

```rust
            let carrier = if ext.starts_with("jar:") {
                "java/net/JarURLConnection"
            } else if ext.starts_with("https:") {
                // Spring's SkipSslVerificationHttpRequestFactory first tests
                // the carrier with `instanceof HttpsURLConnection`.  Returning
                // the plain HTTP base here skipped that whole configuration
                // branch, so its permissive TrustManager was never created.
                "javax/net/ssl/HttpsURLConnection"
            } else {
```

The comment records a real earlier fix and must not be undone. But the concrete
subclass satisfies that `instanceof` too: `javap` confirms
`sun.net.www.protocol.https.HttpsURLConnectionImpl extends javax.net.ssl.HttpsURLConnection`,
and it is **already registered with the same natives** —
`native-builtins/src/http_url_connection.rs:4289`:

```rust
    register_one(r, "sun/net/www/protocol/https/HttpsURLConnectionImpl");
```

See NOMINATION 1.

## 4. DEFECT: an `SSLContext`'s trust verdict depends on unrelated `init` order

The same `SSLContext`, built from the same `TrustManagerFactory`, over the same
keystore, against the same peer, **accepts or rejects depending only on where an
unrelated `SSLContext.init` sits in the program**. JSSE trust material is
per-instance; this is process-global state.

Minimal repro — build a trusting context and a default-trust context, vary only
their order, then connect with the **trusting** one:

| order of the two `init` calls | HotSpot 25 | CratonVM `--jdk-only` | CratonVM `--real-jdk` |
|---|---|---|---|
| `defaulting.init` then `trusting.init` | ACCEPTED | **REJECTED** | **REJECTED** |
| `trusting.init` then `defaulting.init` | ACCEPTED | ACCEPTED | ACCEPTED |

The rejection is
`java.io.IOException: TLS connect: handshake process: invalid peer certificate: UnknownIssuer`.
Deterministic: 3/3 each way.

A second, independent symptom of the same class of bug, with the programmatic
`TrustManager` removed entirely:

| client trust configuration | HotSpot 25 | CratonVM `--jdk-only` |
|---|---|---|
| programmatic `TrustManagerFactory` | ACCEPTED | ACCEPTED |
| `-Djavax.net.ssl.trustStore` + `…trustStorePassword` + `…trustStoreType` | ACCEPTED | **REJECTED** |

**`javax.net.ssl.trustStore` — the standard way essentially every Java
deployment configures trust, and the way Tomcat's own TLS tests configure their
client — is not consulted.**

**Control:** identical under `--real-jdk`. **Pre-existing, not strict mode.**

**The mechanism is NOT pinned.** Four datapoints (two programs × two orders) are
consistent with a single process-global trust slot, but no single rule of the
form "first init wins" / "last init wins" fits all four, so this record does
**not** assert one. What is established is the observable: the verdict is
order-dependent and HotSpot's is not. Whoever fixes it should locate the global
first rather than adopt a hypothesis from this record — a wrong hypothesis here
is a known failure mode of these documents.

## 5. DEFECT: `Runtime.addShutdownHook` never runs, in any mode

```java
Runtime.getRuntime().addShutdownHook(new Thread(() -> System.out.println("HOOK-RAN")));
```

| exit path | HotSpot 25 | CratonVM `--jdk-only` | CratonVM `--real-jdk` |
|---|---|---|---|
| `System.exit(0)` | HOOK-RAN | *(nothing)* | *(nothing)* |
| `main` returns | HOOK-RAN | *(nothing)* | *(nothing)* |
| `System.exit(7)` | HOOK-RAN | *(nothing)* | — |

**Control:** identical under `--real-jdk`. **Pre-existing and VM-wide, not
strict mode.** This matters for a servlet container specifically: Tomcat and
`Catalina` register a shutdown hook to stop the server gracefully, so a
CratonVM-hosted Tomcat killed by `System.exit` never runs its shutdown path.

It is also why **every** corpus row below scored DIVERGE — see section 7.

## 6. HARNESS: the corpus classpath was incoherent (FIXED in `corpora.d/tomcat.sh`)

The first Tomcat corpus run returned **12/12 AGREE**. It was worth nothing.
`cp_add_jars_r "$m2/org/junit/platform"` sweeps the group recursively and put
junit-platform **1.12.1 and 1.14.4 on the classpath simultaneously**. JUnit
detects that itself and aborts in *discovery*, before any test runs, on **both**
arms:

```
JUnitException: Some JUnit versions on the classpath are not upward compatible
  - org.junit.jupiter.engine:   5.14.4
  - org.junit.platform.commons: 1.12.1
Caused by: java.lang.NoSuchMethodError:
  'org.junit.platform.engine.OutputDirectoryCreator
   org.junit.platform.engine.EngineDiscoveryRequest.getOutputDirectoryCreator()'
```

Twelve identical crashes on each side, `rc=1` on both, ~2 s each — scored as
twelve AGREEs. An agreeing failure is not an oracle.

Second problem behind the first: **Tomcat 12's tests are JUnit *4* sources**
(`org.junit.Test`, `org.junit.Assume`, `@RunWith(Parameterized.class)`) run by
the vintage engine, and `junit:junit` was **not on the classpath at all**.
Pinning the platform version alone would still have discovered zero tests.

Both fixed in `corpus_classpath` via a new `cp_add_newest_artifact` helper that
takes the highest version *per artifact* (which also keeps `junit` 4.13.2 and
excludes the cached 3.8.1).

**Also fixed — `corpus_discover` over-reported by 19%.** It globs `Test*.class`,
which matches Tomcat's `Tester*` **fixtures** (support classes, a fake OCSP
responder, recording valves) — 152 of 805 names. Tomcat's own build excludes
them explicitly (`build.xml:2276`, `<exclude name="**/Tester*.java" />`).
Discovery is now 653 real test classes, `Tester*` = 0, `TestSsl` retained.

## 8. HARNESS: `run-corpus.sh` computes the working directory and discards it

`regression-suite/corpus/run-corpus.sh:426`:

```sh
  local wd; wd="$(corpus_workdir "$CORPUS_ROOT")"
```

`grep -n '\$wd\|wd='` over the whole file returns **that line and nothing
else**. `wd` is assigned once and never referenced; neither arm is launched from
it. The `corpus_workdir` hook is defined (line 136), documented, called — and
its result thrown away, so both arms inherit whatever cwd the caller had.

Every corpus whose tests open a path relative to its source root is silently
mis-scored. For Tomcat that is most of the TLS suite: the five classes whose
failures name `user1.jks` or a sibling fixture — `TestSsl` (21), `TestClientCert`
(18), `TestCustomSslTrustManager` (9), `TestCustomSsl` (1),
`TestSslHandshakeFailure` (1) — account for **50 of the 69 non-passing tests**
in the table above, and they fail on **both** VMs. See NOMINATION 2.
`run-corpus.sh` is outside this lane's edit scope.

**Demonstrated, not argued.** Because `wd` is unused, the arms inherit the
*caller's* cwd — so re-running the identical command from `C:/craton/apps/tomcat`
is both the workaround and the proof. `TestSsl` on the **HotSpot oracle**:

| | `user1.jks` errors | tests | failed | aborted |
|---|---|---|---|---|
| run from repo root (as the runner does today) | many | 21 | **7** | 14 |
| run from the Tomcat root | **0** | 21 | **1** | 14 |

**Six tests that HotSpot actually passes were being scored as failures**, and
Tomcat now loads its real fixtures — the log shows
`configured from keystore [C:\craton\apps\tomcat\test\org\apache\tomcat\util\net\localhost-rsa.jks]`
and a TLS virtual host `[foobar]` for the SNI test. The 14 aborts are `Assume`
skips for connector variants this host lacks, which is legitimate.

Four TLS classes re-run from the Tomcat root, `--timeout 400`. **`user1.jks`
errors: 0 across all eight logs.** This is the only Tomcat TLS measurement in
this record taken against fixtures that actually resolve, and it supersedes
those rows of the section 7 table.

```

```

| class | HotSpot | CratonVM `--jdk-only` | |
|---|---|---|---|
| `TestSslHandshakeFailure` | tests=1 failed=0 | tests=1 failed=0 | genuine agreement |
| `TestCustomSsl` | tests=1 failed=0 | tests=1 failed=0, **then never exited** | CV-TIMEOUT |
| `TestCustomSslTrustManager` | tests=9 **failed=1** aborted=6 | tests=9 **failed=0** aborted=6 | CV passes what HotSpot fails |
| `TestSsl` | tests=21 failed=1 aborted=14 | **did not complete** | CV-TIMEOUT |

Three things here deserve separate attention.

**(i) `TestCustomSsl` — the tests passed and the VM did not exit.** The CV arm
printed `SBRUNNER_RESULT tests=1 failed=0`, then logged Tomcat's own
`LifecycleBase stop` lines, wrote nothing after 21:27:17, and was killed at
400 s (~21:30). So this is **not** a failing test and **not** a stalled test —
it is a **hang at process exit after a clean pass**, roughly three minutes of
it. Combined with defect 5 (no shutdown hook ever runs), the suspicion is
non-daemon threads that are never reaped, but that is a suspicion, not a
diagnosis.

**(ii) `TestCustomSslTrustManager` — CratonVM passes a test HotSpot fails.**
That is the *wrong direction* for a TLS trust test and should not be read as
good news. The failing case is:

```
JUnit Vintage:TestCustomSslTrustManager:[JSSE]:testCustomTrustManagerNone[JSSE]
 => javax.net.ssl.SSLHandshakeException: Remote host terminated the handshake
    java.base/sun.security.ssl.SSLSocketImpl.startHandshake(SSLSocketImpl.java:455)
    java.base/sun.net.www.protocol.https.HttpsClient.afterConnect(HttpsClient.java:483)
    java.base/sun.net.www.protocol.https.HttpsURLConnectionImpl.connect(HttpsURLConnectionImpl.java:141)
    org.apache.catalina.startup.TomcatBaseTest.methodUrl(TomcatBaseTest.java:708)
```

Note the HotSpot stack runs through `sun.net.www.protocol.https` — **the exact
path CratonVM does not take**, per defect 3. So the two arms are not executing
the same client code, and CratonVM's "pass" may simply be a client that never
applied the constraint the test is about. **Unresolved. Do not score this as a
CratonVM win**; it needs a deliberate probe of what the `None` trust-manager
case is supposed to enforce.

**(iii) `TestSsl` — did not complete**: 2 of 21 test cases in 400 s, then killed
by `timeout`, against a HotSpot arm that finished all 21 in ~143 s.

Read this carefully. It is **not** scored as a VM defect here, and it is not a
throughput claim — wall clock on this host is non-metric by this project's own
rule. What is on the record is *completion*: the oracle completes and CratonVM
does not, within the same budget.

Nor is it obviously plain slowness. The arm produced no crash markers, no
register dump and no `CRATONVM_SYMBOLIZE=` line, but its log **stops dead at
21:16:24 in the middle of `testSni[JSSE]`**, right after
`ContextConfig getDefaultWebXmlFragment`, and the process was not killed until
~21:18:08 — roughly **104 seconds of complete silence** mid-test.

The runner reached the same verdict independently:

```
org.apache.tomcat.util.net.TestSsl   CV-TIMEOUT   cv=TIMEOUT(rc=124) 404391ms   hs=RAN 136641ms
```

`testSni` opens several TLS connections in sequence. That is the shape
`docs/feature-designs/jdk-only-tls-async-close.md` is about, and this record
does **not** propose a fix: the obvious readiness gate is unsound there, because
socket readiness is not stream readiness and `rustls`' `wants_read()` is false
while decrypted plaintext is still buffered. **This is reported against that
design as a candidate live reproducer** — the first one from a real
application — and it needs a stack, not a larger `--timeout`.

**File:** `native-builtins/src/net_phase_e.rs`, ~line 8683.

                // Spring's SkipSslVerificationHttpRequestFactory first tests

## Residuals

1. **The `SSLContext` trust global (defect 4) is unlocated.** It is the highest
   remaining risk here: it is silent, it is order-dependent, and it makes a
   security decision.
2. **`-Djavax.net.ssl.trustStore` being ignored blocks Tomcat's TLS suite** from
   ever being a real measurement, independently of defect 8.
3. **HTTP/2 and WebSocket over TLS untried.** This lane served HTTP/1.1 only.
4. **Client-auth TLS untried** — `TestClientCert` never got far enough to say.
5. `easymock` is absent from the local m2 repository, so the Tomcat test classes
   that need it cannot run on this host at all.
6. **`TestCustomSslTrustManager.testCustomTrustManagerNone` is unresolved and is
   the most suspicious single row in this record** — CratonVM passes what the
   oracle fails, on a trust-manager test, over a client path the two VMs do not
   share. Section 8a(ii).
7. **The `TestCustomSsl` exit hang (section 8a(i)) is undiagnosed.** It is a
   distinct shape from the `TestSsl` mid-test stall and the two should not be
   assumed to have one cause.
8. **Only 12 of 653 discovered Tomcat classes were run**, chosen for this lane
   (TLS/net, core startup, HTTP/1.1), not sampled to be representative. Of the
   four re-run against resolving fixtures, only one pair is a clean agreement.
9. **Section 7's TLS rows are superseded by section 8a** and should not be
   quoted: they were measured with fixtures that could not load.
