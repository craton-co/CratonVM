# Phase 1 baseline, measured — and a correction to the exit criterion

**Measured 2026-08-12 on `cratonvm-merged-dev` (dev tip `210703b7a`), Windows,
against HotSpot 25.0.3 (Microsoft-13877124) as the oracle, same host, same
session.**

This is the "before" for the three Phase 1 lanes. It exists so their fixes are
measured against a number somebody actually took, rather than against the
roadmap's prose.

## The witnesses

Two programs, both kept in the session scratchpad under `p1/`:

* `P1Witness.java` — 8 checks: `java.sql` loadability + `AtomicReferenceFieldUpdater`
  round trip (P1-A), `System.getenv()` shape and unmodifiability (P1-B),
  `SSLSocket`/`SSLEngine` construction (P1-C, weak — see below).
* `P1Tls.java` — 6 checks: a **real loopback TLS round trip**. In-process
  `SSLServerSocket`, RSA self-signed PKCS12 identity, genuine handshake, a byte
  written and echoed both ways. RSA deliberately: a separate known defect
  concerns JDK-generated **EC** identities and mixing the two would confound
  the result.

Neither prints a host-dependent value, so both are safe for the cross-VM diff.

## Result

| arm | `P1Witness` | `P1Tls` |
|---|---|---|
| HotSpot 25 | **8 ok / 0 bad** | **6 ok / 0 bad** |
| `cratonvm --jdk-only` | **2 ok / 6 bad** | **3 ok / 1 bad** |

The oracle is clean in both, so every divergence below is ours.

## The three fabricated receivers, by name

| lane | fabricated class refused under `--jdk-only` |
|---|---|
| P1-A | `java/util/concurrent/atomic/AtomicReferenceFieldUpdater$RustJvmImpl` |
| P1-B | `cratonvm/internal/UnmodifiableMap` |
| P1-C | `javax/net/ssl/SSLSocketOutputStream` |

P1-A's cascade is visible in the raw output and confirms the mechanism: once the
updater class is refused, `java/sql/SQLException` *itself* becomes a
`NoClassDefFoundError` for every later caller. That is how one native takes down
a whole package.

## Correction: the roadmap's exit criterion is too narrow

The roadmap §6 defines done as "no `cratonvm/internal/*` class instantiated,
verifiable with `--explain-jdk-only`".

**Six of the nine fabricated receivers do not match that prefix** — two of the
three named in this section, plus four more found later on this page. They live in
the JDK's own package namespace — `java/util/concurrent/atomic/...$RustJvmImpl`
and `javax/net/ssl/SSLSocketOutputStream`. A screen on `cratonvm/internal/`
would have reported Phase 1 clean while both were still fabricated.

So the criterion must be **the refused-class set that `--explain-jdk-only`
reports, whatever the package**, not a prefix match. `$RustJvmImpl` looks like a
naming convention rather than a one-off; whether it is a family is worth
establishing on its own.

This is the same species as the instrument failures already recorded in the
roadmap §5, and it was caught the same way — by a witness that named the class
instead of asserting a property of it.

## Also: the first P1-C probe was too weak, and passed

The initial `P1-C` checks in `P1Witness` — construct an `SSLSocket`, construct
an `SSLEngine`, check neither is a `cratonvm/*` class — **passed on CratonVM.**
They never reached a *connected* socket's streams, which is the only place the
fabricated receiver is handed out.

Recording it because it is the cheapest possible illustration of the standing
rule: **a narrow probe reports its own reach, not the defect.** Construction
being healthy is not evidence the area is healthy. `P1Tls.java` exists because
of this and is the probe that should be trusted for P1-C.

## P1-D — two blockers the roadmap does not name, with wider reach than the three it does

`native-api/src/no_image_receiver.rs` already holds the authoritative tables:
**49 `NO_IMAGE_JDK_RECEIVERS`** (JDK-namespaced classes that *no* real JDK image
declares) plus **8 `VM_MINTED_STAND_IN_RECEIVERS`**. (This page first said 9,
copied from that source file's own doc comment, which is stale; counted in the
tree the three tables are 49 / 8 / 9, the last being `VM_SERVICE_RECEIVERS`.
The total of 57 below was right for the wrong reason — 49 + 8 — and the error
survived because the number it produced was correct.) Any of those handed to
application code is the Phase 1 defect by construction. That is the true Phase 1
worklist — 57 candidates, not 3.

`FabReach.java` screens them by reaching each family through the most ordinary
Java that could route to it. **HotSpot 17/17. `--jdk-only` 15/17.** The two
failures are both in `java.util.function`:

```
FAIL Predicate and/or/negate
  -> java.lang.AbstractMethodError:
     method java/util/function/Predicate.test(Ljava/lang/Object;)Z has no Code attribute
FAIL Consumer.andThen
  -> java.lang.NoClassDefFoundError: java/util/function/Consumer$AndThen
```

Both mint sites are in `native-builtins/src/phases_late/streams.rs`.

Why this outranks the named three: `Predicate.and/or/negate` and
`Consumer.andThen` are **default methods on the core functional interfaces**.
Streams, collection pipelines, Spring, and essentially every modern Java
codebase use them constantly. `SSLSocket` blocks HTTPS; this blocks ordinary
control flow.

**The family is half-fixed, which is the signature of the shape.**
`Function.identity/andThen/compose` **passes** while `Predicate` and `Consumer`
fail, from the same file, minted the same way. That is the "fix the positive
half and leave its twin" pattern this project has hit repeatedly — and it is
exactly why a green `Function` check is not evidence about `Predicate`.

Note also that the two failures are **two different shapes**, not one:
`Consumer$AndThen` is the fabricated-receiver refusal (P1's shape), while
`Predicate` fails as `AbstractMethodError … has no Code attribute` — the
fabricated object exists but its method body does not. **No `Code` attribute
means an abstract declaration**, so the fix for the second is not the fix for
the first, and a lane that repairs only the class-minting will leave `Predicate`
red.

## P1-E — FFM downcalls, also unnamed by the roadmap

A second screening wave (`FabReach2.java`, 16 more probes over the families
`FabReach` did not reach: streams/collectors, `System.Logger`, FFM,
`WatchService`, `HttpServer`, `HttpClient`, JMX MXBeans, the SharedSecrets-backed
accessors, `AccessController`) is **HotSpot 16/16, `--jdk-only` 15/16**:

```
FAIL FFM downcall (DowncallHandle)
  -> java.lang.NoClassDefFoundError: java/lang/foreign/DowncallHandle
```

Mint site `native-builtins/src/panama.rs` — a different file from P1-D's, so the
two are independent lanes.

Reach: `Linker.downcallHandle` is the entry point for all of Panama. netty and
the newer high-performance libraries take the FFM road when it is available, and
CratonVM pins `sun.misc.unsafe.memory.access=allow`, which changes which road
some of them pick.

## The Phase 1 blocking set, measured

**33 probes across both waves. HotSpot 33/33. `--jdk-only` 28/33.**

57 candidate fabricated classes reduce to **five blocking families** at this
point in the measurement — revised to **nine** by wave 3, below:

| lane | family | blocks |
|---|---|---|
| P1-A | `Atomic*FieldUpdater$RustJvmImpl` | all of `java.sql` — JDBC, ORM, pools |
| P1-B | `cratonvm/internal/UnmodifiableMap` | `System.getenv()` → Spring |
| P1-C | `javax/net/ssl/SSLSocket{Input,Output}Stream` | all HTTPS |
| **P1-D** | `Consumer$AndThen`, `Predicate$$Lambda$*` | core functional interfaces |
| **P1-E** | `java/lang/foreign/DowncallHandle` | all of Panama/FFM |

The narrowing is the useful part: **28 of 33 ordinary-Java routes already work
under `--jdk-only`**, including streams and collectors, `HttpServer` and
`HttpClient` round trips, JMX MXBeans, `WatchService`, `FileChannel`, dynamic
proxies, `ServiceLoader`, and every iteration family. Most of the 57-entry table
is either unreachable from ordinary code or already repaired — so Phase 1 is
five lanes, not fifty-seven.

Two of the five were invisible to the roadmap, and both were found the same way:
by reaching for the family through ordinary Java rather than by reading the
tables. The tables say what *could* be fabricated; only a probe says what an
application actually hits.

## Wave 3: four more, found by *source audit first*, then measured

The five families above were found by probing. A source audit then predicted
three more from a two-term rule that needs no run:

> A mint is a live `--jdk-only` blocker iff **(1)** the receiver is on
> `NO_IMAGE_JDK_RECEIVERS`/`VM_MINTED_STAND_IN_RECEIVERS` *and* **(2)** the
> *minting native* is `bridge` — it survives strict mode and asks anyway. A
> third term, bare `try_alloc…(…)?` vs an `Err(_)` arm, decides how loud it
> fails.

Term 2 is free: `scripts/baselines/jdk-only-kind-map-25-linux.tsv` is a frozen
per-registration census with an adjudicated kind per triple.

`FabReach3.java` tested the predictions. **HotSpot 7/7; `--jdk-only` 3/7:**

```
OK   Properties.propertyNames()            <- predicted widest failure; RECOVERS
OK   Properties.keys()/elements()          <- RECOVERS
FAIL ConcurrentHashMap.keys()/elements() -> cratonvm/internal/SnapshotEnumeration
FAIL Hashtable.keys()/elements()         -> java/util/Enumeration$Impl
FAIL AsynchronousFileChannel read/write  -> java/util/concurrent/CompletedFuture
OK   ProcessBuilder.start                  <- the PINNED half (control)
FAIL Runtime.exec(String[])              -> cratonvm/synthetic/Process
```

Three things this run establishes that neither method could alone:

* **The audit found what probing missed.** Three live families, none reachable
  by the 33 routes of waves 1–2. A reachability screen reports its own reach;
  the kind map plus the mint-site read reports the *population*.
* **The audit's scoping was wrong where the probe was right.** `Properties`
  was predicted the widest failure — `System.getProperties().propertyNames()`
  is the JDBC/logging idiom — and it **passes**. Two `Enumeration` routes
  recover and two do not, naming **two different** fabricated classes. Neither
  method's verdict survives without the other's.
* **The `Runtime.exec` row carries its own control.** `ProcessBuilder.start`
  and `Runtime.exec` share one mint in
  `native-io/src/process.rs::spawn_and_wrap_with_redirects`. `start` was
  re-tagged `SyntheticStub` to stop the class escaping into strict mode; the six
  `Runtime.exec` overloads were left ambient `Bridge`. So the pinned half passes
  and its twin fails **in the same probe run** — the "fix the positive half and
  leave its twin" shape, demonstrated rather than argued. Fixed by re-tagging
  all six.

**`java/util/concurrent/CompletedFuture` matters for Phase 4**: the mint site's
own comment names H2's `FileAsync.write` and `TestFileSystem.testConcurrent` on
the `async:` filesystem — part of the very workload Phase 4 is meant to
adjudicate Phase 2 with.

Also confirmed by the same audit: **`sun/misc/Cleaner` and
`jdk/internal/logger/AbstractLoggerFinder` have zero registrations in the kind
map** — stale table rows, not live fabrications, exactly as the mint-site count
suggested. A reader counting fabricated classes off that table overcounts by two.

## The campaign's own headline example has a stale attribution

The roadmap §0 offers, as the strongest evidence that strict mode can be *more*
correct than Compatible: `Collections.synchronizedList` loses elements in
Compatible (6534 and 4697 of 8000 across two runs) and is exact under
`--jdk-only`, attributed to an identity-stub shadow that strict mode drops.

**The measurement stands. The attribution does not.** A Phase 2 lane traced it:
the identity stub was removed by `e8a7caba4` (2026-07-01, an ancestor of HEAD),
and both live registrars now build the real wrapper through the real
constructor. Both modes construct the same object — so retiring
`Collections.synchronizedMap`, the obvious next move, **would fix nothing**, and
the measured data loss has an **unidentified** cause. The lane's best hypothesis
is a `SyntheticStub` inside the wrapper's own `synchronized(mutex) { list.add(e) }`.

Two things worth carrying:

* **A result and its explanation rot separately.** The number is still
  reproducible; the sentence explaining it stopped being true six weeks ago, and
  nothing flagged that because nothing re-derives an explanation.
* This was the argument for a whole Phase 2 lane. Had it not been checked, the
  lane would have retired a native, measured no improvement, and had no way to
  tell "the fix did not work" from "the fix was aimed at the wrong thing".

The `synchronizedList` loss needs its own record and its own bisect. It is a
live Compatible-mode data-loss bug with no known cause.

## "The refusal is correct" does not make it a control

One lane, reviewing the FFM row, concluded that because
`java/lang/foreign/DowncallHandle` is a class no real JDK declares, the probe
failure is "strict mode correctly refusing a synthetic carrier — a control, not
a defect", and should not be counted.

**Half right, and the half that is wrong matters.** Every one of the nine
families has a *correct* refusal — that is the definition of the shape:

> A native registered in the **essential** set survives strict mode, runs, asks
> for a **fabricated** receiver, gets the refusal that `--jdk-only` exists to
> give, and dies as `NoClassDefFoundError` at the application's call site.
> **The refusal is correct. The survival of its caller is the defect.**

If a correct refusal made a row a control, all nine would be controls and Phase 1
would be empty — while `java.sql` stays unloadable and HTTPS stays dead. The
application-visible fact is that **no Java program can make an FFM downcall on
this VM**, and HotSpot 25 makes the same call cleanly. That is a defect by the
only test that matters.

The lane's narrower point is sound and worth keeping: it is **not a missing
feature**. Nothing needs to be implemented — `Linker.downcallHandle` works. The
carrier was simply the wrong class, and the fix is to hand back a real
`java.lang.invoke.MethodHandle`, which is what the caller holds it as, casts it
to, and calls `invokeExact` on.

The general rule, since this reading will recur: **a correct refusal is the
mechanism working; a caller that cannot survive it is the defect.** Ask what the
application can do, not whether the VM behaved as designed.

## `--explain-jdk-only` reports boot refusals and *only* boot refusals

Measured on the same binary, same run. The roadmap says the banner
"under-reports the blocker set by half — 13 of 27". The true shape is sharper.

**Reported:** exactly 13, all from the boot block in `vm/src/vm/vm_init.rs`, all
before `main` — `java/util/Enumeration$Impl`, `java/util/Comparator$Native`, and
eleven `cratonvm/internal/Unmodifiable*`. The message text is good; it names the
class, says the natives bound to it are unreachable, and predicts the call-site
failure.

**Not reported at all:** every one of the **five** runtime refusals sampled at
this point. The wave-3 four were **not** re-checked against the banner, so the
categorical claim below is sampled, not exhaustive — it holds for five of nine.
None of
`AtomicReferenceFieldUpdater$RustJvmImpl`, `UnmodifiableMap` (as requested by
`System.getenv`), `SSLSocketOutputStream`, `Consumer$AndThen` or
`DowncallHandle` appears anywhere in the output, though each kills an
application path in that same run.

So the accurate statement is **every boot-time refusal is reported and every
runtime refusal is silent** — not "13 of 27". That also relocates the fix: the
boot block is already correct, and the entire value of the cross-cutting `warn!`
change is on the runtime path.

Note `cratonvm/internal/UnmodifiableMap` appears on both sides — refused at boot
*and* refused again at runtime. Any de-duplication must not suppress the second
on the strength of the first; they are different events and the runtime one is
the one that explains an application failure.

Separately, the shutdown `[jdk-only:shutdown] policy violation` report names
**one** requested class, with requester `file:line`, initiating loader and
reason — a good format, apparently truncated to the first violation. Whether
that is by design or defect is open.

## What these 33 probes did NOT reach

Stated because a screen that does not declare its gaps reads as a proof of
absence, and this one is not. Roughly eight table entries were never exercised
by any probe above:

* `java/lang/Compiler` — deleted from the JDK years ago; no route exists.
* `java/rmi/activation/Activatable`, `ActivationGroup` — RMI activation, removed
  from the platform; almost certainly dead weight in the table.
* `java/net/InetAddressImplFactory`, `java/net/PlainServerSocketImpl` — only
  indirectly touched by the plain-socket probe; not addressed head-on.
* `jdk/internal/misc/SharedSecrets`, `sun/reflect/Reflection`, `sun/misc/URLClassPath`,
  `sun/misc/Cleaner` — reached only transitively, if at all. `sun/misc/Cleaner`
  and `jdk/internal/logger/AbstractLoggerFinder` are also the two entries with
  **zero** mint sites anywhere in the tree, which suggests they are stale rows
  rather than live fabrications — worth confirming before anyone spends a lane
  on them.
* `jdk/internal/ref/BucketDirectBufferDeallocator` — the direct-buffer probe may
  take the non-bucket road.

So the honest claim is: **nine blocking families** — five among the routes an
ordinary application takes, four found by the source audit — not "only nine
fabrications remain". A corpus run (P4-A) is
what would close the remaining gap, and that is precisely why the roadmap gates
Phase 2 on it.

## Reproduce

```
cd <scratchpad>/p1
javac -d . P1Witness.java P1Tls.java
java -cp . P1Witness ; java -cp . P1Tls                       # oracle
<bin>/cratonvm.exe --jdk-only -cp . P1Witness                 # arm
<bin>/cratonvm.exe --jdk-only -cp . P1Tls
```

`ks.p12` (RSA, `CN=localhost`, SAN `localhost`/`127.0.0.1`, storepass
`changeit`) is generated once with `keytool` and lives beside the sources.
