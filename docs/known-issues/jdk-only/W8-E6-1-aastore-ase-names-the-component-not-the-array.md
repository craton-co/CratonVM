## 1. The oracle, in full

`ArrayStoreException`'s message, like `ClassCastException`'s, is **generated by
the VM** rather than written by a JDK author, so nothing but the VM can get it
right. It is `Klass::external_name()` of the **value's own class**.

`java -cp out AseMsgs`, verbatim (`tag|exception|getMessage()`):

```text
R1_ObjArr_lt_Integer|java.lang.ArrayStoreException|java.lang.Integer
R2_StrArr2d_lt_IntegerArr|java.lang.ArrayStoreException|[Ljava.lang.Integer;
R3_ObjArr2d_lt_intArr|java.lang.ArrayStoreException|[I
R4_ObjArr_lt_StrArr2d|java.lang.ArrayStoreException|[[Ljava.lang.String;
R5_ObjArr_lt_AppElem|java.lang.ArrayStoreException|AseMsgs$AppElem
R6_IntegerArr_lt_String|java.lang.ArrayStoreException|java.lang.String
R7_StrArr2d_lt_int2dArr|java.lang.ArrayStoreException|[[I
R8_ObjArrArr_lt_ObjArr|NO-THROW
R9_AppElemArr_lt_String|java.lang.ArrayStoreException|java.lang.String
R10_StrArr3d_lt_StrArr|java.lang.ArrayStoreException|[Ljava.lang.String;
```

Three rules, and only the first is the defect:

1. **An array value is named in JVMS descriptor form with dots** —
   `[Ljava.lang.Integer;`, `[[I`, `[[Ljava.lang.String;` — **never** the
   component (`java.lang.Integer`) and never JEP 358 source form
   (`Integer[]`). Rows R2/R3/R4/R7/R10.
2. **A plain class is named binary-with-dots**, nested classes included:
   `AseMsgs$AppElem`, not `AseMsgs.AppElem`. Row R5.
3. The message names the **value**, never the array or its component type —
   R6 and R9 both say `java.lang.String` although their arrays differ.

Row R8 is the negative control: `Object[][] <- Object[]` is a legal store, so
a fixture that only ever asserts the throwing shapes cannot tell a correct
check from one that throws on everything.

This reproduces, independently, `RArrayStoreTiers`' own recorded oracle
(`EXPECTED_COLD[4] = "java.lang.ArrayStoreException:[Ljava.lang.Integer;"`).

### The oracle's own optimizer, and why only the cold tier is assertable

HotSpot runs `-XX:+OmitStackTraceInFastThrow` **on by default**: once an
implicit exception (ASE / NPE / AIOOBE / CCE) is thrown often enough from a
*compiled* site, it swaps in a preallocated instance with **no message and no
stack trace**. `RArrayStoreTiers` already encodes this — it asserts messages
only on the cold pass and asserts the exception *kind* across tiers — and the
probe above executes each shape exactly once, so both are in the deterministic
regime. Any future probe that loops a store shape and reads `getMessage()` will
see `null` appear at some iteration and must not read that as a VM defect.

## 3. Which of the two candidate causes it is

The task named two: either the lookup returns the component class for an array
object, or the array class's `name` is stored in source form. **It is the
first**, and the codebase already says so in two places:

* `vm/src/runtime/interpreter/typecheck.rs`, inside `array_descriptor_of`:
  `// The class_id on a Reference array holds the component class id.`
* `vm/src/runtime/interpreter/lambda.rs`, the doc comment on
  `cce_display_class_name`: *"The header word of a reference array holds the
  COMPONENT class id, so the caller's `class_id_of` -> `class.name` lookup
  yields `java/lang/String` for a `String[]`"* — and it records that this
  produced the nonsensical `java.lang.String cannot be cast to
  java.lang.String`, "the TestObjectDataType failure, chased for a session as a
  class-identity split".

So the class id on a reference array is the component's **by design**, not by
accident, and every consumer that wants the array's own name must go through a
descriptor reconstruction. Both `aastore` arms did

```rust
.get_class(shared.mem.heap.class_id_of(elem_ref))
.map(|c| c.name.to_string())
```

which is **off by exactly one array dimension for every array-valued element**,
and correct for everything else. That is why s04 was the *only* message
divergence: s01/s02/s03/s05 all store a plain object.

The second candidate is independently ruled out: names in `ClassStore` are
internal/slashed (`java/lang/Integer`), and the measured `got=` was **dotted**
(`java.lang.Integer`). The dotting is applied downstream by
`hotspot_vm_type_error_message` in `vm/src/runtime/exceptions.rs` — which
proves, from the measurement alone, that the fast-path raise site does reach
that funnel. That mattered for the fix (§4).

## 4. What was applied

Both `aastore` arms now ask the existing helper instead of the raw lookup:

* `vm/src/runtime/interpreter.rs`, the `0x53` fast path;
* `vm/src/runtime/interpreter/opcodes.rs`, `Instruction::Aastore`.

```rust
let raw_elem_name = /* unchanged lookup */;
let elem_cls = cce_display_class_name(shared, elem_ref, &raw_elem_name);
```

**No new helper was written.** `cce_display_class_name` is the answer to the
same question `checkcast` asks — "what is the Java-visible class of this
object, for a VM-minted type error" — it renders arrays as descriptors via
`array_descriptor_of`, and it additionally carries the `UnmodifiableMap`
storage-stamp translation that keeps a VM-internal class out of an app-visible
message. Before this change it had **two** callers (`lambda.rs`'s SAM argument
check and `opcodes.rs`'s `checkcast`) for **five** sites that need it; this
takes two more.

Three details that make the one-line reuse actually correct:

* **The helper returns the INTERNAL (slashed) name**, and that is what we want:
  the funnel's `hotspot_external_name` dots it, giving `[Ljava/lang/Integer;`
  → `[Ljava.lang.Integer;`. §3 established from the measurement that this
  fast path does reach the funnel.
* **The funnel leaves a primitive-array descriptor alone**, because its
  `rewritable` predicate is `contains('/') && !contains(whitespace)` and `[I`
  has no `/`. Row R3 therefore comes out right without a special case — and so
  does a default-package application class (row R5's `AseMsgs$AppElem`, and by
  the same token `[LAppElem;`), whose internal and external names are equal.
* **Two statements, not one.** `cce_display_class_name` takes
  `class_manager.read()` itself; folding it into the lookup expression would
  hold that guard across the call and invite a re-entrant read against a queued
  writer. The `checkcast` site is already written this way.

The `"?"` fallback also strictly improves: `cce_display_class_name` tests the
heap header first, so an array whose component class is unresolvable now yields
a descriptor rather than `"?"`.

## 5. Review of the s15 bounds fix (not this lane's change)

Correct, and correct in both twins. JVMS §6.5 `aastore` fixes NPE → AIOOBE →
ASE; the fast path tested only `index < 0`, so a past-the-end index fell
through to the covariance check and reported ASE. Three notes from reviewing it:

* **Null still routes right.** The fast path's `if let Value::Object(Some(..))`
  fails for a null array, falls out, re-pushes the operands and lets the
  slow-path arm raise the (JEP 358) NPE. Order preserved.
* **Hoisting `array_length` out of the `index < 0` branch adds no new failure
  mode**, though it is worth having checked rather than assumed: the `heap.rs`
  backend's `array_length` *asserts* the object is an array and the `gen_heap`
  backend logs a rate-limited guard warning and returns 0. But on this same
  instruction `set_array_element` already performs the identical assert/guard
  unconditionally, so a non-array arrayref reached an array helper before the
  change too. The cost is one extra header read per `aastore`.
* **The trailing `Err(i) => aioobe(..)` arm on `set_array_element` is now
  unreachable** in both twins. Harmless; left in place as belt-and-braces.

## 7. NOMINATION — the third twin, `vm/src/jit/helpers.rs` (not this lane's file)

`jit_aastore` has the identical raw lookup and therefore the identical defect.
Its own comment records that on x64 **nothing calls this function** (the
emitter in `jit/src/x64/bytecode_walk.rs` lowers `aastore` inline), so this is
latent today rather than measurable — but it is the same one-line reuse, and
leaving it is precisely how the two-handlers-for-one-opcode drift documented in
the s15 fix arose in the first place.

`cce_display_class_name` is `pub(super)` in `interpreter::lambda`, so the JIT
cannot see it. `interpreter.rs` already does `pub use lambda::*;` and glob
re-exports cap at the item's own visibility, so widening the item is sufficient
— no new re-export needed. `array_descriptor_of` is already `pub(crate)` and
already reachable from the JIT as `crate::runtime::interpreter::array_descriptor_of`
(that module path is how `helpers.rs` reaches `aastore_element_assignable`
today), so a one-file variant is possible; the two-file version below is
preferred because it leaves the codebase with **one** helper and **five**
callers rather than a fourth spelling of the same parse.

**(a) `vm/src/runtime/interpreter/lambda.rs`** — widen the helper.

new:
```rust
pub(crate) fn cce_display_class_name(shared: &SharedVm, obj_ref: ObjectRef, raw_name: &str) -> String {
```

## 8. NOMINATION — `Character.charCount(-1)`, `native-builtins/src/lang_math.rs` (not this lane's file)

`RJdkIntrinsics2 --only=charcls` fails on
`"Character.charCount(-1) must be 1 — below MIN_SUPPLEMENTARY, not a panic"`.
**Not in this lane's files.** It is `native_character_char_count`, and it is not
a panic — it is a signedness inversion returning `2`.

Oracle, `java -cp out CpNeg` (`scratchpad/e6/CpNeg.java`):

```text
-1|charCount=1|isBmp=false|isValid=false|isSupp=false
-2147483648|charCount=1|isBmp=false|isValid=false|isSupp=false
1114112|charCount=2|isBmp=false|isValid=false|isSupp=false
65535|charCount=1|isBmp=true|isValid=true|isSupp=false
65536|charCount=2|isBmp=false|isValid=true|isSupp=true
1114111|charCount=2|isBmp=false|isValid=true|isSupp=true
0|charCount=1|isBmp=true|isValid=true|isSupp=false
```

`java.lang.Character.charCount` is
`codePoint >= MIN_SUPPLEMENTARY_CODE_POINT ? 2 : 1` — a **signed** compare, so
every negative input answers `1`. The native casts to `u32` first, so `-1`
becomes `0xFFFF_FFFF`, which is `> 0xFFFF`, and it answers `2`.

**The family was checked, and only this member is wrong** — the `as u32` is not
a blanket bug, which is why the fix must not be applied by pattern:

| native | JDK definition | signed or unsigned | verdict |
|---|---|---|---|
| `charCount` | `cp >= 0x10000 ? 2 : 1` | **signed** | **wrong** — the cast inverts it |
| `isBmpCodePoint` | `cp >>> 16 == 0` | unsigned | correct; the `as u32` matches `>>>` exactly |
| `isValidCodePoint` | `cp >>> 16 < 17` | unsigned | correct — it already uses the signed `0..=0x10FFFF` range, which agrees on every input |

**(c) `native-builtins/src/lang_math.rs`**, `native_character_char_count`.

old:
```rust
    let cp = match args.first() {
        Some(Value::Int(v)) => *v as u32,
        _ => return Ok(Some(Value::Int(1))),
    };
    Ok(Some(Value::Int(if cp > 0xFFFF { 2 } else { 1 })))
```
new:
```rust
    // `Character.charCount` is `cp >= MIN_SUPPLEMENTARY_CODE_POINT ? 2 : 1` —
    // a SIGNED compare, so every negative code point answers 1 (measured on
    // JDK 25.0.3: charCount(-1) = 1, charCount(Integer.MIN_VALUE) = 1).
    // Casting to `u32` first turned -1 into 0xFFFF_FFFF and answered 2.
    //
    // Do NOT propagate this to the siblings: `isBmpCodePoint` is `cp >>> 16
    // == 0` and `isValidCodePoint` is `cp >>> 16 < 17`, both genuinely
    // UNSIGNED, and both already agree with HotSpot on negative input.
    // charCount is the one member of this family that is signed.
    let cp = match args.first() {
        Some(Value::Int(v)) => *v,
        _ => return Ok(Some(Value::Int(1))),
    };
    Ok(Some(Value::Int(if cp >= 0x10000 { 2 } else { 1 })))
```

Predicted after: `RJdkIntrinsics2 --only=charcls` clears this row.
`charCount(0x110000) == 2` (an invalid-but-positive code point, which HotSpot
also answers `2`) is the regression guard — a fix that clamped to
`0..=0x10FFFF` would answer `1` and be wrong in the other direction.

## 9. Residual

* **Hot-tier ASE messages are unmeasured and unmeasurable from this fixture.**
  `RArrayStoreTiers` deliberately asserts messages cold-only (§1), so even a
  fully green run says nothing about what the compiled tier prints. Since the
  x64 emitter does not call `jit_aastore` at all, the compiled tier currently
  has no ASE message path to be right or wrong about; that changes the moment
  §7's emitter wiring lands, and §7(b) must land with it.
* **`array_descriptor_of` fails soft to `[Ljava/lang/Object;`** when the
  component class cannot be resolved. That is pre-existing and shared with
  `checkcast`; it cannot affect s04 (whose component, `java/lang/Integer`, is
  always loaded) but it would silently produce a wrong-but-plausible message
  for an array of an unresolvable component.
