## Fixed: `Parameter.getDeclaredAnnotations()` AIOOBE on non-static inner-class constructors

**Symptom:** `java.lang.ArrayIndexOutOfBoundsException: null` at `java.lang.reflect.Parameter.getDeclaredAnnotations(Parameter.java:333)`, reached via `AnnotationsScanner` from any reflective scan of a constructor parameter (Spring's `BeanOverrideUtils`, JUnit Jupiter's constructor-injection resolution, etc.). Hit 22 test methods across 9 classes; 7 are CV-unique (HotSpot passes): `SpringJUnitJupiterAutowiredConstructorInjectionTests` + the 6 `@Nested` `*ExtensionContextNestedTests` classes under `test.context.junit.jupiter.nested`.

**Root cause:** `native_method_get_parameter_annotations` (registered for both `Method` and `Constructor` — see the registration comment: CratonVM's `Constructor` reflective objects are built without the raw `annotations`/`parameterAnnotations` byte[] fields real JDK bytecode parses, so the real `getParameterAnnotations()` bytecode would return empty and these natives replace it entirely) returned an array sized to `param_annotations.len()` — the class file's `RuntimeVisibleParameterAnnotations` count, indexed against the *source-level* parameter list. For a **non-static inner class constructor**, the compiler prepends a synthetic leading parameter (the enclosing instance, `this$0`) that has no entry in that table, so the real parameter count (from the descriptor) is one more than `param_annotations.len()`. The returned array was too short and shifted: index 0 held the *first explicit* parameter's annotations instead of an empty array for the synthetic one, and the last (real) parameter's index ran off the end → AIOOBE. Confirmed with a minimal repro (`InnerCtorParamRepro.java`, kept out-of-tree) comparing a non-static vs `static` inner class constructor — only the non-static (synthetic-leading-param) case diverged from HotSpot.

**Fix:** when `param_annotations.len() < count_method_params(&method_desc)`, right-shift: build the output array to the full descriptor-length, pad the leading `synthetic_leading = param_count - param_annotations.len()` slots with empty `Annotation[]`, then copy the real rows starting at that offset. Mirrors real JDK's `Executable.handleParameterNumberMismatch`, which this native override otherwise bypasses entirely. Also clamps defensively against the (invalid/unexpected) case of *more* raw rows than descriptor params, to avoid a Rust-side out-of-bounds write.

**Blast radius (confirmed by rerun):** fixes the 7 `nested`/`SpringJUnitJupiterAutowiredConstructorInjectionTests` CV-unique classes directly (23/23 classes, 168/168 methods green in the affected slice), **plus** clears **all 6 `test.context.web` ABEND classes** (`EnableWebMvcXmlConfigTests`, `GenericXmlWebContextLoaderTests`, `MetaAnnotationConfigWacTests`, `RequestAndSessionScopedBeansWacTests`, `ServletContextAwareBeanWacTests`, `ServletTestExecutionListenerJUnitIntegrationTests` — an uncaught AIOOBE during a shared reflective bootstrap step was crashing (ABEND) the whole batch these classes shared, not just the manifesting class). Verified each individually post-fix: all OK, confirmed again in a full 249-class re-sweep. **13 of the original 25 CV-unique failures resolved by this one fix** (25 → 12).

**Note on `test.context.bean.MockitoBeanContextCustomizerEqualityTests`:** running this class alone (`KRunDebug`, direct `--java-home` invocation) is a clean `OK` post-fix — test *discovery* itself was hitting the same AIOOBE scanning `@Nested`/parameterized constructors, and the fix resolves it in isolation. But the full-suite batch re-sweep still shows it as `LOADERR`, immediately preceded in its batch by `MockitoBeanConfigurationErrorTests` (itself `LOADERR`, `junit-platform-suite` engine discovery failure — looks like an intentional-error-case test, not obviously a CratonVM bug). This smells like a **pre-existing, separate batch-order state-leak** — one class's failed discovery corrupting some static registry that the next class's discovery reads — not a regression introduced by this fix. Not investigated further here; kept in the residual count above pending a dedicated repro.

## Residual 1 (OPEN) — `test.context.groovy` (5 classes) + `test.context.web.BasicGroovyWacTests`

**Symptom:** `.groovy`-script-based `ApplicationContext`/`WebApplicationContext` loading in the Spring **TestContext framework** (`GenericGroovyXmlContextLoader`, distinct module/class from the already-fixed `spring-context` `GroovyBeanDefinitionReader`/`BeanBuilder` DSL cluster — see [`hib-proxyclassreuse-loader-blind-class-resolution.md`](hib-proxyclassreuse-loader-blind-class-resolution.md)'s "Manifestation — Spring `context.groovy`" section) fails: `XmlBeanDefinitionReader` chokes trying to parse the `.groovy` script as XML (`SAXParseException: Content is not allowed in prolog`).

**Root cause found:** `native-builtins/src/net_phase_e.rs` (~line 5130) hardcodes `ClassUtils.isPresent(name, cl)` to return `false` for any `name.starts_with("groovy.")` (comment: "S111r27 — keep optional integrations truly optional… when these flip true under partial emulation, later probes may dive into missing subsystems (JSF/Groovy) and destabilize bootstrap", authored ~2026-05-08). `DelegatingSmartContextLoader`'s static `GROOVY_PRESENT` check calls exactly this, so it always falls back to the plain `GenericXmlContextLoader` for `.groovy` resources — confirmed directly: `groovy.lang.Closure` resolves fine via `Class.forName`, but `ClassUtils.isPresent("groovy.lang.Closure", cl)` returns `false` only because of this stub.

**Why the obvious fix (delete the `groovy.` branch) was NOT shipped:** doing so makes `DelegatingSmartContextLoader` correctly pick the Groovy loader, which then genuinely invokes Groovy's real ANTLR4-based script compiler (`groovyjarjarantlr4`) — and that exposes a **separate, deep, unrelated bug**: a class-file field-count mismatch for `groovyjarjarantlr4.v4.runtime.atn.ATNConfig` (`num_slots=3` allocated vs. slot indices 3/4 written by the ATN simulator — i.e. the real class needs ≥5 fields but CratonVM computed 3), which the existing `gc::guard` defensive drop logs on *every* dropped read/write. Running even one groovy-script test class this way produced 250k+ warning lines in under 20s with no sign of completing (verified under both `--nojit` and jit-real — not a JIT-tiering artifact, a genuine interpreter/class-layout bug). Shipping the isPresent fix as-is would trade 6 fast, clean CV-unique failures for VM-wide log-spam/near-hang risk on **any** code path that parses a nontrivial Groovy script once Groovy detection is fixed — unacceptable. **Reverted; `net_phase_e.rs` is unchanged on this branch.**

**To actually close this out:** the `ATNConfig` (and likely sibling ANTLR runtime classes under the `groovyjarjarantlr4` shaded package) field-layout bug needs to be root-caused and fixed *first* — probably a class-file parsing gap specific to this relocated/shaded package, or a JIT/interpreter speculative-layout-probe issue misidentifying these objects (the guard's own message hints at "a speculative collection-layout probe dispatched on a non-matching receiver type", unconfirmed). Only then is it safe to remove the `net_phase_e.rs` groovy stub. Until that lands, this doc's 6 classes stay open.

## Fixed (round 2): `InheritableThreadLocal` not propagated through `Thread(ThreadGroup, Runnable, String[, long])` constructors

**Symptom:** `IllegalStateException: Failed to retrieve ApplicationEvents for the current thread` — `ApplicationEventsHolder`'s backing store is a plain `InheritableThreadLocal`, and code that asserts on a worker/pool thread (Awaitility's default `untilAsserted` poller, JUnit 5 parallel execution, TestNG's own thread) never sees the value the test thread set. Affected: `test.context.junit.jupiter.event.JUnitJupiterApplicationEventsIntegrationTests` (`asyncConsumption`), `test.context.junit4.event.JUnit4ApplicationEventsAsyncIntegrationTests` (`asyncConsumption`), `test.context.testng.event.TestNGApplicationEventsAsyncIntegrationTests` (`asyncConsumption`) — **all now fully green (8/8, 2/2, 2/2 methods)**. `test.context.junit.jupiter.event.ParallelApplicationEventsIntegrationTests` still has a 2-method residual — see below, it's a different (JUnit5-parallel-execution) bug, not this one.

**Root cause, precisely isolated via a minimal repro** (`InheritableTLRepro2.java`/`ITLRepro3.java`/`ITLRepro4.java`, kept out-of-tree): under real-JDK mode (`--java-home`, no `--synthetic-jdk`), an `InheritableThreadLocal` value set on the parent thread propagates correctly to a child created via `new Thread(Runnable)` **or** `new Thread(ThreadGroup, Runnable)` **or** `new Thread(Runnable, String)` — i.e. any constructor where *at most one* of `{group, name}` is explicitly non-null. It fails **only** when **both** `group` and `name` are explicitly non-null simultaneously (`Thread(ThreadGroup, Runnable, String[, long])`) — which is exactly what `java.util.concurrent.Executors.defaultThreadFactory()` uses for every pooled worker, so **every** `ExecutorService`/`ScheduledExecutorService`-backed thread was affected, not just these test classes. Confirmed the child's `name`/`group`/`priority`/`contextClassLoader` are all correctly set even in the failing case — **only** `inheritableThreadLocals` is dropped, and reading it back via `NativeContext::get_field_by_name` shows `Value::Int(0)` (not `Value::Object(None)`) — i.e. whatever writes it never reaches `putfield`, leaving the raw zero-fill representation a native heap read observes (rather than the `Object(None)` a bytecode `getfield` would present).

All public `Thread` constructors delegate to the exact same private master constructor (`Thread(ThreadGroup, String, int, Runnable, long)`, JDK 25 `javap` confirms this — verified byte-identical bytecode reached regardless of entry point) which contains the `this.inheritableThreadLocals = ThreadLocal.createInheritedMap(parent.inheritableThreadLocals)` copy. Tracing the bytecode shows the *only* control-flow difference between passing/failing cases is two independent, non-adjacent forward conditional branches (`if (group != null) skip-reassignment` and `if (name != null) skip-default`) both being taken simultaneously — a synthetic repro reproducing just that shape (two independent skip-branches + a reused local-variable slot, unrelated to `Thread` entirely) did **not** reproduce it, so the defect is specific to this method's actual bytecode, not a generic "two branches" interpreter bug. None of the involved constructors are natively overridden (only the no-arg `Thread()` is), so this is **real bytecode misbehaving**, not a native-registration gap. Root-causing the exact interpreter mechanism (why *this* control-flow combination drops *only* this one `putfield`) needs opcode-level bytecode tracing that wasn't completed — tracked as a follow-up.

**Fix (pragmatic workaround, not the interpreter root cause):** `native_thread_start0` (already the native override for `Thread.start0()`, active in real-JDK mode, and already doing an analogous fixup for `contextClassLoader` propagation per the existing `TC0622` comment) now also checks, right before spawning: if the child's `inheritableThreadLocals` field reads back as `Object(None)` **or** `Int(0)`, and the parent (the thread calling `.start()`) has a non-null map, copy it via a real `ThreadLocal.createInheritedMap(parentMap)` invocation (not just aliasing the reference — the child needs its own independent copy per `InheritableThreadLocal` semantics) and write it into the child. Opt-out: `CRATONVM_INHERIT_TL_WORKAROUND=0`.

**Known trade-off:** `characteristics` (the internal flag distinguishing an explicit `Thread(group, target, name, stackSize, false)` opt-out of inheritance) isn't retained anywhere observable post-construction, so this fix can't tell "buggy" apart from "intentionally opted out". A legitimate opt-out combined with non-null `group`+`name` would incorrectly regain inheritance. That specific combination is rare in practice (the 5-arg opt-out constructor is rarely used at all); documented here pending a real interpreter-level fix that would make this workaround unnecessary.

**Repro (works standalone, no Spring needed):**
```java
static final ThreadLocal<String> TL = new InheritableThreadLocal<>();
TL.set("hello");
new Thread(() -> System.out.println(TL.get())).start();                      // "hello" — OK, always was
Executors.newSingleThreadExecutor().submit(() -> System.out.println(TL.get())); // was null, now "hello"
```

## Residual 3 (OPEN, newly discovered) — `ArrayStoreException` in `StringBuilder.append` during Mockito's ByteBuddy failure-message formatting

**Symptom:** `test.context.bean.override.mockito.MockitoBeanByTypeLookupIntegrationTests` (not in the original 25-class count — found investigating the batch-order artifact below) fails all 5 methods with `IllegalStateException: Failed to load ApplicationContext`, caused by `java.lang.ArrayStoreException: arraycopy: incompatible array element types (src=Char, dest=Byte)` at `Arrays.copyOf` ← `AbstractStringBuilder.ensureCapacityNewCoder` ← `StringBuilder.append` ← `org.mockito.internal.util.StringUtil.join` ← `InlineDelegateByteBuddyMockMaker.prettifyFailure` ← `.createMockType` ← `Mockito.mock(...)`.

**Analysis:** `prettifyFailure` is Mockito's own error-formatting helper, called *only* from the `catch` block when ByteBuddy's `.make()` genuinely fails to generate the mock class — i.e. this is a **double fault**: some real ByteBuddy mock-creation failure happens first (root cause still unknown — its exception is what `prettifyFailure` was trying to nicely report), and then the error-*reporting* code itself crashes with an unrelated `ArrayStoreException`, which is the only thing that survives to be observed (confirmed only one `Caused by:` level in the full trace — the original failure is completely masked). Minimal repros forcing a Latin1→UTF16 `StringBuilder` coder-widen (both with and without a simultaneous capacity grow) did **not** reproduce the `ArrayStoreException` in isolation, so whatever triggers it needs the exact string content/shape Mockito builds here — not chased further. Two bugs are tangled together and neither is root-caused; this needs someone to first find what makes ByteBuddy's mock creation fail for this specific test's bean-override scenario before the StringBuilder crash even becomes reachable to isolate.

**Connection to `MockitoBeanContextCustomizerEqualityTests`:** this is the actual trigger for the residual documented below.

## Residual 4 (OPEN) — batch-order cascade from Residual 3, blast radius is non-deterministic

Several `bean.override.mockito.*` classes (`MockitoBeanConfigurationErrorTests`, `MockitoBeanContextCustomizerEqualityTests`, `MockitoBeanDuplicateTypeCreationIntegrationTests`, and in a later full-suite run also `MockitoBeanByTypeLookupForConstructorParametersIntegrationTests`, both `MockitoSpyBean*ForConstructorParametersIntegrationTests`, and all 3 `hierarchies.MockitoBean*` classes) pass cleanly in total isolation (`KRunDebug` standalone), but show `LOADERR` (`TestEngine ... failed to discover tests`) when run in the same batch JVM as `MockitoBeanByTypeLookupIntegrationTests` (Residual 3). First reproduced with a **4-class-wide, self-healing** cascade (re-running just the `bean.override.mockito.*` package at `--batch 12`); a later full 249-class sweep caught the **same trigger cascading through 9 classes instead** — the blast radius is *not* a fixed window, it varies run-to-run (likely GC-timing- or heap-state-dependent, matching the pattern of other transient-corruption bugs in this codebase). So this isn't a permanent global-state leak — some side effect of the ArrayStoreException/double-fault crash in Residual 3 transiently corrupts JUnit Platform test *discovery* for a variable number of subsequent classes in the same batch JVM, then recovers. Fixing Residual 3 is the natural next step before investigating this further; not chased independently, and not worth cataloguing an exact affected-class list since it will differ next run.

## Residual 5 (OPEN) — `ParallelExecutionSpringExtensionTests` — genuine hang, not just slow

**Symptom:** `test.context.junit.jupiter.parallel.ParallelExecutionSpringExtensionTests` (`@RepeatedTest(10)`, each repetition running 1000 sub-tests via JUnit5's own parallel-execution engine with a dedicated worker thread pool) never completes. Given a 1800s (30 min) individual timeout: **zero progress indication for 25+ minutes**, genuinely stuck (not merely slow-but-progressing) — confirmed by killing it after 25 min with no `RESULT` line ever printed. During the hang, the log also captured a handful (not runaway — ~10 lines, self-recovering) of `GC: inconsistent header — kind=Object but array_length=512 (num_slots=0, class_id=4); inline-alloc forgot to set kind=Array` warnings from `cratonvm_gc::gen_heap`, suggesting a race under the heavy concurrent allocation/thread-pool load this test generates, though not confirmed as the actual cause of the hang (could be a separate, coincidental symptom). Not investigated further — this looks like it needs the same kind of deep concurrency-bug hunt as the `InheritableThreadLocal` fix above, but for JUnit5's own internal parallel-execution machinery rather than `Thread` construction; out of scope for this session.
