## Read the H2 timeout column before reading the H2 numbers

The baseline's own follow-up (`RESULTS-20260721-hang-rootcause.md`,
`RESULTS-20260723-hangrerun.md`) established that **most H2 "hangs" are slow,
not stuck**: rerunning the 60 hung classes at a 1500s timeout instead of 60s
turned most of them into passes. HANG at a 60s timeout is therefore a
*timeout*, not a status, and it moves with host load.

That matters acutely for this run. Host load average during it climbed from
~14 at launch to **137 on 16 cores** — other sessions, not this one — and the
run then lost the host entirely. Any HANG delta against a baseline measured on
a quieter host is load, not regression, unless it is confirmed by a rerun at a
longer timeout on an idle box.

## Results — H2, complete (218/218)

| Status | Baseline 2026-07-23 | This run | Δ |
|---|---:|---:|---:|
| PASS | 139 | **139** | **0** |
| HANG | 60 | 63 | +3 |
| FAIL | 19 | 16 | −3 |
| **Total** | 218 | 218 | |

**No change in the pass count.** The entire delta is three classes moving
between the two non-pass buckets, in the direction contention produces: a
class that used to fail fast now runs past the 60s timeout and is recorded as
HANG instead. Given the run executed at load 90–160 on 16 cores, with the host
dropping SSH entirely several times, that is the expected shape of load noise
and not evidence of a behaviour change either way.

What this does and does not establish:

* It **does** establish that the remediation wave did not regress H2's pass
  set. That was the question worth asking of a wave that changed the GC's
  reclamation rules, the escape analysis, the deopt metadata, dispatch-cache
  keying and the class loader.
* It does **not** establish anything about the three moved classes. Confirming
  those needs a rerun at a longer per-class timeout on a quiet host — the
  method the baseline itself used to show most H2 hangs are slow, not stuck.

## Results — Tomcat, partial (29 of 645), stood down deliberately

23 classes exited 0, 6 exited 124 (the driver's timeout code).

I stopped this run rather than letting it finish. It had completed 29 of 645
classes in roughly half an hour, which extrapolates past fifteen hours, and my
four shards were themselves part of why the host kept refusing connections.
Continuing would have produced a timeout-dominated result while degrading
every other session on the box.

The runner's results file is append-only and already-recorded classes are
skipped on re-invocation, so this is resumable rather than wasted:
