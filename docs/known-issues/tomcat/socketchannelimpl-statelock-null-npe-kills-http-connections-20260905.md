# `sun.nio.ch.SocketChannelImpl.stateLock` reads null — a connection-killing NPE across 4 unrelated Tomcat test classes

## Status

**OPEN, newly diagnosed 2026-09-05.** Not previously documented anywhere under
`docs/known-issues/` or `docs/internal/` (grepped for `stateLock` and
`SocketChannelImpl` — no hit). `docs/known-issues/tomcat/nonpassed-class-census.md`
explicitly lists the HTTP/2 family this affects as **"Not diagnosed."** This
page supplies that diagnosis for 3 of its 4 classes and adds a 4th class from
the same run that shows the identical signature.

**Severity:** MEDIUM-HIGH — kills in-flight HTTP/1.1 and HTTP/2 connections
outright (not merely a slow path), reproducibly, across independent test
areas (HTTP/2 flow control, servlet async I/O).

## Run this was found in

Fresh `dev`-tip Tomcat build, commit `7acc0b27c`, Azure host
(`azureuser@20.80.105.49`, `/data/cratonvm`), full 640-class suite under
`-XX:+UseZGC`, `zgc-3gc-20260905/shard-0/results.csv`. No crash in this run;
the 4 classes below are all `FAIL`.

## The signature

Every one of the four logs contains this exact stack, verbatim (only the
calling frame and the log level/thread name vary):

```
java.lang.NullPointerException: Cannot enter synchronized block because "this.stateLock" is null
	at sun.nio.ch.SocketChannelImpl.toString(SocketChannelImpl.java:1583)
	at org.apache.tomcat.util.net.NioChannel.toString(NioChannel.java:241)
	at org.apache.tomcat.util.net.SocketWrapperBase.toString(SocketWrapperBase.java:546)
	at org.apache.coyote.AbstractProcessorLight.process(AbstractProcessorLight.java:81)
	at org.apache.coyote.http2.StreamProcessor.process(StreamProcessor.java:102)
	...
```

and, in `TestHttp2Section_6_1`, the same root frame reached from a different
caller (a `StringManager`-driven log message formatting the socket, and the
socket's own `doClose`):

```
java.lang.NullPointerException: Cannot enter synchronized block because "this.stateLock" is null
	at sun.nio.ch.SocketChannelImpl.toString(SocketChannelImpl.java:1583)
	at org.apache.tomcat.util.net.NioChannel.toString(NioChannel.java:241)
	at java.text.MessageFormat.subformat(MessageFormat.java:1539)
	at java.text.MessageFormat.format(MessageFormat.java:1037)
	at org.apache.tomcat.util.res.StringManager.getString(StringManager.java:156)
	at org.apache.coyote.AbstractProtocol$ConnectionHandler.process(AbstractProtocol.java:1216)
	...
```

```
java.lang.NullPointerException: Cannot enter synchronized block because "this.stateLock" is null
	at sun.nio.ch.SocketChannelImpl.toString(SocketChannelImpl.java:1583)
	at org.apache.tomcat.util.net.NioChannel.toString(NioChannel.java:241)
	at org.apache.tomcat.util.net.SocketWrapperBase.toString(SocketWrapperBase.java:546)
	at org.apache.tomcat.util.net.NioEndpoint$NioSocketWrapper.doClose(NioEndpoint.java:1478)
	at org.apache.tomcat.util.net.SocketWrapperBase.close(SocketWrapperBase.java:668)
	...
```

This is a real, JDK-25-bytecode-thrown NPE (the "helpful NPE" wording is
JEP 358's, generated by the JDK's own interpreter/verifier, not a CratonVM
synthetic message) — i.e. the diagnosis is not "CratonVM fabricated an
exception," it is "real `SocketChannelImpl.toString()` bytecode executed a
`monitorenter` on a field that reads null on this VM."

`SocketChannelImpl.stateLock` is `private final Object stateLock = new
Object();`, assigned in the class's own constructor and used to guard nearly
every state-changing/state-reading method on the class (`toString`,
`implConfigureBlocking`, `close`, `connect`, ...). Grep confirms **zero**
prior mentions of `stateLock` anywhere in `docs/known-issues/` or
`docs/internal/`.

## What this actually breaks (not just a log-formatting cosmetic)

In every occurrence the NPE is thrown from inside Tomcat's own error path —
either while building a diagnostic string for a `SEVERE`/`FINE` log record, or
while tearing a socket down — and it propagates out and aborts the request
in flight. `TestFlowControl`'s log makes the causality explicit:

```
FINE [http-nio-...] StreamProcessor.process Connection [0], Stream [1], An error occurred during processing that was fatal to the connection
java.lang.NullPointerException: Cannot enter synchronized block because "this.stateLock" is null
	...
```

i.e. Tomcat logs this NPE itself as the reason the connection died. The
client side of the same request then sees the connection close mid-response:

```
1) testNotFound[0: loop [0], useAsyncIO[false]](org.apache.coyote.http2.TestFlowControl)
java.io.IOException: End of input stream with [9] bytes left to read
```
```
1) testAsyncIoEnd00(org.apache.catalina.core.TestAsyncContextImpl)
java.io.IOException: HttpURLConnection response failed: connection closed before response head
```
```
1) testErrorOnWaitingStream01[0: ...](org.apache.coyote.http2.TestHttp2Section_5_1)
java.net.SocketException: SocketException: write0: Broken pipe (os error 32)
```

All four `testAsyncIoEnd0{0,1,2,3}` failures in `TestAsyncContextImpl` show
this identical client-visible IOException, and the same class's log contains
8 instances of the `stateLock` NPE — consistent with it being the common
trigger, though the exact 1:1 correspondence between a given NPE occurrence
and a given failing sub-test was not traced line-by-line in this session.

## Relationship to the already-fixed `keyLock` bug (BUG-DF01) — related family, NOT the same field

`docs/internal/fixed-suite-bugs/CRATONVM_BUGS/BUG-DF01-nio-keyfor-keylock-null-selector-loop.md`
documents an already-fixed sibling defect: `AbstractSelectableChannel.keyLock`
reading null inside `keyFor()`, killing the NIO poller loop outright (HANG,
not FAIL). That fix added a native `keyFor(Selector)` override so the real
`synchronized(keyLock)` bytecode never runs. **This is a different field**
(`stateLock`, declared on the concrete `SocketChannelImpl`, not
`keyLock`/`regLock` on the abstract `AbstractSelectableChannel` superclass)
reached through a different method family (`toString`/`doClose`/logging, not
`keyFor`). The shape is the same failure class this project has hit
repeatedly — a synthetic/native-constructed real-JDK NIO channel object whose
field layout omits or never populates a `private final` lock object the real
bytecode depends on — but DF01's fix does not cover this field, and this NPE
is still live on today's `dev` tip (`7acc0b27c`).

## What is NOT established this session

* The exact code path that constructs (or re-wraps) the `SocketChannelImpl`
  instance that reaches these call sites without `stateLock` populated was
  not traced to a specific native/synthetic constructor this session — the
  fix likely belongs in the same family of native NIO-channel construction
  code as DF01 (`native-io/src/nio_selector.rs` and neighbors), but that is
  inference from the shared symptom shape, not a pinned call site.
* Whether `TestHttp2Section_8_2` (HANG in this same run, `1 of 6658` per
  `nonpassed-class-census.md`'s prior characterization) shares this cause was
  not checked this session.
* Whether this NPE also explains any part of the Tribes/multicast family's
  failures (two of those logs independently show a *different* NPE at
  `sun.nio.ch.SocketChannelImpl.implConfigureBlocking`, possibly the same
  `stateLock` guard reached through a different method — not confirmed) is
  left open; that family is otherwise attributed to this host's network
  environment (`tribes-multicast-family-still-environmental.md`) and was not
  reinvestigated here.
