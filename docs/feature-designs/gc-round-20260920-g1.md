# G1: directions out of the 2026-09-20 design round

Five proposals, sized, with the first step named. They are ordered by the ratio
of what they prevent to what they cost, not by how interesting they are.

The round's own findings are the evidence for #1 and #4; #2 and #3 are
capability gaps the code already states about itself.

---

## 1. One region-walk iterator, so the next walker cannot forget a sentinel

**Size: medium (one new type, ~17 call-site rewrites, no behaviour change).**

`gc/src/g1.rs` contains **seventeen** hand-written linear region walks of the
shape

```rust
let mut offset = 0;
while offset < cursor {
    let p = base + offset;
    if let Some(skip) = jit_tlab_skip_span_len(&jit_skips, p) { offset += skip; continue; }
    if let Some(gap)  = gap_filler_len(p as *const u8)        { offset += gap;  continue; }
    let h = unsafe { &*(p as *const ObjectHeader) };
    if is_humongous_filler(h) { break; }
    let size = object_total_size(h);
    if size < HEADER_SIZE || offset + size > cursor { break; }
    /* ...the four lines this walker actually cares about... */
    offset += size;
}
```

Every one of those five guards is load-bearing and every one has been forgotten
at least once. `docs/GC.md` records "TLAB gap-sentinel desync in **every** G1
region walker" as a fixed defect *class*; this round found four more walkers
missing one or both of the two TLAB sentinels
(`empty_header_is_a_real_object`, `grid_closes_on_cursor`,
`grid_object_containing`, `count_unretired_forwards`) plus one missing the
frozen-peer list (`rset_completeness_counts`). Three of those were added after
the class was "fixed". The pattern is not that people are careless; it is that
the contract lives in a prose comment on `gap_filler_len` and the enforcement
lives in seventeen copies.

**The type.** A `G1RegionWalk<'a>` iterator yielding
`(offset, *mut u8, &ObjectHeader, usize /*size*/)`, constructed from
`(&G1Region, &[(usize, usize)] /*skips*/)`, that owns all five guards and
reports *why* it stopped:

```rust
enum WalkEnd { Cursor, HumongousFiller, Unsizeable { offset, size }, Straddles { .. } }
```

The stop reason is not a nicety — several callers behave differently on a
truncated walk (`note_humongous_targets_in_region` returns `false`, which is
what makes the humongous death certificate "earned"; the card-cleaning callers
must bound `clean_and_redirty` by `walked_upto`, never by the cursor). Today
each expresses that by hand.

**Why it is safe to do in one pass:** the seventeen loops already agree on the
five guards after this round's patches, so the rewrite is mechanical and the
diff is reviewable as "loop header replaced, body unchanged".

**First step.** Add the type and convert exactly one caller — `walk_objects`,
which is the simplest and has no card or rewrite side effects — plus a unit
test that builds a region holding `[object, GAP_FILLER, object, published skip
span, object]` and asserts the iterator yields three objects and ends
`Cursor`. That fixture does not exist today and is the thing that would have
caught all five omissions.

## 2. Card-granular Phase 2, not card-*screened* Phase 2

**Size: large (a new per-region bitmap with an allocator-side maintenance
obligation).**

`gc/src/g1_cards.rs` opens by stating the finding: a remembered-set entry names
a source *region*, so Phase 2 walks the whole megabyte to find the handful of
slots that point into the collection set, and "HotSpot's G1 pays per dirty
512-byte card instead."

The card table shipped, and it is used — but as a **screen**, not as an index.
`scan_source_region_for_cset_refs` still strides every object of the source
region and asks `cards.any_dirty_in(obj, size)` per object. That removes the
*slot* visits for clean objects, which is the majority of the win on a
reference-dense old region, and removes none of the header decoding or grid
striding. The cost is still `O(bytes in the source region)`.

To pay `O(dirty cards)` the walk has to be able to *start* at a card boundary,
which means answering "which object contains this address" without walking from
the region base. That is an object-start oracle:

* one bit per 8 heap bytes, so `region_size / 64` bytes of metadata
  (16 KiB per 1 MiB region — the same shape as `mark_bitmap`, and ZGC already
  has the type in `gc/src/zgc/starts.rs`);
* set by every allocation path into the region (`G1Region::bump_alloc`, the
  evacuator's TLAB carve, `alloc_humongous_locked`), cleared by
  `G1Region::reset` alongside the mark bitmap and the cards;
* a `first_object_at_or_before(addr)` query = one reverse bit scan.

**The correctness risk is entirely on the maintenance side**, and it is the
same risk `G1Region::try_mark_and_account` carries: an allocation path that
forgets to set a bit makes Phase 2 skip a live holder, which is a lost edge and
then a use-after-free. So it needs the same treatment the accumulated liveness
got — a debug-build oracle that re-derives the bits by a linear walk and
asserts equality at every pause (`CRATONVM_G1_CLEANUP_WALK` is the precedent).

**First step.** Land the bitmap and the oracle *with no reader*: maintain it,
assert it agrees with the linear walk in debug builds, and ship nothing that
depends on it. If it survives a gauntlet, Phase 2's rewrite is then a local
change with a proven input. If it does not, the finding is an allocation path
nobody knew about — which is worth having on its own.

## 3. Make the mixed pause parallel-able, and measurable either way — **DONE**

**Size: small for the instrument, unknown for the dispatch.**

*Closed 2026-09-21. The known-issues page this cited is retired to
`docs/internal/fixed-bugs/g1-mixed-collections-never-reach-the-parallel-evacuator-RETIRED-20260921.md`.*

Both halves landed, and the dispatch half came back with a number that says
not to flip it:

* **The route.** `CRATONVM_G1_PARALLEL_MIXED=1` (`parallel_mixed_enabled`)
  dispatches `mixed_collection` to `mixed_collection_parallel`, which is
  therefore no longer live code reachable only from `#[cfg(test)]`.
* **The instrument.** `MIXED_ROUTE_SERIAL` / `MIXED_ROUTE_PARALLEL`, read by
  `g1_mixed_route_counts()` and printed unconditionally as `[GC] g1
  mixed-route: serial=<n> parallel=<n> total=<n>`. A separate pair from the
  young one, as this section asked, rather than a widening of
  `g1_young_evac_counts` — the young accessor keeps its name and its meaning.
* **The dispatch decision: stays opt-in.** Not for the race (48/48 clean on
  `SteadyChurnRecreation @16m --nojit` across default / `WORKERS=1` /
  `PARALLEL_EVAC=0`, re-measured 2026-09-21), but because the lever
  parallelises Phase 3 and on a mixed pause 100% of the copying is Phase 2's.
  See `docs/internal/g1-2026-09-20/w6p-the-mixed-parallel-number-and-the-phase-it-is-not-about.md`.
  **The thing worth fixing is named there and it is not this flag.**

## 4. A per-pause grid-closure assertion in debug builds

**Size: small.**

`grid_closes_on_cursor` already exists and answers exactly the right question —
"did a linear walk of this region land on the cursor, having stepped only whole
objects?" — and it is called only from the corrupt-holder *report* path, i.e.
only after something has already gone wrong.

Every defect in the walker family this round touched is a grid desync, and
every one of them is detectable by that function one pause earlier than by its
symptom. Run it over every non-Free region at the end of `collect_garbage`
under `cfg!(debug_assertions)` (and under `CRATONVM_G1_DBG_REACH` in release),
and abort with the region index, the offset it stopped at, and
`locate_in_object_grid`'s verdict for that offset.

Cost: one linear pass over the live heap per pause in debug builds. That is the
same order as the `CRATONVM_G1_CLEANUP_WALK` oracle already accepted for the
liveness accumulator, and for the same reason.

**First step.** Wire it behind `CRATONVM_G1_DBG_REACH` only (which already
exists and already implies "I am hunting corruption"), measure the pause cost
on `G1ChurnPauseProbe`, and promote to `debug_assertions` if it is bounded.

## 5. Recover remembered-set precision at cleanup instead of at reset

**Size: medium.**

`RememberedSet` coarsening (`gc/src/region.rs`, `rset_source_cap`, default 512)
is **one-way for the life of the region's contents**: the only thing that
clears the flag is `G1Region::reset`. A long-lived Old region that coarsens once
makes every later pause that collects it walk *every plausible source region
wholesale* (`live_rset_sources` returns the whole heap and then returns early),
for as long as the region lives — which for an Old region is potentially the
life of the process. The field doc is honest that recovering precision "would
mean rebuilding the exact source set, and the module already refuses to expose
that because a dropped live entry is a use-after-free."

But the concurrent-mark **cleanup** pause has something no mutator has: a
complete mark bitmap and a whole-heap walk it is already entitled to take
(`CRATONVM_G1_CLEANUP_WALK` restores exactly such a walk). A source set derived
from a *complete* walk over *marked* objects is exact, not an approximation —
the same reason Phase 4's edge rebuild is allowed to add entries.

The safety condition is the one the refusal names: the rebuild must be
all-or-nothing. If the walk truncates anywhere (unsizeable header, humongous
filler, straddling object — the `WalkEnd` reasons from proposal #1), the
coarsened flag stays and nothing is dropped.

**First step.** Instrument before designing: `record_g1_rset_coarsened` already
exists as a counter. Add "how many pauses walked a coarsened source set, and how
many regions that cost them" to the `[GC-STAT]` line, and run a large-heap
workload. Coarsening is *supposed* to be rare (512 sources is unreachable on
the 256-region default heap); if the number is zero on every workload anyone
runs, this proposal is correctly unbuilt and the page should say so.
