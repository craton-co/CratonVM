# Real-Classfile `Proxy.newProxyInstance`

Status: design / partially-built. M. The proxy class-file *generator* already
exists (`classloading/src/proxy_gen.rs`, 57 fns) and a "define or fall back"
wiring is in place — but the default dispatch is still the single synthetic
`Proxy$Instance` shim that dispatches by name lookup, which is the documented
JCK-compliance gap.

## Goal

Make `java.lang.reflect.Proxy.newProxyInstance` generate a **real, unique proxy
class file** per interface set, define it through the normal class loader, and
instantiate *that* class — so `proxy.getClass()` is a distinct `$ProxyN` class,
`isProxyClass` is true for it, and interface-method dispatch goes through real
generated bytecode rather than a name-keyed synthetic intercept. Retire the
`Proxy$Instance` synthetic shim.

## Current state (cited)

- **Default dispatch = synthetic `Proxy$Instance`, Strategy B+.**
  `vm/src/runtime/proxy.rs:4`–`53`: every proxy, regardless of interface set,
  lands on the single synthetic class `java/lang/reflect/Proxy$Instance`
  (`PROXY_INSTANCE_CLASS`, `:53`), with a fixed 3-slot layout (handler /
  interfaces / identity-hash, `:24`–`:31`). Interface methods are dispatched by
  intercepting on this class name in the `invokevirtual` interceptor +
  `proxy_invoke_handler_shared` + the reflect-proxy natives (`proxy.rs:38`–`44`).
- **The module doc names this as a deliberate stop-gap** pending WP2.3:
  `proxy.rs:9`–`12` — "Strategy A (real bytecode generation per JDK
  `ProxyGenerator`) would block on [`Unsafe.defineClass` / `Lookup.defineClass`]
  in-flight in parallel". `proxy.rs:38` — "When WP2.3 lands, this module can flip
  to Strategy A by emitting a real class file and registering it with the class
  manager".
- **The JCK row records the gap.** `docs/internal/jck-compliance.md`
  (`api/java_lang/reflect`, 85%): *"Known gap: `Proxy.newProxyInstance` does not
  currently synthesise a new class-file; interface-method dispatch works by name
  lookup."*
- **The generator already exists and is partly wired.**
  - `classloading/src/proxy_gen.rs`: `ProxyClassSpec` (`:93`) + `ProxyMethod`
    (`:106`), `emit_proxy_classfile` (`:146`) emitting a full classfile (a
    `static final Method m_<i>` per method, `:40`; per-method body shape at
    `:57`), plus a complete `CpBuilder` (`:436`) and `CodeBuilder` (`:634`) for
    constant-pool and bytecode emission, descriptor parsers
    (`descriptor_param_slots` `:310`, `descriptor_return` `:345`).
  - `native-builtins/src/lib.rs:35237` already calls
    `proxy_gen::emit_proxy_classfile(&spec)`, and `define_or_get_proxy_class`
    (around `lib.rs:35280`) builds the spec, defines the class, **caches it by
    `(loader_id, sorted iface ClassIds)`**, and on *any* failure **falls back to
    the legacy synthetic shim** (its doc: "Returns `None` on any failure so the
    caller can fall back to the legacy synthetic shim without raising an
    exception").

Net: Strategy A is built and reachable, but it is a fallible *fast path* in
front of the synthetic shim, not the canonical path — so behavior still defaults
to name-lookup whenever class definition isn't fully wired, and `getClass()`
identity / `isProxyClass` semantics follow the shim.

## Design

Promote the real-classfile path from "best-effort fast path with synthetic
fallback" to the **canonical** path, and make the synthetic shim a narrow
last-resort (or remove it).

### 1. Solidify class definition through the normal loader

The fallback fires "on any failure". Enumerate and fix those failure modes so
definition succeeds for the cases real apps hit:

- The generated `$ProxyN` must be defined via the **normal class loader** for
  the proxy's interfaces' loader (JDK semantics: the proxy class is defined in
  the loader that can see all the interfaces), through `classloading`'s
  `define_class_full` — not registered as a pre-baked synthetic. Confirm the
  super (`java.lang.reflect.Proxy`) and the interfaces resolve in that loader.
- This is the WP2.3 dependency (`proxy.rs:9`): defining a class at runtime from
  generated bytes is the same capability `Unsafe.defineClass` /
  `Lookup.defineClass` need. If WP2.3 has landed, route through it; if not,
  ensure `define_class_full` (already called by `define_or_get_proxy_class`) is
  a sufficient definition path for proxies specifically.

### 2. Correct `$ProxyN` semantics

Once defined as a real class:

- `proxy.getClass()` returns the unique `$ProxyN` (distinct per interface set),
  not the shared `Proxy$Instance`.
- `Proxy.isProxyClass(c)` is true iff `c` is one of the generated `$ProxyN`
  classes — track them in the proxy-class cache, not by name-prefix on the shim.
- `getInterfaces()`, `getInvocationHandler(proxy)`, and the per-method `Method`
  objects (`m_<i>` static fields, `proxy_gen.rs:40`) come from the generated
  class's own metadata.
- Default-method handling (`InvocationHandler.invokeDefault`) and `hashCode` /
  `equals` / `toString` routing-through-the-handler must match the JDK's
  generated proxy (the generated body forwards these three to the handler unless
  declared otherwise).

### 3. Make Strategy A canonical; shrink the shim

- Flip `newProxyInstance` to **require** the real-classfile path; on a genuine
  definition error, raise the JDK exception (`IllegalArgumentException` /
  `UndeclaredThrowableException`) instead of silently degrading to the shim — a
  silent degrade is the compliance hazard (different `getClass()` identity).
- Gate the flip (`CRATONVM_REAL_PROXY`) so it can soak against the reflection
  suites before becoming default. Keep the shim only behind the gate-off path.
- Once green, delete the `Proxy$Instance` synthetic class and the three
  name-keyed intercepts (`proxy.rs:38`–`44`).

## Implementation steps (ordered)

1. **Audit `define_or_get_proxy_class` failure modes** (`lib.rs:~35280`): log
   every `None`-return cause; fix the ones real apps hit (loader visibility,
   super/interface resolution, descriptor edge cases in `proxy_gen`).
2. **Verify normal-loader definition** of `$ProxyN` (WP2.3 / `define_class_full`)
   and `getClass()` identity.
3. **`isProxyClass` + interface/handler/Method semantics** off the generated
   class, tracked via the proxy cache.
4. **Default-method + Object-method routing** parity with the JDK generated body.
5. **Gate `CRATONVM_REAL_PROXY`**, make it the path, raise real exceptions
   instead of degrading.
6. **Soak** against `api/java_lang/reflect` RC.1..RC.7 and the proxy-using app
   suites (logging proxies, Spring/JDK dynamic proxies — cf. `MEMORY.md` Gradle
   logging-proxy CCE note).
7. **Flip default + delete the synthetic shim** (`proxy.rs` `Proxy$Instance` and
   the three intercepts).

## Risks

- **Loader visibility / definition errors** are the reason the fallback exists;
  promoting the path means these must actually be fixed, not hidden. The audit
  in step 1 is the crux.
- **`getClass()` identity changes** are observable and tested — apps that
  `instanceof`-check or cache by proxy class will behave differently than under
  the shim. That's the point (it becomes *correct*), but it can surface latent
  app assumptions; the gate lets it soak.
- **Object-method routing** (`hashCode`/`equals`/`toString` to the handler) must
  exactly match the JDK generated proxy or proxies misbehave in collections.
- **Generated-bytecode verification**: the emitted classfile must pass the
  verifier (stack maps, max_stack/locals) — `proxy_gen`'s `CodeBuilder` must
  produce valid frames for the verified path.
- **Caching correctness**: the `(loader_id, sorted ifaces)` key must match JDK
  proxy-class identity rules (same interfaces in different *order* may or may not
  share a class per spec — verify).

## Effort

M. The generator and a reachable wiring already exist; the work is hardening
class definition (gated on WP2.3 if not yet landed), getting `$ProxyN` semantics
exactly right, and flipping the default + deleting the shim. The failure-mode
audit (step 1) determines the true size.

## Increment 1 — failure-mode audit + canonical flip (landed)

### Failure-mode enumeration (`define_or_get_proxy_class`, native-builtins `lib.rs`)

Every path on which the function returns `None` (→ caller degrades to the
synthetic `Proxy$Instance` shim), audited from source:

1. **Spec build (`build_proxy_spec_for` → `None`).** Triggers only when an
   interface `ClassId` fails to resolve to a name (`class_name_of_id`
   returns `None`) — a genuinely unloadable interface. Rare.
2. **Classfile emission (`emit_proxy_classfile` → `Err`).** Only a malformed
   method descriptor surfaces here (typed `ClassFileError` from
   `descriptor_param_slots` / `descriptor_return`). Rare.
3. **Class definition (`define_class_full` → `Err`).** The historically
   dominant bucket. Concrete causes:
   - **3a. Prohibited package name** — *already fixed*: `build_proxy_spec_for`
     names the class `com/sun/proxy/$ProxyN` (or the iface's package for a
     non-public iface) instead of the old `java/lang/reflect/$ProxyN`, which
     `define_class_with_options` rejected for a non-bootstrap loader
     (`SecurityException: Prohibited package name`).
   - **3b. Unresolvable super (`Proxy$Instance`)** — *already fixed*: the
     `Proxy$Instance` synthetic super is registered via
     `ensure_synthetic_class` before the define, so `load_class` of the super
     succeeds in real-JDK mode (it previously failed → first proxy in the
     process fell back).
   - **3c. Pass-2/3 VerifyError** on the generated bytecode. Mitigated by the
     emitter being straight-line (no branches / no handlers / no
     `StackMapTable` needed; `skip_verification: false`). The `super()`
     `INVOKESPECIAL Proxy$Instance.<init>` type-checks because the in-flight
     `$ProxyN`'s superclass link resolves to the registered `Proxy$Instance`
     (`verify_insn.rs` `<init>` rule + `ClassStoreHierarchy::is_subclass`).
   - **3d. Duplicate define** (`IncompatibleClassChangeError`) — guarded by
     the `(loader_id, sorted ifaces)` cache returning the existing `ClassId`
     before a re-define is attempted.
4. **Silent degrade itself** — the deepest issue: the prior contract returned
   `None` on *any* failure and the caller accepted the synthetic shim with NO
   diagnostic, so the shim was the de-facto canonical path whenever 1–3
   weren't perfectly wired. `getClass()` identity then followed the shim
   (the JCK-compliance hazard).

### What increment 1 changed

- **Canonical flip via `CRATONVM_REAL_PROXY` gate** (`real_proxy_enabled()`,
  native-builtins `lib.rs`): defaults **ON** — the real generated-`$ProxyN`
  path is now the canonical path; the synthetic shim is reachable only with
  `CRATONVM_REAL_PROXY=0` (or `false`/`off`/`no`). This addresses failure mode
  (4): the degrade is no longer the silent default.
- **Failure-mode observability**: each `None` return is now tagged
  `FALLBACK(spec|emit|define)` under `CRATONVM_DBG_PROXY` and classified to a
  concrete cause in code comments, so the remaining degrades are diagnosable
  rather than invisible.
- **Acceptance test** (`classloading/src/proxy_gen.rs`,
  `real_proxy_classfile_defines_verified_not_synthetic_shim`): emits the
  canonical single-interface spec and defines it through
  `ClassManager::define_class_with_options` with **verification enabled**
  (`skip_verification: false`) against the registered synthetic super +
  interface — exactly the wiring `define_or_get_proxy_class` uses — then
  asserts the defined class IS the real `com/sun/proxy/$Proxy0` (not the
  synthetic `Proxy$Instance`, `is_synthetic_stub == false`), with the proxied
  interface and the interface-method body on the generated class. This pins
  that the verified-define of the generated bytecode succeeds for the standard
  single-interface case, i.e. the real path is canonical.

### Remaining (next increments)

- **`Proxy$Instance.<init>(InvocationHandler, Class[])V` is absent** from the
  synthetic super (`synthetic_stub_ctor_methods` does not special-case
  `Proxy$Instance`). Allocation bypasses the ctor (`alloc_object` +
  `set_field`), so it is currently dead, but any path that *executes* the
  generated `<init>` (JIT call site, `new`+`invokespecial`) would hit
  `NoSuchMethodError`. Fix belongs in `class_manager.rs`
  (`synthetic_stub_ctor_methods`) — out of this item's edit boundary; flag for
  the class-manager owner.
- **Default-method + Object-method routing** parity (design §2 / §4).
- **Raise the real JDK exception** (`IllegalArgumentException` /
  `UndeclaredThrowableException`) instead of degrading even when the gate is
  on and a define genuinely fails (design §3), then delete the shim.
