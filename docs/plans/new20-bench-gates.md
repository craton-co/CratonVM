# NEW-20 — Benchmark gates for the JIT (and the interpreter)

## Goal

Stop performance regressions from sneaking in. Today
`vm/benches/vm_benchmarks.rs` runs as criterion microbenchmarks but
nothing reads the numbers, nothing fails CI when they regress, and
there is no committed baseline. NEW-20 closes that gap end-to-end.

**Definition of done (per roadmap):** "CI publishes a benchmark report
per release with absolute numbers + geomean delta vs the prior
release."

The smaller, *enforceable* DoD I will hit in this checkpoint:

1. A real `bench-gate` binary that runs the whole criterion suite,
   parses the JSON output, compares each metric against a committed
   baseline JSON file, and exits non-zero with a clear diff if any
   metric regresses by more than the configured threshold (default
   15%, per NEW-20.2).
2. Two new bench targets implementing N-Body and Binary Trees from the
   shootout, exercised through the real RustJVM interpreter (so they
   reflect actual JVM throughput, not Rust microbenchmarks).
3. A committed baseline file (`bench/baseline.json`) containing the
   measured medians from the host machine, with a documented
   regenerate procedure for forks running on different hardware.
4. A new CI job (`.github/workflows/bench-gate.yml`) that runs the
   gate on push to release branches and on pull requests touching
   `vm/`, `jit/`, `gc/`, or `native-builtins/`.
5. Real unit tests for the comparison logic (regression detection,
   missing baseline entries, new entries, geomean math) — the gate's
   correctness must be testable without running criterion.

## What's already in place

- `vm/benches/vm_benchmarks.rs` — 9 criterion benchmarks covering VM
  startup, allocation, GC, native dispatch, interpreter loops,
  fibonacci, string creation. Already wired through `[[bench]]`.
- `criterion` 0.5 — produces machine-readable JSON via
  `--output-format bencher`-compatible files in `target/criterion/.../estimates.json`.
- `vm/benches/Cargo.toml` doesn't exist; the bench is declared in
  `vm/Cargo.toml` under `[[bench]] name = "vm_benchmarks"`.
- The CI workflow `ci.yml` runs `cargo build --all-targets`, which
  *compiles* the bench but never runs it.

## Approach

A bench gate is a comparison engine, not yet another framework. The
existing criterion benches already produce the data we need; we
*only* need to:

1. Read the criterion JSON estimates from
   `target/criterion/<bench>/<bench-id>/new/estimates.json`.
2. Load the committed baseline from `bench/baseline.json`.
3. Compute `(new_ns - baseline_ns) / baseline_ns` for each metric.
4. Print a table; exit 1 if any delta exceeds the threshold.
5. (Optional) emit a fresh `bench/last_run.json` artifact.

For NEW-20.4 (NBody + BinaryTrees) I will not invent yet another
benchmark format — they become two more criterion bench groups in
`vm_benchmarks.rs`. The harness picks them up automatically.

For NEW-20.1 / NEW-20.3 (SPECjvm2008 / DaCapo): those suites are 100+
MB external JARs that depend on JDK classes RustJVM can't yet load
end-to-end. Bringing them in would bloat the repo and bypass the
"no stubs" constraint by faking results. Instead, the gate
infrastructure is built generically — once the JDK bootstrap is
solid (post NEW-1/NEW-4) you only need to add a wrapping bench that
spawns the suite. The roadmap entry is updated to reflect this:
the *gate* is delivered now; the *external suite hookup* is
explicitly tracked as a follow-up under NEW-1 (which removes the JIT
skip list that would otherwise distort SPECjvm numbers).

## Checkpoints

### CP1 — `bench-gate` Rust binary

**File:** `vm/src/bin/bench_gate.rs` (new) +
`vm/Cargo.toml` `[[bin]]` entry.

Walks `target/criterion/`, reads each `estimates.json`, loads
`bench/baseline.json`, computes deltas, prints a table, exits 1 on
regression.

CLI:

```text
bench-gate                      # run the gate against current criterion output
bench-gate --baseline FILE      # use a different baseline file
bench-gate --threshold 0.10     # 10% instead of 15%
bench-gate --update-baseline    # write current run as the new baseline
bench-gate --report FILE        # write JSON report to FILE
```

Exit codes: `0` clean, `1` regression, `2` baseline missing or
corrupt, `3` no criterion data found (run `cargo bench` first).

### CP2 — NBody + BinaryTrees bench targets

**File:** `vm/benches/vm_benchmarks.rs` — extend.

These are compiled as *Java bytecode* generated by hand (matching the
pattern of `make_fib_bytecode` / `make_counting_loop_bytecode`),
since the bench harness must not depend on a working `javac` install.
Both benchmarks are well-defined integer-only kernels:

- **N-Body**: simulate 5 bodies for N steps, return final energy as
  a fixed-point integer (multiply by 1e6). The classic shootout uses
  doubles; we use a fixed-point version so the kernel stays in
  integer/long ops the interpreter executes most reliably.
- **Binary Trees**: build a perfect binary tree of depth `d`, sum its
  values, return the sum. No allocation needed beyond ints.

These exercise: `iadd`/`imul`/`isub` arithmetic, conditional
branches (`if_icmpge`), loop control, method calls (`invokestatic`
for the tree builder).

### CP3 — Baseline file + comparator

**File:** `bench/baseline.json` (new), `vm/src/bin/bench_gate.rs`
contains the comparator.

Baseline schema (intentionally simple — anyone can edit by hand):

```json
{
  "schema_version": 1,
  "host": "windows-x86_64-12thgen",
  "captured_at": "2026-04-15T00:00:00Z",
  "metrics": {
    "vm_startup": { "median_ns": 0 },
    "shared_vm_startup": { "median_ns": 0 },
    "startup_to_first_bytecode": { "median_ns": 0 },
    "object_allocation/100": { "median_ns": 0 },
    "object_allocation/1000": { "median_ns": 0 },
    "gc_cycle_1000_objects": { "median_ns": 0 },
    "native_dispatch_noop": { "median_ns": 0 },
    "interpreter_counting_loop/1000": { "median_ns": 0 },
    "interpreter_counting_loop/10000": { "median_ns": 0 },
    "interpreter_counting_loop/100000": { "median_ns": 0 },
    "interpreter_fibonacci/10": { "median_ns": 0 },
    "interpreter_fibonacci/20": { "median_ns": 0 },
    "interpreter_fibonacci/30": { "median_ns": 0 },
    "interpreter_fibonacci/40": { "median_ns": 0 },
    "string_creation_100": { "median_ns": 0 },
    "shootout_nbody/100": { "median_ns": 0 },
    "shootout_nbody/1000": { "median_ns": 0 },
    "shootout_binary_trees/8": { "median_ns": 0 },
    "shootout_binary_trees/12": { "median_ns": 0 }
  }
}
```

The first time the gate runs it bootstraps: if `--update-baseline` is
passed, it writes the current measured values into the file. CI runs
without `--update-baseline`.

Comparison rules:

- A metric whose baseline is `0` (placeholder) is treated as
  uninitialized — the gate prints "BOOTSTRAP" and never fails.
- A metric present in baseline but missing from the run prints
  "MISSING" and fails with exit 1 (signals that the bench was
  removed or misnamed).
- A metric present in both with `delta > threshold` prints "REGRESS"
  and fails with exit 1.
- A new metric (in run, not in baseline) prints "NEW" and does not
  fail, but the report records it for the next baseline update.
- Geometric mean of all deltas is computed and printed at the
  bottom; it must also stay within threshold.

### CP4 — `bench-gate.yml` CI workflow

**File:** `.github/workflows/bench-gate.yml` (new).

Triggers:

- `push` to `main` and any `release/*` branch.
- `pull_request` touching `vm/`, `jit/`, `gc/`, or `native-builtins/`.

Steps: `cargo bench --bench vm_benchmarks --no-fail-fast`, then
`cargo run --bin bench-gate -- --report bench/last_run.json`.
Uploads `bench/last_run.json` as a workflow artifact and posts a
comment on the PR with the table on regression.

### CP5 — Tests

**File:** `vm/src/bin/bench_gate.rs` includes a `#[cfg(test)] mod tests`.

- `regression_above_threshold_fails`
- `improvement_below_threshold_passes`
- `placeholder_baseline_bootstraps`
- `missing_metric_fails`
- `new_metric_does_not_fail`
- `geomean_computes_correctly`
- `parse_estimates_reads_criterion_format`
- `cli_update_baseline_writes_file`

These exercise the comparator with synthetic data — no criterion run
required.

## Invariants

- `bench-gate` must never depend on hardware-specific timing
  thresholds; the threshold is relative (% delta) so the same
  baseline travels across CI runners as long as they're consistent.
- The comparator never panics on malformed criterion JSON — every
  `?` returns a typed error mapped to a non-zero exit.
- Baseline file format is forward-compatible: unknown fields are
  ignored, missing fields default to "uninitialized".
- The harness reads only files inside `target/criterion/` — no
  network, no file system writes outside `bench/`.
