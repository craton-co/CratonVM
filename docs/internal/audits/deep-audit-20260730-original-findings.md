## Critical code and architecture todo

- [ ] **P0 — Fix the remaining Spring AOT class-loader identity bug before treating Spring AOT as “working.”** The repo’s own open Spring bug list says one residual class remains; the concrete root cause already identified is that a Spring CGLIB proxy inherits the wrong copy of its superclass from the wrong loader, which then surfaces as `Field.set` argument-type mismatches and likely also explains related log4j plugin-construction noise. The next investigation target is explicitly the loader inheritance / define path in `lookup_define.rs` and the loader recorded on the proxy superclass at define time. citeturn34view0turn32view1

- [ ] **P0 — Redesign method-redefinition caching so redefine does not permanently dump the VM onto a catastrophically slow path.** The repo documents that after any Mockito `mock()`, CratonVM slows a real `StringBuilder.length()` call from tens of nanoseconds to roughly 36–41 microseconds, while HotSpot remains around 17 ns/call. The documented mechanism is severe: any redefine permanently disables JIT compilation process-wide for that run, and redefined targets miss quickening, method-resolution, and cached invoke paths, causing per-call re-resolution and re-quickening. The repo’s own recommended fix is to key caches on `(class_id, redefine_generation)` and repopulate them after redefine instead of globally falling back whenever `any_class_redefined()` is true. citeturn31view0

- [ ] **P0 — Reduce the default synthetic runtime surface instead of merely smoke-testing it.** Even with `synthetic-jdk` off by default, the default runtime still keeps synthetic implementations live for ForkJoinPool, AQS/ReentrantLock, sockets, and RandomAccessFile, controlled by `CRATONVM_REAL=*` switches. CI only smoke-tests five named “real path” cases, which is too narrow for subsystems this fundamental. The current design still leaves correctness risk concentrated in synthetic concurrency and I/O paths that are not the JDK’s real bytecode. citeturn28view1turn45view1

- [ ] **P1 — Stop compiling incomplete or confusingly named experimental features by default.** The `vm` crate’s default feature set includes `experimental-tls`, `experimental-jmx`, `experimental-serialization`, `experimental-aot`, `experimental-debug`, and `zgc`; at the same time, the architecture document says ZGC is experimental, metadata-only / not wired into selectable production backend dispatch in the normal path. Compiling experimental or incomplete code by default unnecessarily expands build time, binary surface, audit scope, and failure surface. citeturn37view0turn18view0

- [ ] **P1 — Break up the highest-risk giant files at real subsystem seams, not only for readability but to cap defect blast radius.** The architecture doc states that `vm/src/runtime/interpreter.rs` is roughly 47.9k lines, `jit/src/x64.rs` about 42.6k, and the `vm` crate itself about 334k lines; it also notes that the hidden `synthetic-jdk` test module inside `vm/src/vm.rs` historically rotted because it was not being compiled. These file sizes are not just style debt; they make localized reasoning, review, ownership, and regression isolation materially harder. citeturn18view0turn12view0

- [ ] **P1 — Re-tighten the lint policy; the current workspace-level blanket `allow` list is too permissive to trust as an early-warning system.** The root `Cargo.toml` allows `dead_code`, multiple `unused_*` lints, `unwrap_used`, `expect_used`, `not_unsafe_ptr_arg_deref`, `suspicious_open_options`, and many more Clippy rules across the workspace. That policy materially lowers the chance that static analysis catches real defects early, especially in a VM with pervasive `unsafe`, FFI, and feature-gated code. citeturn2view0

## Security and safety todo

- [ ] **P0 — Align the product posture for untrusted code; the current security story is internally inconsistent.** `SECURITY.md` explicitly says CratonVM is experimental, not intended for production use, and must not be used to run untrusted Java code in security-sensitive environments. Yet `docs/SECURITY_HARDENING.md` presents opt-in profiles “for running untrusted or multi-tenant workloads” and labels `CRATONVM_CONFINE_IO` a “Certified profile,” even though the same document also says the VM is not a certified sandbox. This wording is risky and needs to be unified around a single, non-marketing threat model. citeturn27view2turn27view1

- [ ] **P0 — Close or explicitly hard-disable the SecurityManager / policy bypasses instead of documenting them as caveats.** The security policy says enforcement is allow-all by default when no policy is loaded, several `checkAccess` variants are unconditional allow, and Panama / FFI downcalls are not gated by the SecurityManager at all. That means the current “hardening” story still has an obvious policy-bypass channel for native access and a permissive default for code that users may incorrectly assume is restricted. citeturn27view2

- [ ] **P1 — Treat the duplicated crypto / signature trust paths as design debt with security consequences.** `SECURITY.md` says the JAR-signature verifier is a separate implementation from the JCA `Signature` API, supports only RSA PKCS#1 v1.5, and does not implement full RFC 5280 path validation. Even though unsupported algorithms fail closed, the duplication increases the chance of semantics drift and trust inconsistencies between “general crypto” and “signed JAR trust.” citeturn27view2

- [ ] **P1 — Finish unsafe-annotation coverage and add an actual runtime UB gate.** The security policy’s unsafe inventory says several peripheral unsafe-heavy subsystems — `native-io`, `native-awt`, `cuda-bridge`, and `jfr` — are not yet fully annotated with `// SAFETY:` comments. CI also shows Miri only in a commented-out “future hardening” section rather than an active gate. For a VM/JIT/GC codebase, incomplete unsafe annotation plus no UB-oriented CI gate is a real risk. citeturn26view0turn45view1

- [ ] **P1 — Tone down the README’s “memory-safe by construction” claim.** The README currently says the VM is “memory-safe by construction” because key subsystems are Rust, but the security policy separately documents extensive unsafe use in GC, JIT, `ObjectRef`, FFI, I/O, AWT, CUDA, and JFR. The message should be narrowed to “Rust reduces classes of memory bugs, but this VM still contains audited and unaudited `unsafe` regions,” otherwise it overstates the current assurance level. citeturn44view3turn26view0

## Performance and product-direction todo

- [ ] **P0 — Stop presenting GPU offload as broadly transparent until the documented eligibility gaps are closed.** The README says eligible Java methods offload with “no annotations and no API changes,” but the roadmap still lists major functional gaps: non-void-return reduction kernels do not launch, JIT-compiled callers can bypass the offload hook, `dispatch_async` is synchronous underneath, and the analyzer only accepts a single canonical counted loop shape. That is not “transparent” in the ordinary sense; it is a narrow fast path with important exclusions. citeturn44view3turn19view2

- [ ] **P0 — Prioritize the repo’s own largest published CPU regressions instead of spreading optimization work too broadly.** The public README still shows HashMap at 21.2× slower than HotSpot, Binary Trees at 8.34× slower, and String/Regex at 7.7× slower. Those are not rounding-error gaps; they are product-shaping deficits and should drive hotspot selection, benchmark gating, and regression budgets. citeturn44view3

- [ ] **P1 — Finish the moving-young collector optimization work before considering any default flip.** The internal throughput note says the post-fix moving-young path is still 2.1× slower than the default on `bt18`, still pays a sizable codegen penalty, still keeps `pointer_map` as an `FxHashMap`, still disables self-call spill elision under moving-young, and still has an unpriced `jit_frame_record` helper consuming 8–13% of both builds. The document itself says a default flip still needs a workload mix rather than one benchmark. citeturn25view1

- [ ] **P1 — Keep attacking redefine / class-define invalidation costs; the repo keeps rediscovering them as top-tier throughput defects.** The Spring AOT bug log records that `JitCache::invalidate_matching` once burned about 31% of total CPU on a representative run because it did whole-cache work even when nothing matched, and the Mockito redefine issue shows a second cache-invalidation design hole on the interpreter/quickening side. This is not one isolated bug family; it is an architectural weak spot around invalidation granularity and generation-aware caching. citeturn33view0turn31view0

- [ ] **P1 — Treat the remaining framework throughput gap as a first-class roadmap item, not just a pile of one-off probes.** The open Mockito redefine note says the post-mock state can be about 2000× slower than HotSpot for a trivial call site. The Spring bug log also documents cases where Jython import time was about 560× slower than HotSpot and where AOT-heavy classes, though no longer crashing, are still far slower than HotSpot. The repo needs a named throughput program for framework compiler / parser / reflective workloads, not only correctness-driven bug hunts. citeturn31view0turn34view1

- [ ] **P2 — The next missing features/directions are already obvious from the repo’s own roadmap, and they are still missing.** The roadmap still calls out incomplete pre-Java-7 verifier support, incomplete `java.util.concurrent` parity, incomplete AArch64 parity, unstable real-JDK boot from `java.base`, incomplete JNI coverage and lifecycle handling, incomplete JFR event coverage, and incomplete module-system semantics. Those are not stretch goals anymore; they are the unresolved product holes that still define the platform’s ceiling. citeturn19view2
