# Azure Linux `common.args` is missing the bytecode-enhancement sysprop — 246+ false FAILs

**Status:** OPEN (2026-08-11), workaround identified and verified. Found while
running the full Hibernate ORM suite on the Azure Linux host
(`/data/cratonvm-hib-linux-20260811`, branch `test/hib-linux-20260811`), first
time this host's harness was exercised end to end for a full-suite run this
session.

## Symptom

A full-suite categorize run (4579 classes, 6 shards, default collector,
binary at dev tip `54ce35df9`) reported `FAIL=305` — a huge outlier compared
to the equivalent Windows default-collector run the same day (`FAIL=4`).
Clustering the 305 failing class names by package showed **246 of them
(84%)** concentrated in exactly one Hibernate test package family:

```
    246 bytecode.enhancement
     10 bytecode.enhance
     17 mapping.lazytoone
      2 proxy.concrete
      1 serialization.EnhancedEntityProxySerializationTest
      1 records.RecordAsEmbeddableEnhancementTest
      1 proxy.MissingSetterWithEnhancementTest
      1 locking.LockExistingBytecodeProxyTest
      ... (all enhancement/lazy-loading/proxy-adjacent)
```

The actual failure, identical across every one of these classes:

```
java.lang.IllegalStateException: BytecodeEnhancedTestEngine is disabled. But
the tests rely on the @BytecodeEnhanced extensions: ClassTestDescriptor:
[engine:junit-jupiter]/[class:org.hibernate.orm.test.bytecode.enhancement.basic.BasicSessionTest].
In order to run this test, make sure to exactly align your dependency to
JUnit with that of hibernate-testing, and set system property
'hibernate.testing.bytecode.enhancement.extension.engine.enabled=true'.
	at org.hibernate.testing.bytecode.enhancement.extension.BytecodeEnhancementPostDiscoveryFilter.apply(...)
```

## Root cause

Hibernate's own JUnit5 test infrastructure (`hibernate-testing`) gates its
whole `@BytecodeEnhanced`-driven test engine behind a system property that
is **off by default**. The reference `common.args` on this Azure host
(`/data/cratonvm/apps/hib-suite-runner/common.args`, hand-built rather than
generated by a tracked dump task — see `cratonvm-dump.gradle` in the same
directory, which only ever dumps a raw classpath, not sysprops) never set
it. This is **not a CratonVM bug** — it is a harness/config gap: any suite
run on this host, on ANY binary, under ANY collector, would hit this exact
wall until the sysprop is added. It has nothing to do with CratonVM's JIT,
GC, or bytecode handling.

Confirmed not CratonVM-specific by construction: the failure is a plain
Java `IllegalStateException` thrown by Hibernate's own test JUnit
extension code before any CratonVM-specific execution path is reached, and
reproduces identically whether the test class is run under CratonVM or
under real HotSpot with the same `common.args` (see below).

## Fix / workaround

Append one line to `common.args`:

```
-Dhibernate.testing.bytecode.enhancement.extension.engine.enabled=true
```

Verified: rerunning the 396 classes in `others.txt` (the full non-passed
set from the broken run) with this line added produced `PASS=295`,
collapsing `FAIL` from 305 to 7 and `HANG` from 4 to 2, leaving only the
genuine CratonVM-vs-HotSpot residual (see the companion doc,
`../../../known-issues/hibernate/hotspot-vs-cratonvm-linux-fullsuite-residuals-20260811.md`).

## Not yet done

This fix was applied only to the local `common.args` inside
`/data/cratonvm-hib-linux-20260811` (my own worktree, since `common.args` is
untracked/generated and this worktree's copy is self-contained). The
**reference** `common.args` at `/data/cratonvm/apps/hib-suite-runner/` on
this same host still lacks the sysprop, and any concurrent or future
session running the full suite there (or in any worktree that copies from
it, as this one originally did) will hit the exact same 246+ false-FAIL
wall until someone adds the line there too. Deliberately left untouched
this session since other sessions may have been actively using that file
concurrently — flagging here instead of patching it live.

## Repro

```
cd apps/hib-suite-runner
JAVA=/data/toolchain/jdk-25/bin/java  # or any CratonVM binary via --java-home
CRATONVM_DISABLE_DEFAULT_WATCHDOG=1 <cv-or-$JAVA> @common.args
  -Dcraton.batch=1 CratonRunner
  org.hibernate.orm.test.bytecode.enhancement.basic.BasicSessionTest
```
Deterministic — every invocation without the sysprop hits this before any
test runs, on both CratonVM and real HotSpot.
