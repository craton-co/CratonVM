## Tooling correction: `invocations` in `--dump-native-registry` is NOT useless

A lane concluded that "the registry dump is taken at registration time, so
`invocations` is useless for ownership and `owns_slot` is the proof." The
first half is wrong and the correction matters, because the whole method in
`HANDOFF-20260814` §4 rests on this tool.

MEASURED, two dumps on the `d2e127930` binary under `--jdk-only`:

| workload | rows with non-zero `invocations` | `Handler.setLevel` |
|---|---|---|
| `RJdkHello` | **120** of 10,640 | `invocations=0` |
| `RJdkIntrinsics3` | **392** of 10,640 | **`invocations=2`** |

The counter works. It read zero for `Handler.setLevel` under `RJdkHello`
because `RJdkHello` never calls `setLevel`. The dump also carries a top-level
`invocations` block (`intrinsic: 267, bridge: 2818` on the `RJdkHello` run),
which alone disproves "taken at registration time".

The rule, stated properly:

- **`owns_slot=true` proves OWNERSHIP** — this registration holds the slot.
  It is workload-independent.
- **`invocations > 0` proves the body RAN**, and only in that run. It is
  workload-DEPENDENT, so it is evidence only if the workload you dumped
  against actually exercises the triple.
- Dumping against a workload that does not call your method and concluding
  "invocations is broken" gets the tool exactly backwards.

**SECOND CORRECTION, from the performance lane (MEASURED):** the `invocations`
count is **not a true count**. It under-reports by two to three orders of
magnitude, and does so in the `--nojit` arm as well — 1,000,000 `HashMap.put`
calls register as about **3,000**. So:

* `owns_slot` — **trustworthy**, use it for ownership.
* `invocations > 0` — **trustworthy as a boolean**: it proves the body ran.
* the *magnitude* of `invocations` — **do not use it**. It is not a call count,
  and no lane should reason from its size or compare two rows by it.

`HANDOFF-20260814` §4 recommends this instrument without that caveat.

Row keys, for reference: `class, descriptor, name, kind, kind_stated,
kind_chosen, registered_by, overwrote, owns_slot, invocations,
real_declaring_method, image_declaring_method`.

Also worth knowing on this host: the flag needs a **Windows** path. Git Bash's
`/tmp` is a POSIX mapping the VM (a native Windows binary) does not resolve,
so `--dump-native-registry /tmp/reg.json` writes somewhere `ls` can see and
native tools cannot.

## CORRECTION: the `gc::guard` W7-84 warning is NOT a reference-slot census

Earlier in this session the orchestrator asserted, in a lane brief and in the
`RSslLiveSession` write-up, that the `Value::Int` written into
`ServerSocket.impl` was "silently dropped by the field-layout guard" and that
this was "the same defect class as the `gc::guard` W7-84 warning that fires
~16 times on every VM start". **Both halves are false**, and lane G25
falsified them in source and by measurement.

**What actually happens to the int.** It is not dropped. It is *actively
written as null*:

```
NativeContextImpl::set_field         vm/src/vm/vm_exec.rs:11200
 -> VmHeap::set_field_as(.., b'L')   gc/src/heap.rs:880
 -> coerce_field_value_by_descriptor gc/src/heap.rs:1674
      Value::Int(_) | Value::Long(_) => Value::Object(None)
```

That coercion is deliberate and documented (tag `S111r29`); it exists so a
bogus `Int(capacity)` into `HashMap.table` degrades to null and
`HashMap.resize()`'s `(oldTab == null) ? 0 : oldTab.length` branch handles it.
It is **bidirectional**: an `Object(None)` written into an `I`/`Z` slot becomes
`Int(0)`, which is why the fourth write in that native set `closed = false`.
It is silent unless `CRATONVM_DBG_OVERLAY` is set — the detector at
`vm_exec.rs:11290` names this exact species and is flag-gated.

**W7-84 is a different code path entirely.** Measured with
`CRATONVM_DBG_LAYOUT=1` over a full `--jdk-only` run: *every* W7-84 warning is
`class_id=ClassId(12) index=0` — **one class, one slot**, the VM's own
class-mirror populator writing over `java.lang.Class.cachedConstructor`,
exactly as the warning text says. Native reference-slot writes produce **no
warning at all** (autobox versus descriptor coercion — different paths). The
"~16 per start" is 12 rate-limited lines standing for at least 33 stores of
that single site.

So: do not use W7-84 warning counts as a proxy for reference-slot violations.
The real census is 271 sites, built by source scan (`scratchpad/g25/census.py`)
— `phases_early.rs` 68, `servlet.rs` 22, `http2.rs` 19, `net_channels.rs` 19,
`tls.rs` 18; by class, `ArrayList.elementData` 56, `SocketChannel` 22,
`HashMap.table` 19. That is a lower bound (single-line allocations only), and
the systemic fix is a layout-aware field writer, not 271 individual edits.

## CORRECTION: the JDK's sources ARE readable on this machine

Every lane brief in this session said *"`C:\craton\jdk25src` is ABSENT — you
cannot read JDK sources locally; work from the oracle's behaviour."* The first
clause is true and the second is **false**.

```
C:\Program Files\Eclipse Adoptium\jdk-25.0.3.9-hotspot\lib\src.zip   52,462,198 bytes
```

`src.zip` ships with the JDK and contains the full `java.base` (and more)
sources for exactly the build being used as the oracle. Two lanes worked this
out for themselves and it changed their results:

* the URI lane read `URI.parseAuthority` and found the real rule is not "reject
  a bad port" but "a failed server-based parse DEMOTES the authority to
  registry-based, nulling host, userInfo and port together" — so the obvious

* the timezone lane read `ZoneInfoFile.java` and `ZoneInfo.java` and found the

  `dstSavings` is the start rule of the last pair with `ZoneInfoFile`'s swap,

Neither is derivable from black-box probing in reasonable time; both are two
minutes of reading.

**Use it.** `unzip -p "$JAVA_HOME/lib/src.zip" java.base/java/net/URI.java`,
or extract once to a scratch directory. It does not replace the oracle — the
oracle is what settles behaviour, and a source reading can be wrong about what
the shipped build does — but it is the difference between transcribing a
contract and guessing at it.

## CORRECTION: "the young collection never runs" was chasing the wrong collector

`G20-1` reported, and this orchestrator repeated as the session's headline
performance finding, that **`moving_young: cycles=0`** meant the generational
moving-young path was *requested and never ran*, making every collection a
whole-heap non-moving pass. Lane `G27` falsified it.

**`gen_heap.rs` is not the collector in a default run.** `vm/src/config.rs:769`
has defaulted to `GcAlgorithm::Zgc` since 2026-08-10, and
`grep -c moving_young gc/src/zgc.rs` returns **0**. The gating predicate at
`gen_heap.rs:5719` is not waiting for anything — it is never reached.

All three diagnostics the finding rested on mislead in the same direction:

* `moving_young_requested=true` is `gc_quiescence::moving_young_enabled()` — a
  **JIT-codegen capability flag** read by every backend, not a request for a
  collection;
* `"no collection has run yet"` fires because **ZGC never calls
  `record_collector_decision`**; only `gen_heap.rs` and `g1.rs` do;
* the whole `[GC] cards:` / `young_sweep:` block is generational-only and
  structurally zero.

The repo already said so in two places the profile did not read:
`harness-guard.sh:637` ("ZGC since 2026-08-10") and `zgc.rs:2244` ("this
backend at 6.6x/11.3x/18.4x the generational collector"). `G20-1` §8 flagged
the `zgc-*` counter labels as unexplained and guessed "legacy prefix" — the
label was the collector, and chasing it was the finding.

**The predicate itself works.** On the same workload with the generational
backend selected: 8/8 cycles MOVING, `moving-jit-coverage-proven`,
`coverage_fallbacks=0`.

## THIRD AND FINAL CORRECTION on `invocations`: it is a FLOOR, and zero proves nothing

Lane G33 found the mechanism. **The counter is not broken; what it is attached
to is.** `record_invocation` is one bounds-checked index and one relaxed
`fetch_add` — not sampled, not saturating, not `cfg`-gated. It takes a
`NativeMethodId`, which a caller can only hold if it resolved the triple
**through the registry** — and every optimisation to the native path consists
of removing that resolution from the hot path. Each one took the counter with
it.

So `invocations` is an exact count of *registry-resolved dispatches* and a
**lower bound** on Java-level calls.

Two mechanisms, causally isolated on the `783685c34` binary:

**1. The interpreter's intrinsic table — arm-independent.**
`CachedInvokeTarget::Intrinsic` holds a raw `fn` pointer and never consults
the registry again. 100,000 calls each:

| native | `--nojit` | `--nojit` + `CRATONVM_DISABLE_INTRINSICS=1` |
|---|---:|---:|
| `Math.abs` | **1** | **100,000** |
| `Object.hashCode` | **1** | **100,000** |
| `System.identityHashCode` (control) | 100,000 | 100,000 |

## PROCESS CORRECTION: `cargo` was never the blocker for test files

Every lane brief this session said **"DO NOT run `cargo build`/`check`/`test`"**
— correct, because seven agents contending for one target directory would

caveat.**

For a test file whose only dependency is `std`, it is not true:

```bash
cd native-builtins
CARGO_MANIFEST_DIR="$(pwd)" rustc --edition 2021 --test -O -o /tmp/g.exe tests/registrar_drift.rs
CARGO_MANIFEST_DIR="$(pwd)" /tmp/g.exe
```

VERIFIED by the orchestrator, not inherited:

| gate | build | result |
|---|---|---|
| `registrar_drift.rs` | `rustc` exit 0 | **7 passed, 0 failed**, 0.82s |
| `registrar_reachability.rs` | `rustc` exit 0 | **5 passed, 0 failed**, 0.91s |

Two gates that had **never been run in their lives** — one of them written
three waves ago and carrying "the Rust gate has not been compiled or run" as
its standing caveat — take under a second each.

This route was already in use for *logic extraction*: three lanes copied
functions into a scratch harness and ran them under `rustc --test` (one
validated 116 of 116 oracle rows, one a six-state machine, one a recording
contract). What nobody tried was pointing it at **the real file in place**.

1. If the file is a `tests/*.rs` depending only on `std` — compile and run it

2. Otherwise, extract the changed logic verbatim into a scratch harness and
   run that.
3. Only then fall back to "parses under `rustfmt`", which is a syntax check
   and nothing more.

The no-`cargo` rule stands. It was never a no-compiler rule.
