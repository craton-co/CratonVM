# JDK-Only Mode

`--jdk-only` embodies the foundational primary target and architecture of CratonVM: running authentic OpenJDK class libraries directly, treating real JDK bytecode as authoritative with strict specification fidelity, rejecting synthetic stand-ins and compatibility stubs.

> **Status: The foundational primary target and default of the `cratonvm` launcher.**
> Under JDK-only mode, genuine class bytecode from OpenJDK runtime images is authoritative.
> If a workload requires accelerated cold start or specialized execution paths, the `--compatible` optimization layer is available.

## Architectural Principles

In JDK-only mode, real class bytes are strictly authoritative:

- A real JDK runtime image (`jmods/java.base.jmod` or modular `lib/modules`) is required. JDK 21 and JDK 25 runtime images are the primary targets.
- No non-array class is fabricated: a class with no real bytecode raises specification-compliant `ClassNotFoundException` or `NoClassDefFoundError` instead of receiving a synthetic stand-in.
- No synthetic-stub native method is registered or invoked.
- Concrete Java bytecode always takes precedence over registered natives (except for reviewed compiler intrinsics).
- An `ACC_NATIVE` method binds to a genuine bridge or reviewed intrinsic, or fails cleanly with a structured `MissingNative` link error.

Class fabrication prevention and strict native registration are enforced across the runtime. Dispatch paths, warm loops, and compiled code adhere to authentic class definitions.

Note that Java class file `ACC_SYNTHETIC` attributes (generated by compilers for inner classes, bridges, etc.) are standard Java bytecode constructs and are fully supported. What `--jdk-only` forbids is artificial VM-level compatibility substitution.

## Flags and Diagnostics

| Flag | Effect | Default |
|------|--------|---------|
| `--jdk-only` | Real JDK execution with strict specification fidelity; compatibility substitutions rejected. | Enabled (Default) |
| `--compatible` | Specialized acceleration layer activating native Rust stand-ins and fast paths. | Disabled |
| `--jdk-only-report <FILE>` | Violation and class origin counter report exported as JSON on shutdown. | — |
| `--dump-class-origins <FILE>` | Comprehensive class-origin census written to JSON on shutdown. | — |
| `--trace-jdk-only` | Reports recorded policy discrepancies to stderr at `WARN` level. | Disabled |
| `--explain-jdk-only` | Long-form diagnostic explanation per entry; preserves non-redacted paths. | Disabled |

Passing `--jdk-only` confirms the active default policy. It conflicts with `--synthetic-jdk` (which replaces the entire JDK library with standalone Rust implementations) and with `--compatible` (which enables the acceleration layer).

The diagnostic flags operate under both `--jdk-only` and `--compatible`. Under `--compatible`, the diagnostic logging identifies which fast-path stand-ins were engaged, providing clear metrics on execution characteristics.

`--trace-jdk-only` drains the append-only violation logs immediately after VM bootstrap (capturing registration checks) and at shutdown.

`--explain-jdk-only` disables path redaction in report files. Keep it disabled when committing census files or attaching logs to public bug reports.

## Class Origins: Generated vs. Fabricated

`--dump-class-origins` tracks the exact origin of every loaded class. Standard JVM mechanisms generate classes dynamically without a disk `.class` file; these are valid JVM behaviors and are fully permitted under `--jdk-only`:

| `origin` Tag | Meaning | `--jdk-only` Status |
|---|---|---|
| `boot-image` | Loaded from the JDK runtime image (`jmods/` or `lib/modules`). | Allowed |
| `application-class-path` | Loaded from application classpath or JAR archives. | Allowed |
| `user-defined` | Defined dynamically by custom user class loaders. | Allowed |
| `vm-array` | Array class generated dynamically by the VM runtime. | Allowed |
| `hidden-class` | Hidden class defined via `MethodHandles.Lookup::defineHiddenClass`. | Allowed |
| `generated-lambda` | Lambda implementation class spun at an `invokedynamic` call site. | Allowed |
| `generated-proxy` | Dynamic proxy class spun via `java.lang.reflect.Proxy`. | Allowed |
| `reflection-accessor` | Dynamic bytecode accessor spun for reflection dispatch. | Allowed |
| `vm-internal` | VM-internal infrastructure class. | Allowed |
| `compatibility-stub` | Fabricated stand-in with no authentic bytecode. | **Forbidden** |

In JDK-only mode, the `compatibility-stub` count remains strictly zero.

## Auditing and Inspection

To inspect the class origins and native dispatch profile of an application:

```bash
cratonvm --dump-class-origins origins.json \
         --dump-native-registry natives.json \
         --jdk-only-report jdk-only.json \
         --classpath . MyApp
```

The resulting `jdk-only.json` aggregates loaded classes across `boot_image_classes`, `application_classes`, `generated_classes`, and `compatibility_classes`, alongside per-category native dispatch counts.

To trace execution diagnostics directly on the console:

```bash
cratonvm --trace-jdk-only --classpath . MyApp
```

## The Compatible Optimization Layer

When fast cold start or specialized acceleration is preferred over pure bytecode execution of the JDK boot libraries, run with `--compatible`:

```bash
cratonvm --compatible --classpath . MyApp
```

Compatible mode (`--compatible`) and synthetic stubs are engineered as an optimization layer for fast cold-start loading and specialized high-throughput execution paths. `--compatible` activates CratonVM's native Rust stand-in classes and fast-path bridges, providing instant startup for CLI utilities and high-throughput paths for specialized workloads. It is also the default policy for embedded environments (`libcratonvm`, `cratonvm-embed`, and `VmConfig::default()`) where host JDK images may be absent or minimal.
