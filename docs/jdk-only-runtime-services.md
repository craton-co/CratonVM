### Evidence provenance

The report this inventory implements was written **before** the two native-category
and object-layout audits and the known-issue records existed. Several rows
inherited a premise those artefacts have since disproved. Every evidence cell is
therefore tagged:

* **re-verified** — the claim has been re-read against a named file and symbol
  in this repository and/or against a named section of a later audit. It is a
  source reading only: "present in the tree" never means "compiles" or
  "passes".
* **inherited** — the claim comes from the original research report and was
  **not** re-checked. Treat it as older than the re-verified rows and re-verify
  before acting.

Two standing limits on every re-verified claim below:

* The audits measured **one** JDK image (25). CI pins `java-version: '25'` in
  every job (`.github/workflows/ci.yml`); **JDK 21 and 17 have no coverage at
  all**. Any 17 / 21 / 25 matrix mentioned anywhere is a *proposal*, and a
  verdict that turns on what a class declares (`ACC_NATIVE`, field order, method
  presence) may differ on another feature version.
* The stub ratchet asserts `BASELINE_SYNTHETIC_STUBS = 157` **exactly** with
  `SLACK = 0`, and separately asserts only `total >= 8_000` as a vacuity floor.
  Do not cite any specific total-registration figure as a verified number.

No static review can produce a genuinely exhaustive missing-method list across
"any JDK": native surfaces and class-library internals vary by feature version.
The tables below are the **confirmed inventory visible in this repository**, and
therefore the *minimum* scope that must be resolved or explicitly excluded. They
are not a ceiling.

## Closure rule

An entry closes only when it is one of:

1. implemented as a **reviewed bridge** (`NativeKind::Bridge`, reviewed per
   [`jdk-only-native-review.md`](jdk-only-native-review.md));
2. implemented as a **reviewed intrinsic** (`NativeKind::Intrinsic`, with
   differential parity evidence);
3. **executed from real bytecode** (the native is deleted from the strict path);
4. implemented as **legitimate generated class bytes** with a non-`CompatibilityStub`
   `ClassOrigin`; or
5. **explicitly out of scope**, failing with a specification-consistent error
   (`ClassNotFoundException` / `NoClassDefFoundError` / `UnsupportedOperationException`
   / a documented platform error) rather than a fabricated success.

"It stopped appearing in the census" is **not** closure. A symptom can disappear
because a ban was added, a call path changed, or the vector stopped exercising
it. Closure requires naming which of the five above applies, and a test.

| `OPEN` | Not started, or in progress with no landed change. |

| `CLOSED(n)` | Closed under closure rule *n* above, with the test named. |

## Working notes

**The 157 are not homogeneous — and the dominant defect runs the other way.**
This note previously said the most important fact in the document was that JMX
and `Function$Identity` sit inside the 157 as permanent bridges wearing the
wrong tag. That was true when the research report was written and is **no longer
true**: both clusters were retagged `NativeKind::Bridge` in the same change that
reverted the global drop, and neither is among the residual 157
(the ambient-category audit §4). What survives from the
old note is only the procedural lesson: a global "157 → 0" deletion reproduces
that regression, so the path is **reclassification first, deletion second**.

The larger defect the audit actually found is the **inverse** — wholesale
*over*-tagging as `Bridge`. 1,195 `native-collections` registrations inherit one
`set_category(Bridge)`, and **not one of them targets an `ACC_NATIVE` method**;
122 `native-awt` registrations inherit a single function-pointer `with_category`,
and only 10 do. That is roughly 1,300 registrations claiming a boundary that
does not exist — an order of magnitude more than the 157 under-tagged entries
the report focused on, and it has the opposite failure signature. Under-tagging
breaks a boot loudly and had to be reverted globally; over-tagging breaks
nothing today, silently inflates the bridge count, hides real stubs from the
census, and lets a compatibility shim survive `--jdk-only`. It is therefore both
the bigger correctness leak *and* the one that is safe to work on incrementally.
Plan wave 2 around it, not only around the 157.

**Ambient classification is the shared root cause.** Neither direction is a
typo: `register()` takes no kind, so the tag is a property of the *caller's* call
chain, of statement order inside a function, and of which registrar ran last
(registration is last-write-wins). That is why an audit was needed to find any of
this, and why `registered_by` / `overwrote` must be populated before any
retagging begins.

**Compatible mode must be byte-for-byte unchanged.** Every row above is scoped
to `--jdk-only`. `--real-jdk` (the default) keeps today's behaviour, and that is
checked by the existing regression suite plus the stub ratchet.

**Wave-1 enforcement is narrow.** Only class fabrication (contract §5) and stub
registration (contract §4) enforce. Everything else in these tables is recorded
and counted. Do not read a green stage-1 `--jdk-only` run as evidence that a row
is closed.

**Per-JDK generation, and the single-image caveat.** The authoritative instance
list for a given image comes from
`target/jdk-only-audit/jdk-<feature>-missing-natives.json` and
`…-synthetic-dependencies.json`. See the JDK-only census audit §6.
Every `javap`-derived verdict cited in this file — class present, method
present, `ACC_NATIVE`, abstract, field order — was measured against **one image,
JDK 25**, and CI pins `java-version: '25'` in every job. JDK 21 and 17 have no
coverage today, so a 17 / 21 / 25 matrix is a *proposal*, not a baseline. Where a
verdict could plausibly differ across feature versions (native surfaces and
class-library internals do vary), say so in the row rather than generalising
from the one image that was measured.

**Row hygiene.** When a row's evidence is re-verified, replace the claim *and*
its provenance note together — a corrected claim with an inherited date is worse
than an uncorrected one, because the next reader cannot tell which half moved.
A row that flips status must still name which of the five closure rules it is
travelling toward; `MEASURING` and `ENFORCING` are waypoints, not closures.
